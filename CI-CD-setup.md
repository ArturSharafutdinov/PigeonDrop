# CI/CD в PigeonDrop: как устроено

Описание текущего конвейера: что запускается, когда и почему сделано именно так. Файл написан как основа для переноса сборки других приложений в GitHub Actions. Пошаговая настройка сервера (VPS, Coolify, PostgreSQL, секреты) лежит в `backend/DEPLOY.md`, здесь её нет.

Источник правды: `.github/workflows/ci.yml` и скрипты в `.github/scripts/`. Если файл расходится с ними, верьте им.

## Общая картина

```
pull request / push в main / ручной запуск
   └─ GitHub Actions (.github/workflows/ci.yml)
        ├─ changes        — какие части репозитория затронуты (только для PR)
        ├─ backend        — проверки Go-сервера (+ пробная сборка образа в PR)
        ├─ watch          — тесты и сборка приложения для часов (zeus build)
        ├─ deploy-script  — тесты самих скриптов деплоя
        └─ stt            — тесты сервиса распознавания речи (+ сборка и проба образа в PR, если менялся stt/)
              │
              ▼  (только push в main или ручной запуск)
        deploy      (нужны backend и deploy-script)      deploy-stt  (нужны stt и deploy-script)
          1. вход в GHCR под GITHUB_TOKEN                  то же самое для сервиса распознавания речи,
          2. image-changed.sh: нужен ли деплой             со своим образом, своим приложением Coolify
             (сравнение с тегом :deployed)                 и своим тегом :deployed; перед публикацией
          3. docker build + push в GHCR                    образ запускается с боевыми лимитами и
             (:<коммит> и :latest)                         распознаёт искусственную запись
          4. coolify-deploy.sh: просит Coolify
             выкатить и ждёт результата
          5. при подтверждении от Coolify: тег
             :deployed на этот образ
```

Деплоятся два образа: Go-сервер из `backend/` и сервис распознавания речи из `stt/`, каждый в своё приложение Coolify, независимо друг от друга. Приложение для часов так не выкладывается: оно публикуется через Zepp. Его собирают и тестируют, но результат сборки никуда не уходит.

Образы собираются в GitHub Actions и кладутся в GHCR (`ghcr.io/artursharafutdinov/pigeondrop-backend` и `…/pigeondrop-stt`). Coolify на VPS ничего не собирает: он только скачивает `:latest` и перезапускает контейнер. Поэтому сборка не конкурирует за ресурсы с другими проектами на общем VPS.

## Когда что запускается

| Событие | Проверки | Деплой |
|---|---|---|
| Pull request | только для затронутых частей (см. ниже) | нет |
| Push в ветку без PR | не запускается (в `push` указан только `main`) | нет |
| Push в `main` | все | да, если проверки прошли и `backend/` отличается от выкаченного |
| Ручной запуск («Run workflow») | все | да, всегда, оба образа |

## Как экономятся минуты Actions

- **Тяжёлые проверки только в PR.** Push в ветку сам по себе ничего не запускает: проверки идут, когда у ветки есть PR. После слияния в `main` проверки запускаются снова, потому что они допускают деплой.
- **Только затронутое.** Задача `changes` смотрит, какие файлы меняет PR (`git diff HEAD^1 HEAD` на слитом коммите PR, нужна история из двух коммитов). Затем:

  | Часть | Файлы | Какие задачи запускаются |
  |---|---|---|
  | `backend` | `backend/**` | `backend` |
  | `watch` | `PigeonDrop/**` | `watch` |
  | `scripts` | `.github/scripts/**` | `deploy-script` |
  | `stt` | `stt/**` | в задаче `stt` добавляется сборка образа и проба (тесты на стандартной библиотеке идут всегда: они занимают секунды) |

  Изменение самого `.github/workflows/ci.yml` затрагивает все части. PR только с документацией запускает одну короткую задачу `changes`. Пропущенная по условию задача считается пройденной для защиты ветки. Не push и не PR (push в `main`, ручной запуск) запускают всё. Если разобрать изменения не удалось, тоже запускается всё.
- **Отмена устаревших запусков.** Группа `ci-${{ github.ref }}`: новый push в PR отменяет предыдущий запуск этого PR. Запуски `main` не отменяются: отменённый посреди пути деплой был бы потерян (это учтено в `backend-changed.sh`).
- **Кэш зависимостей.** Модули Go и кэш сборки (`setup-go`) по хешу `backend/go.sum` и `backend/tools/go.sum` (в `tools/` свои модули генераторов кода, их долго компилировать с нуля); загрузки npm для `zeus-cli` (`actions/cache`, ключ с версией CLI). Кэша слоёв Docker нет: слой со сборкой зависит от `VERSION` (коммит), поэтому почти всегда пересобирался бы, а выигрыш только на скачивании модулей.
- **Меньше задач.** Минуты считаются по задаче с округлением вверх, и каждая платит за свой старт и checkout. Тесты и сборка приложения для часов объединены в одну задачу `watch`. Пробная сборка Docker-образа идёт только в PR: при push в `main` образ собирает задача деплоя.

Прочие настройки workflow:

- **Отмена запусков.** Группа `ci-${{ github.ref }}`. Для pull request новый запуск отменяет предыдущий, для `main` не отменяет (иначе пропал бы деплой).
- **Права.** На весь workflow только `contents: read`. Задаче `deploy` дополнительно выдано `packages: write`, чтобы она могла пушить в GHCR.
- **Таймауты** заданы у каждой задачи (5–25 минут), чтобы зависший запуск не жил вечно.

## Задачи проверки

`backend`, `watch` и `deploy-script` выполняются параллельно, после `changes`.

**`backend`.** Поднимает PostgreSQL 17 как service-контейнер, адрес передаётся в `TEST_DATABASE_URL`. Шаги по порядку:

1. Сгенерированный код свежий: `make generate`, затем `git diff --exit-code -- . ':!tools'`. Если кто-то поправил `api/openapi.yaml` или SQL и не перегенерировал код, задача падает.
2. `gofmt`: `test -z "$(gofmt -l .)"`.
3. `go vet ./...`.
4. `go test -race ./...`.
5. Пробная сборка Docker-образа (без push), только в PR.

Переменная `REQUIRE_DB=1` заставляет тесты падать, если базы нет. Без неё тесты без базы пропускаются, и запуск выглядел бы зелёным, ничего не проверив.

**`watch`.** Node 24. Сначала `npm test` в `PigeonDrop/`: зависимости ставить не нужно, тесты загружают настоящие исходники приложения, а модули `@zos/*` подменены заглушками. Затем ставит `@zeppos/zeus-cli@1.9.3` (версия зафиксирована), копирует `config.example.js` в `config.js` и запускает `zeus build < /dev/null`. Настоящий `config.js` не в git (там реальный адрес сервера), для компиляции хватает примера.

**`stt`.** Тесты сервиса на подменной модели (стандартная библиотека Python, секунды) идут всегда. В PR, которые меняют `stt/` (или сам `ci.yml`), добавляется сборка образа (скачивает модель около 640 МБ, несколько минут) и проба `stt/smoke-synthetic.sh`: контейнер запускается с боевыми лимитами (3 ГБ без подкачки, 2 ядра) и распознаёт две искусственные записи (тишина и тон) через настоящий протокол. Настоящие записи в репозитории не лежат, поэтому проверяется, что образ стартует, загружает модель и отвечает; как он справляется с речью, показывает `stt/smoke.sh` на ваших записях.

**`deploy-script`.** Запускает `.github/scripts/test/test-coolify-deploy.sh` и `test-image-changed.sh`. Скрипт деплоя — единственная часть конвейера, которая иначе упала бы только в день релиза, поэтому она проверяется заранее против поддельного API Coolify (`fake-coolify.mjs`): успех, провал, отказ, недоступность, отсутствие секретов.

## Задача `deploy`

Условия запуска: `needs: [backend, deploy-script]` (при push и ручном запуске они выполняются всегда) и событие `push` или `workflow_dispatch`. Checkout делается с `fetch-depth: 0`: скрипту сравнения нужна вся история.

### 1. Вход в реестр

Вход в `ghcr.io` под `github.actor` с встроенным `GITHUB_TOKEN`. Отдельный токен для публикации не нужен. Имя образа: `ghcr.io/<владелец>/<репозиторий>-backend`, в нижнем регистре (регистр в Docker обязателен). Оно кладётся в `$GITHUB_ENV` как `IMAGE`.

### 2. Нужен ли деплой: `.github/scripts/image-changed.sh`

Один скрипт для обоих образов; различаются они переменной `CHANGE_PATHS` (для сервера `backend .github/scripts`, для распознавания речи `stt .github/scripts`: изменение скриптов деплоя проверяется на обоих образах) и `WHAT` (название для сообщений). Пишет `deploy=true` или `deploy=false` в `$GITHUB_OUTPUT`. Алгоритм:

1. Ручной запуск: всегда `true`.
2. Скачивает образ с тегом `:deployed`. Не получилось (тега ещё нет): `true`.
3. Читает из образа метку `org.opencontainers.image.revision`: это коммит, из которого он собран. Метки нет или такого коммита нет в checkout: `true`.
4. `git diff --quiet <выкаченный коммит> $GITHUB_SHA -- $CHANGE_PATHS`. Различий нет: `false`, образ не пересобирается и сервер не перезапускается. Различия есть или сравнить не удалось: `true`.

Любая неясность означает «деплоить»: лишний деплой стоит несколько минут, а пропущенный оставляет сервер устаревшим, и никто этого не замечает.

**Почему сравнение с выкаченным коммитом, а не с предыдущим push.** Раньше сравнивали с предыдущим push, и это терялось. GitHub отменяет все ожидающие запуски, кроме самого нового, поэтому два слияния с разницей в секунды отменяли деплой первого. Следующий push, затрагивающий только документацию, видел «backend не менялся» и пропускал деплой насовсем. Так потерялось удаление старых маршрутов (PR #13, 2026-10-05). Выкаченный коммит записан в самом образе, поэтому ни отменённый запуск, ни упавший деплой ничего не теряют: следующий push их подхватит.

### 3. Сборка и публикация образа

Шаг выполняется, только если предыдущий сказал `deploy=true`. Образ собирается из `backend/Dockerfile` с аргументом `VERSION=$GITHUB_SHA`, метками `source` и `revision` и двумя тегами:

- `:<sha коммита>` — для отката и чтобы знать, что запущено (`pigeondrop version` печатает этот коммит);
- `:latest` — то, что запускает Coolify.

Dockerfile двухэтапный: сборка на `golang:1.26-alpine` (зависимости отдельным слоем), итоговый образ `distroless/static-debian12:nonroot`, процесс не от root, в образе есть собственная проверка здоровья (`/pigeondrop healthcheck`), потому что `curl` в нём нет.

### 4. Вызов Coolify: `.github/scripts/coolify-deploy.sh`

Нужны переменные окружения `COOLIFY_URL`, `COOLIFY_TOKEN`, `COOLIFY_APP_UUID` (секреты GitHub).

1. Без любой из трёх: предупреждение `::warning::` и выход с кодом 0. Так workflow безопасно запушить до настройки Coolify: образ всё равно появится в GHCR.
2. `POST $COOLIFY_URL/api/v1/deploy?uuid=<uuid>&force=false`. Ответ 405 (старые Coolify принимают только GET): повтор методом `GET`. Любой код, кроме 200: ошибка, задача красная.
3. Из ответа берётся `deployments[0].deployment_uuid`. Если его нет: ошибка.
4. Опрос `GET /api/v1/deployments/<uuid>` каждые 10 секунд, до 90 попыток (15 минут):
   - `finished`: успех, в `$GITHUB_OUTPUT` пишется `deployed=true`;
   - `failed`, `error`, `cancelled*`: ошибка, задача красная;
   - за 15 минут ничего не решилось: только предупреждение, `deployed=true` не пишется.

`POLL_SECONDS` и `POLL_ATTEMPTS` существуют только для тестов с поддельным Coolify.

### 5. Тег `:deployed`

Шаг выполняется, только если скрипт записал `deployed=true`: образ `:<sha>` получает тег `:deployed` и пушится. Именно этот тег читает следующий запуск на шаге 2. Предупреждения (нет секретов, не дождались) тег не ставят, поэтому до настройки Coolify каждый push в `main` собирает образ заново: это ожидаемо.

## Задача `deploy-stt`

Устроена так же, как `deploy`, со следующими отличиями:

- образ `ghcr.io/<владелец>/<репозиторий>-stt` собирается из `stt/` (около 1,6 ГБ: модель внутри; без кэша слоёв сборка занимает несколько минут, поэтому образ пересобирается только когда менялись `stt/` или скрипты деплоя);
- **перед публикацией образ пробуют**: `stt/smoke-synthetic.sh` запускает его с боевыми лимитами и распознаёт искусственную запись. Образ, который не отвечает, не станет `:latest`, и Coolify ничего не получит;
- приложение Coolify другое: секрет `COOLIFY_STT_APP_UUID` (если его нет, образ всё равно собирается и публикуется, а шаг выкатки только предупреждает: так первый образ появляется до создания приложения);
- свой тег `:deployed`, поэтому изменение одного образа не пересобирает и не перезапускает другой;
- скрипт сравнения скачивает образ с тегом `:deployed` целиком (1,6 ГБ), чтобы прочитать метку коммита: на каждый push в `main` это около минуты. Если станет заметно, метку можно читать без скачивания (`docker buildx imagetools inspect`).

Создание приложения в Coolify, секрет и подключение сервера: `backend/DEPLOY.md`, шаг 9.

## Секреты и разовая настройка

| Где | Что | Для чего |
|---|---|---|
| Секреты репозитория GitHub | `COOLIFY_URL` | адрес Coolify |
| | `COOLIFY_TOKEN` | токен API Coolify с правами `read` и `deploy` |
| | `COOLIFY_APP_UUID` | UUID приложения сервера в Coolify |
| | `COOLIFY_STT_APP_UUID` | UUID приложения сервиса распознавания речи (создаётся позже, `backend/DEPLOY.md`, шаг 9) |
| VPS | `docker login ghcr.io` | чтобы Coolify мог скачать приватный образ; токен GitHub (classic) только с `read:packages`, логин под тем пользователем, под которым Coolify подключается к серверу |
| Coolify | приложение типа Docker Image, тег `latest` | запускает образ из GHCR |

`GITHUB_TOKEN` для публикации в GHCR создаётся автоматически и ничего не требует. Пакет в GHCR оставлен приватным. Токены не присылают в чат: их вводит владелец на GitHub и на VPS.

Подробности, переменные приложения, тома и типичные ошибки первого запуска (`unauthorized` при скачивании, контейнер в `Restarting`): `backend/DEPLOY.md`.

## Откат

Вручную, в Coolify: в приложении сменить **Tag** на `<sha коммита>` (список тегов на странице пакета в GitHub) и нажать Deploy. Конвейер про ручной откат не знает: тег `:deployed` остаётся на последнем коммите, который выкатил он сам. Откат кода не откатывает миграции базы.

## Что проверено, а что нет

Проверено на настоящих GitHub Actions и Coolify (2026-10-04): сборка и публикация в GHCR, вызов Coolify и ожидание результата, скачивание приватного образа, запуск, миграции, `/healthz`. Логика с тегом `:deployed` появилась позже (PR #17) и прошла тесты `deploy-script`.

Не проверено: откат сменой тега, резервные копии, поведение при двух одновременных деплоях.

## Как перенести другое приложение

Общий каркас годится для любого приложения, которое собирается в Docker-образ и выкатывается через Coolify.

**Что повторяется без изменений:**

- задачи проверки по частям репозитория, каждая со своим `working-directory` и таймаутом;
- вход в GHCR через `GITHUB_TOKEN` и `permissions: packages: write` только у задачи деплоя;
- теги `:<sha>` и `:latest` и метка `org.opencontainers.image.revision`;
- решение о деплое по тегу `:deployed`, а не по предыдущему push;
- `coolify-deploy.sh` целиком (он параметризуется только переменными окружения);
- тест скрипта деплоя на поддельном Coolify.

**Что своё у каждого приложения:**

- отдельное приложение в Coolify и свой `COOLIFY_APP_UUID` (секрет с тем же именем придётся делать на уровне окружения GitHub или с другим именем);
- пути, по которым решается деплой (`CHANGE_PATHS` в вызове `image-changed.sh`; скрипт уже общий, так сделан второй образ);
- имя образа (суффикс `-backend`, `-stt`), путь контекста сборки и `Dockerfile`;
- свои проверки (линтеры, тесты, генерация кода) вместо Go-шных.

**Подводные камни:**

- один workflow-файл на несколько приложений быстро разрастается: две задачи деплоя (`deploy` и `deploy-stt`) уже почти копии друг друга; общую часть (вход, сравнение, сборка, вызов Coolify) стоит вынести в reusable workflow (`workflow_call`) с входными параметрами: путь, имя образа, UUID приложения; третье приложение пора делать именно так;
- `fetch-depth: 0` нужен всем, кто сравнивает коммиты;
- тег `:deployed` общий для образа, поэтому у каждого приложения должен быть свой образ (своё имя);
- запуск, отменённый GitHub посреди очереди, при такой схеме ничего не теряет, но только если сравнение идёт с выкаченным коммитом; не возвращайтесь к сравнению с предыдущим push;
- у приложений на одном VPS не ставьте общий тег `:latest` в один образ: Coolify каждого приложения должен смотреть в свой образ.
