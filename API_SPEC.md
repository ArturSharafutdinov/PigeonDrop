# PigeonDrop HTTP API — спецификация

_Актуально на: 2026-10-03. Для часов и Side Service: контракт `/v1` (сервер на Go). Прежний контракт: эталонная реализация `server/` (Node.js прототип)_

## Зачем этот документ

Контракт реализуют два сервера: **прототип на Node.js** (`server/`, без зависимостей; запускается только локально с ngrok-туннелем, на VPS не выкладывается) и **сервер на Go** (`backend/`), который его заменяет. Машиночитаемая версия контракта Go-сервера — `backend/api/openapi.yaml`. Тесты `server/test` проверяют только HTTP, поэтому прогоняются против обоих: так проверяется, что замена не меняет контракт. Различия, которые есть сегодня, отмечены ниже словами «только Go». Часы и Side Service (`PigeonDrop/`) знают только про этот HTTP-контракт — им всё равно, что за ним стоит.

**Этот документ — источник истины для контракта.** Любая реализация сервера должна воспроизводить именно то, что здесь описано; `server/server.js` и `server/accounts-store.js` — просто текущая реализация (референс), а не сам контракт. Если сервер начнёт вести себя иначе, чем описано ниже — часы/Side Service, скорее всего, сломаются без единой строчки изменений на их стороне, потому что они опираются именно на эти форматы и коды ответов.

**С 2026-10-03 часы и Side Service пользуются контрактом `/v1`** (раздел ниже): запись идёт с токеном устройства и принадлежит пользователю, а не лежит в общей куче. Прежние маршруты (`/messages`, `/accounts`, `/setup`, `/uploads`) нужны только Node-прототипу и его контрактным тестам; новые приложения на часах их не вызывают.

## Контракт часов и Side Service: `/v1` (только сервер на Go)

Подробнее и машиночитаемо — `backend/api/openapi.yaml`; устройство сервера — `backend/README.md`. Здесь то, на что опираются часы и Side Service.

**Ошибки** `/v1` — `{"ok": false, "error": "<английская фраза для журнала>", "code": "<машинный код>"}`; клиент ориентируется на `code`. Успешные ответы `/v1` не оборачиваются в `ok`, кроме загрузки записи (её ответ несёт `ok: true`, на него смотрит Side Service). Непредвиденная ошибка — `500 { ok:false, error:"internal error" }`.

### Привязка часов (RFC 8628)

Часы ничего не знают про пользователей. Чтобы стать «чьими-то», они проходят привязку; вызывает всё это Side Service по просьбе часов (`pairStart`, `pairPoll`).

1. **`POST /v1/device/code`** `{ "clientName": "Amazfit Balance" }` (имя необязательное, до 64 символов) → `200 { deviceCode, userCode, verificationUri, verificationUriComplete, expiresIn, interval }`. `deviceCode` — секрет часов (43 символа); `userCode` — короткий код вида `BCDF-GHJK`; `verificationUriComplete` — то, что часы показывают как QR-код (`<сервер>/pair?code=BCDF-GHJK`); `expiresIn` — секунд до конца привязки (600); `interval` — как часто опрашивать (5 с). Выдача кодов ограничена по адресу: `429 { code: "too_many_attempts" }` с `Retry-After`.
2. Человек открывает ссылку на телефоне, входит в аккаунт, сверяет код с экраном часов и подтверждает (`POST /v1/device/approve`, по cookie сессии; часы в этом не участвуют).
3. **`POST /v1/device/token`** `{ "deviceCode": "..." }`, опрос раз в `interval` секунд:
   - `200 { "status": "pending", "interval": 5 }` — пока не подтвердили;
   - `200 { "status": "approved", "deviceToken": "pdd_...", "deviceId": "..." }` — подтвердили; токен выдаётся **один раз**, повтор того же опроса — `400 invalid_device_code`;
   - `400 { code: "expired_token" }` — время вышло, `400 { code: "invalid_device_code" }` — код неизвестен или токен уже забрали: в обоих случаях привязку нужно начинать заново;
   - `429 { code: "too_many_attempts" }` — опрос чаще, чем раз в 3 секунды (не засчитывается) или слишком много неверных кодов: подождать `Retry-After`.

Часы хранят `deviceToken` у себя (`utils/device.js`); он дальше идёт с каждой загрузкой. В базе сервера лежит только его хеш.

### Загрузка записи

**`POST /v1/messages`**, заголовок `Authorization: Bearer <deviceToken>`, тело `{ "messageId": "<имя файла на часах>", "audio": "<base64 стандартного файла Ogg/Opus>" }`. Формат файла тот же, что описан для `/messages` ниже (упаковка на телефоне, `OggS`, 16 кГц, моно); формат Zepp сервер тоже принимает.

- **`200 { ok:true, id, messageId, bytesReceived, duplicate, receivedAt, storage, pruned }`** — запись сохранена за владельцем устройства. **Идемпотентно в пределах устройства по `messageId`:** повтор возвращает сохранённый результат (`duplicate: true`, `pruned: 0`) и ничего не сохраняет заново; у другого устройства может быть такой же `messageId`. Запись сохраняется, даже если из неё не получилось декодировать звук (на странице тогда нет проигрывателя, только «Скачать оригинал»).
  - **`storage`** — `{ state, usedBytes, limitBytes }`: насколько заполнено хранилище аккаунта (учитываются только файлы записей). `state`: `ok` (меньше 90%), `nearly_full` (от 90%), `full` (эта самая загрузка не поместилась и удалила старые записи). Часы показывают по нему предупреждение. Неизвестное значение `state` клиент игнорирует.
  - **`pruned`** — сколько самых старых записей аккаунта эта загрузка удалила, чтобы освободить место.
- **`401 { ok:false, code:"unauthorized" }`** — токена нет, он неизвестен или устройство отозвано. Side Service отвечает часам `{ unauthorized: true }`, часы забывают токен и просят привязаться заново.
- **`413 { ok:false, code:"payload_too_large" }`** — запись больше 512 КиБ (минута звука около 140 КиБ) или тело запроса больше допустимого для загрузки (около 770 КБ). Повтор не поможет. Side Service отвечает часам `{ fileError: true }`: часы пропускают эту запись и продолжают с остальными.
- **`429 { ok:false, code:"too_many_attempts" }`** с `Retry-After` — с этого устройства больше 60 загрузок в час (считается каждый запрос, повторы тоже). Side Service отвечает `{ rateLimited: true }`: часы останавливают отправку, оставляют записи в очереди и пробуют при следующем запуске, подключении или записи.
- `400 invalid_request` — тело не JSON, нет полей, `audio` не base64, `messageId` длиннее 255 символов или с управляющими символами.

**Хранилище аккаунта.** На аккаунт приходится 100 МиБ записей. Новая запись принимается всегда; если она не помещается, сервер удаляет самые старые записи аккаунта (по времени получения) ровно настолько, чтобы она поместилась, и сообщает об этом в `storage.state = "full"` и `pruned`. Удаляются и строки, и файлы. Сервер не может сам послать сообщение на часы, поэтому предупреждение приходит только в ответе на загрузку. Файл WAV для браузера на сервере не хранится: он делается из оригинала при воспроизведении, в лимит идёт только оригинал.

Просмотр, прослушивание и удаление записей человеком (`GET/DELETE /v1/messages`, `GET /v1/storage`, `/v1/devices`, страница `/pair`) часов не касаются.

## Прежний контракт (Node-прототип)

Всё ниже — контракт, который реализуют `server/` и Go-сервер без префикса `/v1`. Часы им больше не пользуются: описания «кто вызывает» (`registerAccount`, `sync`, `page/qrcode.js`, `WEB_APP_BASE_URL`) относятся к прежней версии приложения, этих файлов и запросов в нём больше нет.

## Соглашения

- Все ответы — `application/json`, единообразный конверт: `{"ok": true, ...}` при успехе, `{"ok": false, "error": "<строка>"}` при ошибке.
- Тела запросов — JSON (`Content-Type: application/json`), кроме `GET`-запросов.
- Ошибка парсинга JSON-тела → `400 { ok:false, error:"invalid JSON body" }`.
- Непредвиденная ошибка на сервере → `500 { ok:false, error:"internal error" }`.
- Неизвестный роут/метод → `404 { ok:false, error:"not found" }`.
- Авторизации нет вообще — `code` в `/accounts/*` не является секретом, это просто идентификатор (см. «Явно вне рамок» ниже).

## Эндпоинты

### `POST /messages` — загрузка записи

Вызывается из `PigeonDrop/app-side/uploads.js`, когда телефон получил от часов все части записи (часы шлют её по частям, см. `ARCHITECTURE.md` §4) и упаковал её в Ogg/Opus.

**Запрос**
```json
{ "fileName": "voice_1785056400000.opus", "audio": "<base64 файла Ogg/Opus>" }
```
- `fileName` — имя файла на часах. **Также ключ идемпотентности** (см. ниже) — не только для логирования.
- `audio` — base64-строка **стандартного файла Ogg/Opus** (см. «Формат `audio`» ниже). Прежний формат — сырые пакеты Zepp с их собственным заголовком (`ARCHITECTURE.md` §4) — сервер-прототип по-прежнему принимает и отличает по первым четырём байтам (`OggS`), но новые клиенты его не шлют.

**Формат `audio`.** Это обычный файл Ogg/Opus (RFC 3533, RFC 7845), его открывают `ffmpeg`, VLC и браузеры, а Telegram принимает как голосовое сообщение (приём в Telegram ещё проверяется):
- один логический поток, **моно**; страницы: `OpusHead`, `OpusTags` (производитель `pigeondrop`, без пользовательских тегов), затем звук по 50 пакетов на страницу; последняя страница помечена концом потока;
- `OpusHead`: версия 1, 1 канал, **pre-skip 0**, частота входа 16000 Гц, усиление 0, семейство каналов 0;
- пакеты — те же, что записали часы: SILK wideband, по 20 мс, **без перекодирования**; позиция гранулы считается как 960 отсчётов (20 мс при 48 кГц) на пакет;
- запись, оборвавшаяся посреди пакета, укорачивается до целых пакетов; запись без единого целого пакета не отправляется вообще.

Сервер обязан проверять входной файл как недоверенные данные: контрольные суммы страниц, границы, число каналов. Если файл не разобрать, он всё равно сохраняется, а `wavFile` равен `null`.

**Успех — `200`**
```json
{ "ok": true, "bytesReceived": 12345, "savedAs": "2026-08-01_14-05-42-123.opus", "wavFile": "2026-08-01_14-05-42-123.wav" }
```
- `savedAs` — имя, под которым сервер сохранил файл (по времени **получения сервером**, не записи на часах — так удобнее сортировать вручную).
- `wavFile` — имя сконвертированного `.wav`, или `null`, если конвертация не удалась (сама запись при этом всё равно сохраняется — конвертация не должна валить весь аплоад).
- `receivedAt` — время получения сервером (RFC 3339). Go-сервер отдаёт его всегда; Node-прототип — только при повторной отправке. Клиенты его не используют.

**Ошибки**
- `400 { ok:false, error:"expected { fileName, audio }" }` — отсутствует `fileName` или `audio`.
- `400 { ok:false, error:"invalid JSON body" }` — тело не JSON.
- `400` (только Go) — `fileName` длиннее 255 символов или с управляющими символами (PostgreSQL не умеет хранить NUL); `audio` не является корректным base64 или пусто после декодирования.
- `413 { ok:false, error:"request body too large" }` (только Go) — тело запроса больше 8 МиБ (запись на 60 секунд — около 180 КБ).

**Обязательное поведение, которое должно сохраниться:** запись должна быть надёжно сохранена независимо от того, успела ли конвертация в `.wav` — это два разных шанса на ошибку, второй не должен аннулировать первый.

**Идемпотентность по `fileName`:** часы держат персистентную очередь загрузки (`PigeonDrop/utils/uploadQueue.js`) и умеют повторно отправлять запись, если не получили подтверждение об успехе — в том числе в случае, когда сервер на самом деле её принял, но подтверждение потерялось на обратном пути по BLE. Поэтому повторный `POST /messages` с уже виденным `fileName` **не должен** сохранять второй файл и повторно конвертировать — сервер обязан вернуть тот же ответ (`savedAs`/`wavFile`/`bytesReceived`), что и в первый раз (см. `server/uploads-store.js` — референсная реализация хранит map `fileName -> результат`).

### `POST /accounts` — создать (или получить существующий) аккаунт

Вызывается из двух мест:
- `PigeonDrop/app-side/index.js` (`type: 'registerAccount'`) — сразу после того как часы сгенерировали код (`page/qrcode.js`).
- `server/public/setup.html` — защитный upsert при загрузке страницы (на случай, если запрос с часов не дошёл из-за отсутствия BLE-соединения в нужный момент).

**Запрос**
```json
{ "code": "m0x1y2z-ab12cd" }
```

**Успех — `200`** (идемпотентно: если аккаунт с этим `code` уже есть — возвращается как есть, новый не создаётся, поля не перезаписываются)
```json
{
  "ok": true,
  "code": "m0x1y2z-ab12cd",
  "customServerUrl": null,
  "serverUrl": "https://pigeondrop.example.com",
  "createdAt": "2026-08-01T12:44:26.946Z",
  "updatedAt": "2026-08-01T12:44:26.946Z"
}
```

**Ошибки**
- `400 { ok:false, error:"expected { code }" }` — отсутствует `code`.
- `400 { ok:false, error:"code is too long" }` (только Go) — `code` длиннее 128 символов.

### `GET /accounts/:code` — прочитать аккаунт

Вызывается из `app-side/index.js` (`type: 'sync'`, при нажатии «Синхронизация» на часах) и из `setup.html` косвенно (через `POST /accounts`, который тоже читает существующую запись).

**Успех — `200`** — та же форма, что у `POST /accounts`.

**Ошибки**
- `404 { ok:false, error:"account not found" }`.

---

### `PUT /accounts/:code` — задать `customServerUrl`

Вызывается только из `server/public/setup.html` (веб-страница настройки, открытая по QR с часов). Часы и Side Service этот эндпоинт не вызывают напрямую.

**Запрос**
```json
{ "customServerUrl": "https://my-own-server.example.com" }
```
`customServerUrl: null` — явный сброс на сервер по умолчанию.

**Успех — `200`** — та же форма, что у `POST /accounts`, с обновлённым `customServerUrl`/`serverUrl`/`updatedAt`.

**Ошибки**
- `404 { ok:false, error:"account not found" }` — этот эндпоинт **не создаёт** аккаунт, только обновляет существующий.
- `400 { ok:false, error:"customServerUrl must be null or an http(s) URL" }` — значение не `null` и не начинается с `http://`/`https://`. Это **лёгкая** проверка, не полноценная валидация URL — сознательно (см. «Явно вне рамок»).

---

### `GET /setup` — веб-страница настройки

Открывается из QR-кода на часах (`WEB_APP_BASE_URL + '/setup?code=' + code`, см. `PigeonDrop/page/qrcode.js`). Отдаёт статический HTML (`server/public/setup.html`), query-параметр `code` сервером не читается — страница сама разбирает `location.search` в браузере.

**Успех — `200`**, `Content-Type: text/html`.

---

### `GET /uploads` — список сохранённых записей

**Только для ручного доступа человеком** — часы и Side Service этот эндпоинт никогда не вызывают. Существует, чтобы можно было прослушать записи из браузера, не заходя в папку `uploads/` на диске.

**Успех — `200`**, `Content-Type: text/html` — простой список ссылок на файлы, новые сверху.

### `GET /uploads/:name` — скачать/прослушать конкретный файл

Тоже только для ручного доступа. `name` — точное имя файла из `uploads/` (то, что было в `savedAs`/`wavFile` ответа `/messages`, не исходный `fileName` с часов).

**Успех — `200`** — содержимое файла. `Content-Type`: `audio/wav` для `.wav`; `audio/ogg` для `.opus` в формате Ogg/Opus (его воспроизводит браузер); иначе `application/octet-stream` (так отдаётся `.opus` в старом формате Zepp). Go-сервер поддерживает запросы `Range`, поэтому в браузере работает перемотка.

**Ошибки**
- `400 { ok:false, error:"invalid filename" }` — `name` содержит `/` или `..` (защита от path traversal).
- `404 { ok:false, error:"file not found" }`.

> **⚠ Без авторизации.** Как и всё остальное в этом прототипе — кто угодно, кто знает адрес сервера, может открыть `GET /uploads`, увидеть список **всех** записей и скачать любую из них; знать имя файла для этого не нужно. Приемлемо для личного прототипа, неприемлемо при реальной многопользовательской системе — понадобится авторизация до того, как эти эндпоинты станут частью публичного продукта.

## Модель данных аккаунта

```
{
  code: string           // идентификатор, генерируется часами (не сервером!)
  customServerUrl: string | null   // null = использовать сервер по умолчанию
  createdAt: string      // ISO 8601
  updatedAt: string      // ISO 8601
}
```

`serverUrl` в ответах API — вычисляемое поле, не хранится: `customServerUrl || DEFAULT_SERVER_URL`. Часы никогда не должны сами решать, что значит «по умолчанию» — сервер всегда отдаёт уже готовое резолвленное значение.

`DEFAULT_SERVER_URL` — конфигурация самого сервера (в Node-прототипе — переменная окружения, дефолт `http://localhost:<PORT>`; при работе через ngrok-туннель или за любым другим публичным адресом должно указывать на этот адрес, иначе выданный клиентам `serverUrl` будет нерабочим `localhost`).

## Инварианты, которые нужно сохранить при любых изменениях реализации

1. **`POST /accounts` идемпотентен** — двойной вызов с одним и тем же `code` не создаёт дублей и не сбрасывает уже установленный `customServerUrl`.
2. **`POST /messages` идемпотентен по `fileName`** — повторный запрос с уже виденным `fileName` не создаёт второй файл, возвращает исходный результат. Часы полагаются на это при ретрае из персистентной очереди (`utils/uploadQueue.js`) — без этого повторные отправки после потерянного ack накапливали бы дубликаты на сервере.
3. **`code` генерируется часами, не сервером.** Сервер только принимает и хранит его — если сервер сам начнёт генерировать код, вся логика QR (часы уже показывают QR с кодом до похода на сервер) сломается.
4. **Формат конверта ответа не меняется** (`ok` + либо данные, либо `error`) — Side Service (`app-side/index.js`) проверяет `data.ok` перед тем как использовать остальные поля.
5. **Коды ответов именно такие, как описаны** (400/404/500) — `page/settings.js`/`page/qrcode.js` не парсят тело ошибки глубоко, но полагаются на факт успеха/неуспеха запроса.

## Явно вне рамок (сознательно не реализовано, не нужно добавлять без отдельного запроса)

- Аутентификация/авторизация — `code` не секрет, это просто идентификатор.
- Полная валидация `customServerUrl` (только проверка `http(s)://`-префикса).
- Rate limiting, ротация/expiry кода.
- Настоящий multi-tenant хостинг, речь → текст, интеграции (Telegram/WhatsApp и т.п.) — будущее развитие `DEFAULT_SERVER_URL`, не текущий контракт.

## Кто и зачем вызывает каждый эндпоинт (сводка)

| Эндпоинт | Кто вызывает | Файл |
|---|---|---|
| `POST /v1/device/code`, `POST /v1/device/token` | Side Service по просьбе часов (`pairStart`, `pairPoll`) | `PigeonDrop/app-side/pairing.js` |
| `POST /v1/messages` | Side Service, после получения всех частей записи от часов, с токеном устройства | `PigeonDrop/app-side/uploads.js` |
| `POST /v1/device/approve`, `GET /v1/device/pairing/:code`, `GET/DELETE /v1/devices`, `GET/DELETE /v1/messages` (`DELETE` без id удаляет все записи), `GET /v1/storage`, `GET /v1/messages/:id/audio`, `/v1/auth/*`, `/v1/me` | Человек, на странице `/pair` (не часы и не Side Service) | `backend/internal/httpapi/pair.js` |
| `POST /messages` (прежний) | Side Service, после получения всех частей записи от часов | `PigeonDrop/app-side/uploads.js` |
| `POST /accounts` | Side Service (`registerAccount`) и `setup.html` (защитный upsert) | `PigeonDrop/app-side/index.js`, `server/public/setup.html` |
| `GET /accounts/:code` | Side Service (`sync`) | `PigeonDrop/app-side/index.js` |
| `PUT /accounts/:code` | Веб-страница настройки | `server/public/setup.html` |
| `GET /setup` | Браузер телефона (переход по QR) | — |
| `GET /uploads` | Человек, вручную в браузере (часы и Side Service не вызывают) | — |
| `GET /uploads/:name` | Человек, вручную в браузере — по ссылке из списка `/uploads` | — |
