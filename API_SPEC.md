# PigeonDrop HTTP API — спецификация

_Актуально на: 2026-08-03, эталонная реализация: `server/` (Node.js прототип)_

## Зачем этот документ

`server/` — временный прототип на Node.js без зависимостей (см. `CLAUDE.md`: "не production-инфраструктура"). Планируется полностью переписать бэкенд на Go. Часы и Side Service (`PigeonDrop/`) знают только про этот HTTP-контракт — им всё равно, что за ним стоит.

**Этот документ — источник истины для контракта.** Реализация на Go должна воспроизводить именно то, что здесь описано; `server/server.js` и `server/accounts-store.js` — просто одна из реализаций (референс), а не сам контракт. Если новая реализация будет вести себя иначе, чем описано ниже — часы/Side Service, скорее всего, сломаются без единой строчки изменений на их стороне, потому что они опираются именно на эти форматы и коды ответов.

## Соглашения

- Все ответы — `application/json`, единообразный конверт: `{"ok": true, ...}` при успехе, `{"ok": false, "error": "<строка>"}` при ошибке.
- Тела запросов — JSON (`Content-Type: application/json`), кроме `GET`-запросов.
- Ошибка парсинга JSON-тела → `400 { ok:false, error:"invalid JSON body" }`.
- Непредвиденная ошибка на сервере → `500 { ok:false, error:"internal error" }`.
- Неизвестный роут/метод → `404 { ok:false, error:"not found" }`.
- Авторизации нет вообще — `code` в `/accounts/*` не является секретом, это просто идентификатор (см. «Явно вне рамок» ниже).

## Эндпоинты

### `POST /messages` — загрузка записи

Вызывается из `PigeonDrop/app-side/index.js` при получении записи от часов через `MessageBuilder` (`on('call', ...)`).

**Запрос**
```json
{ "fileName": "voice_1785056400000.opus", "audio": "<base64 opus-байты>" }
```
- `fileName` — имя файла на часах. **Также ключ идемпотентности** (см. ниже) — не только для логирования.
- `audio` — base64-строка сырых байт `.opus`-файла в проприетарном формате Zepp (см. `ARCHITECTURE.md` §4 про формат пакетов).

**Успех — `200`**
```json
{ "ok": true, "bytesReceived": 12345, "savedAs": "2026-08-01_14-05-42-123.opus", "wavFile": "2026-08-01_14-05-42-123.wav" }
```
- `savedAs` — имя, под которым сервер сохранил файл (по времени **получения сервером**, не записи на часах — так удобнее сортировать вручную).
- `wavFile` — имя сконвертированного `.wav`, или `null`, если конвертация не удалась (сама запись при этом всё равно сохраняется — конвертация не должна валить весь аплоад).

**Ошибки**
- `400 { ok:false, error:"expected { fileName, audio }" }` — отсутствует `fileName` или `audio`.

**Обязательное поведение, которое должно сохраниться:** запись должна быть надёжно сохранена независимо от того, успела ли конвертация в `.wav` — это два разных шанса на ошибку, второй не должен аннулировать первый.

**Идемпотентность по `fileName`:** часы держат персистентную очередь загрузки (`PigeonDrop/utils/uploadQueue.js`) и умеют повторно отправлять запись, если не получили подтверждение об успехе — в том числе в случае, когда сервер на самом деле её принял, но подтверждение потерялось на обратном пути по BLE. Поэтому повторный `POST /messages` с уже виденным `fileName` **не должен** сохранять второй файл и повторно конвертировать — сервер обязан вернуть тот же ответ (`savedAs`/`wavFile`/`bytesReceived`), что и в первый раз (см. `server/uploads-store.js` — референсная реализация хранит map `fileName -> результат`).

---

### `POST /accounts` — создать (или получить существующий) аккаунт

Вызывается из двух мест:
- `PigeonDrop/app-side/index.js` (`type: 'registerAccount'`) — сразу после того как часы сгенерировали код (`page/qrcode.js`).
- `server/public/setup.html` — защитный upsert при загрузке страницы (на случай, если запрос с часов не дошёл из-за отсутствия BLE-соединения в нужный момент).

**Запрос**
```json
{ "code": "m0x1y2z-ab12cd" }
```

**Успех — `200`** (идемпотентно: если аккаунт с этим `code` уже есть — возвращается как есть, новый не создаётся, поля не перезаписываются)
```json
{
  "ok": true,
  "code": "m0x1y2z-ab12cd",
  "customServerUrl": null,
  "serverUrl": "https://pigeondrop.example.com",
  "createdAt": "2026-08-01T12:44:26.946Z",
  "updatedAt": "2026-08-01T12:44:26.946Z"
}
```

**Ошибки**
- `400 { ok:false, error:"expected { code }" }` — отсутствует `code`.

---

### `GET /accounts/:code` — прочитать аккаунт

Вызывается из `app-side/index.js` (`type: 'sync'`, при нажатии «Синхронизация» на часах) и из `setup.html` косвенно (через `POST /accounts`, который тоже читает существующую запись).

**Успех — `200`** — та же форма, что у `POST /accounts`.

**Ошибки**
- `404 { ok:false, error:"account not found" }`.

---

### `PUT /accounts/:code` — задать `customServerUrl`

Вызывается только из `server/public/setup.html` (веб-страница настройки, открытая по QR с часов). Часы и Side Service этот эндпоинт не вызывают напрямую.

**Запрос**
```json
{ "customServerUrl": "https://my-own-server.example.com" }
```
`customServerUrl: null` — явный сброс на сервер по умолчанию.

**Успех — `200`** — та же форма, что у `POST /accounts`, с обновлённым `customServerUrl`/`serverUrl`/`updatedAt`.

**Ошибки**
- `404 { ok:false, error:"account not found" }` — этот эндпоинт **не создаёт** аккаунт, только обновляет существующий.
- `400 { ok:false, error:"customServerUrl must be null or an http(s) URL" }` — значение не `null` и не начинается с `http://`/`https://`. Это **лёгкая** проверка, не полноценная валидация URL — сознательно (см. «Явно вне рамок»).

---

### `GET /setup` — веб-страница настройки

Открывается из QR-кода на часах (`WEB_APP_BASE_URL + '/setup?code=' + code`, см. `PigeonDrop/page/qrcode.js`). Отдаёт статический HTML (`server/public/setup.html`), query-параметр `code` сервером не читается — страница сама разбирает `location.search` в браузере.

**Успех — `200`**, `Content-Type: text/html`.

---

### `GET /uploads` — список сохранённых записей

**Только для ручного доступа человеком** — часы и Side Service этот эндпоинт никогда не вызывают. Существует, чтобы можно было прослушать записи на задеплоенном сервере (например, Railway) без захода по SSH/CLI.

**Успех — `200`**, `Content-Type: text/html` — простой список ссылок на файлы, новые сверху.

### `GET /uploads/:name` — скачать/прослушать конкретный файл

Тоже только для ручного доступа. `name` — точное имя файла из `uploads/` (то, что было в `savedAs`/`wavFile` ответа `/messages`, не исходный `fileName` с часов).

**Успех — `200`** — содержимое файла, `Content-Type: audio/wav` для `.wav`, иначе `application/octet-stream`.

**Ошибки**
- `400 { ok:false, error:"invalid filename" }` — `name` содержит `/` или `..` (защита от path traversal).
- `404 { ok:false, error:"file not found" }`.

> **⚠ Без авторизации.** Как и всё остальное в этом прототипе — кто угодно, кто знает адрес сервера и имя файла, может скачать запись. Имена файлов основаны на времени получения и частично предсказуемы. Приемлемо для личного прототипа, неприемлемо при реальной многопользовательской системе — понадобится авторизация до того, как эти эндпоинты станут частью публичного продукта.

## Модель данных аккаунта

```
{
  code: string           // идентификатор, генерируется часами (не сервером!)
  customServerUrl: string | null   // null = использовать сервер по умолчанию
  createdAt: string      // ISO 8601
  updatedAt: string      // ISO 8601
}
```

`serverUrl` в ответах API — вычисляемое поле, не хранится: `customServerUrl || DEFAULT_SERVER_URL`. Часы никогда не должны сами решать, что значит «по умолчанию» — сервер всегда отдаёт уже готовое резолвленное значение.

`DEFAULT_SERVER_URL` — конфигурация самого сервера (в Node-прототипе — переменная окружения, дефолт `http://localhost:<PORT>`; при работе через ngrok должно указывать на публичный адрес, иначе выданный клиентам `serverUrl` будет нерабочим `localhost`).

## Инварианты, которые нужно сохранить при переписывании

1. **`POST /accounts` идемпотентен** — двойной вызов с одним и тем же `code` не создаёт дублей и не сбрасывает уже установленный `customServerUrl`.
2. **`POST /messages` идемпотентен по `fileName`** — повторный запрос с уже виденным `fileName` не создаёт второй файл, возвращает исходный результат. Часы полагаются на это при ретрае из персистентной очереди (`utils/uploadQueue.js`) — без этого повторные отправки после потерянного ack накапливали бы дубликаты на сервере.
3. **`code` генерируется часами, не сервером.** Сервер только принимает и хранит его — если сервер сам начнёт генерировать код, вся логика QR (часы уже показывают QR с кодом до похода на сервер) сломается.
4. **Формат конверта ответа не меняется** (`ok` + либо данные, либо `error`) — Side Service (`app-side/index.js`) проверяет `data.ok` перед тем как использовать остальные поля.
5. **Коды ответов именно такие, как описаны** (400/404/500) — `page/settings.js`/`page/qrcode.js` не парсят тело ошибки глубоко, но полагаются на факт успеха/неуспеха запроса.

## Явно вне рамок (сознательно не реализовано, не нужно добавлять при переписывании без отдельного запроса)

- Аутентификация/авторизация — `code` не секрет, это просто идентификатор.
- Полная валидация `customServerUrl` (только проверка `http(s)://`-префикса).
- Rate limiting, ротация/expiry кода.
- Настоящий multi-tenant хостинг, речь → текст, интеграции (Telegram/WhatsApp и т.п.) — будущее развитие `DEFAULT_SERVER_URL`, не текущий контракт.

## Кто и зачем вызывает каждый эндпоинт (сводка)

| Эндпоинт | Кто вызывает | Файл |
|---|---|---|
| `POST /messages` | Side Service, после получения записи от часов | `PigeonDrop/app-side/index.js` |
| `POST /accounts` | Side Service (`registerAccount`) и `setup.html` (защитный upsert) | `PigeonDrop/app-side/index.js`, `server/public/setup.html` |
| `GET /accounts/:code` | Side Service (`sync`) | `PigeonDrop/app-side/index.js` |
| `PUT /accounts/:code` | Веб-страница настройки | `server/public/setup.html` |
| `GET /setup` | Браузер телефона (переход по QR) | — |
