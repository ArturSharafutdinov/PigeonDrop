# PigeonDrop HTTP API — спецификация

_Актуально на: 2026-10-04. Контракт `/v1`, которым пользуются часы, Side Service и страница `/pair`. Маршруты без `/v1` (`/messages`, `/accounts`, `/setup`, `/uploads`) удалены вместе с Node-прототипом: они есть только в истории git._

## Зачем этот документ

Контракт реализует сервер на Go (`backend/`). Машиночитаемая версия — `backend/api/openapi.yaml`. Часы и Side Service (`PigeonDrop/`) знают только про этот HTTP-контракт — им всё равно, что за ним стоит.

**Этот документ — источник истины для контракта.** Любая реализация сервера должна воспроизводить именно то, что здесь описано; код — это реализация, а не сам контракт. Если сервер начнёт вести себя иначе, чем описано ниже — часы/Side Service, скорее всего, сломаются без единой строчки изменений на их стороне, потому что они опираются именно на эти форматы и коды ответов.

## Контракт часов и Side Service: `/v1`

Подробнее и машиночитаемо — `backend/api/openapi.yaml`; устройство сервера — `backend/README.md`. Здесь то, на что опираются часы и Side Service.

**Ошибки** `/v1` — `{"ok": false, "error": "<английская фраза для журнала>", "code": "<машинный код>"}`; клиент ориентируется на `code`. Успешные ответы `/v1` не оборачиваются в `ok`, кроме загрузки записи (её ответ несёт `ok: true`, на него смотрит Side Service). Непредвиденная ошибка — `500 { ok:false, error:"internal error" }`.

### Привязка часов (RFC 8628)

Часы ничего не знают про пользователей. Чтобы стать «чьими-то», они проходят привязку; вызывает всё это Side Service по просьбе часов (`pairStart`, `pairPoll`).

1. **`POST /v1/device/code`** `{ "clientName": "Amazfit Balance" }` (имя необязательное, до 64 символов) → `200 { deviceCode, userCode, verificationUri, verificationUriComplete, expiresIn, interval }`. `deviceCode` — секрет часов (43 символа); `userCode` — короткий код вида `BCDF-GHJK`; `verificationUriComplete` — то, что часы показывают как QR-код (`<сервер>/pair?code=BCDF-GHJK`); `expiresIn` — секунд до конца привязки (600); `interval` — как часто опрашивать (5 с). Выдача кодов ограничена по адресу: `429 { code: "too_many_attempts" }` с `Retry-After`.
2. Человек открывает ссылку на телефоне, входит в аккаунт, сверяет код с экраном часов и подтверждает (`POST /v1/device/approve`, по cookie сессии; часы в этом не участвуют).
3. **`POST /v1/device/token`** `{ "deviceCode": "..." }`, опрос раз в `interval` секунд:
   - `200 { "status": "pending", "interval": 5 }` — пока не подтвердили;
   - `200 { "status": "approved", "deviceToken": "pdd_...", "deviceId": "..." }` — подтвердили; токен выдаётся **один раз**, повтор того же опроса — `400 invalid_device_code`;
   - `400 { code: "expired_token" }` — время вышло, `400 { code: "invalid_device_code" }` — код неизвестен или токен уже забрали: в обоих случаях привязку нужно начинать заново;
   - `429 { code: "too_many_attempts" }` — опрос чаще, чем раз в 3 секунды (не засчитывается) или слишком много неверных кодов: подождать `Retry-After`.

Часы хранят `deviceToken` у себя (`utils/device.js`); он дальше идёт с каждой загрузкой. В базе сервера лежит только его хеш.

### Загрузка записи

**`POST /v1/messages`**, заголовок `Authorization: Bearer <deviceToken>`, тело `{ "messageId": "<имя файла на часах>", "audio": "<base64 стандартного файла Ogg/Opus>" }`. Формат файла описан ниже; прежний формат Zepp (сырые пакеты с собственным заголовком, `ARCHITECTURE.md` §4) сервер тоже принимает и отличает по первым четырём байтам (`OggS`), но приложение его не шлёт.

**Формат `audio`.** Это обычный файл Ogg/Opus (RFC 3533, RFC 7845), его открывают `ffmpeg`, VLC и браузеры, а Telegram принимает как голосовое сообщение (приём в Telegram ещё проверяется):
- один логический поток, **моно**; страницы: `OpusHead`, `OpusTags` (производитель `pigeondrop`, без пользовательских тегов), затем звук по 50 пакетов на страницу; последняя страница помечена концом потока;
- `OpusHead`: версия 1, 1 канал, **pre-skip 0**, частота входа 16000 Гц, усиление 0, семейство каналов 0;
- пакеты — те же, что записали часы: SILK wideband, по 20 мс, **без перекодирования**; позиция гранулы считается как 960 отсчётов (20 мс при 48 кГц) на пакет;
- запись, оборвавшаяся посреди пакета, укорачивается до целых пакетов; запись без единого целого пакета не отправляется вообще.

Сервер проверяет входной файл как недоверенные данные: контрольные суммы страниц, границы, число каналов. Если файл не разобрать, он всё равно сохраняется (`hasWav: false`).

- **`200 { ok:true, id, messageId, bytesReceived, duplicate, receivedAt, storage, pruned }`** — запись сохранена за владельцем устройства. **Идемпотентно в пределах устройства по `messageId`:** повтор возвращает сохранённый результат (`duplicate: true`, `pruned: 0`) и ничего не сохраняет заново; у другого устройства может быть такой же `messageId`. Запись сохраняется, даже если из неё не получилось декодировать звук (на странице тогда нет проигрывателя, только «Скачать оригинал»).
  - **`storage`** — `{ state, usedBytes, limitBytes }`: насколько заполнено хранилище аккаунта (учитываются только файлы записей). `state`: `ok` (меньше 90%), `nearly_full` (от 90%), `full` (эта самая загрузка не поместилась и удалила старые записи). Часы показывают по нему предупреждение. Неизвестное значение `state` клиент игнорирует.
  - **`pruned`** — сколько самых старых записей аккаунта эта загрузка удалила, чтобы освободить место.
- **`401 { ok:false, code:"unauthorized" }`** — токена нет, он неизвестен или устройство отозвано. Side Service отвечает часам `{ unauthorized: true }`, часы забывают токен и просят привязаться заново.
- **`413 { ok:false, code:"payload_too_large" }`** — запись больше 512 КиБ (минута звука около 140 КиБ) или тело запроса больше допустимого для загрузки (около 770 КБ). Повтор не поможет. Side Service отвечает часам `{ fileError: true }`: часы пропускают эту запись и продолжают с остальными.
- **`429 { ok:false, code:"too_many_attempts" }`** с `Retry-After` — с этого устройства больше 60 загрузок в час (считается каждый запрос, повторы тоже). Side Service отвечает `{ rateLimited: true }`: часы останавливают отправку, оставляют записи в очереди и пробуют при следующем запуске, подключении или записи.
- `400 invalid_request` — тело не JSON, нет полей, `audio` не base64, `messageId` длиннее 255 символов или с управляющими символами.

**Хранилище аккаунта.** На аккаунт приходится 100 МиБ записей. Новая запись принимается всегда; если она не помещается, сервер удаляет самые старые записи аккаунта (по времени получения) ровно настолько, чтобы она поместилась, и сообщает об этом в `storage.state = "full"` и `pruned`. Удаляются и строки, и файлы. Сервер не может сам послать сообщение на часы, поэтому предупреждение приходит только в ответе на загрузку. Файл WAV для браузера на сервере не хранится: он делается из оригинала при воспроизведении, в лимит идёт только оригинал.

Просмотр, прослушивание и удаление записей человеком (`GET/DELETE /v1/messages`, `GET /v1/storage`, `/v1/devices`, страница `/pair`) часов не касаются.

## Соглашения

- Ответы — `application/json` (кроме звука и страницы `/pair`); тела запросов — JSON.
- Ошибки: `{"ok": false, "error": "<фраза>", "code": "<машинный код>"}` (подробнее в начале раздела `/v1`).
- Неизвестный маршрут или метод — `404 { ok:false, error:"not found" }`; непредвиденная ошибка — `500 { ok:false, error:"internal error" }`.
- Проверка работоспособности: `GET /healthz` → `200 { ok:true }` или `503`, если база недоступна.

## Инварианты, которые нужно сохранить при любых изменениях реализации

1. **`POST /v1/messages` идемпотентен по `messageId` в пределах устройства.** Повтор не создаёт вторую запись, возвращает сохранённый результат. Часы полагаются на это при повторной отправке из персистентной очереди (`utils/uploadQueue.js`): подтверждение может потеряться на обратном пути по BLE, и без идемпотентности каждая потеря оставляла бы дубликат.
2. **Запись сохраняется независимо от того, удалось ли её декодировать.** Это два разных шанса на ошибку, второй не должен аннулировать первый.
3. **Коды `401`, `413` и `429` у загрузки именно такие, как описаны.** По ним Side Service решает, что сказать часам (`unauthorized`, `fileError`, `rateLimited`), а часы — забыть токен, пропустить запись или остановить отправку.
4. **Токен устройства показывается один раз** (при привязке), на сервере хранится только его хеш.

## Явно вне рамок (не реализовано, не добавлять без отдельного запроса)

- Цепочки (очередь, Telegram, прочие узлы), режим «свой сервер», речь → текст: это дальнейшая работа, не текущий контракт.

## Кто и зачем вызывает каждый эндпоинт (сводка)

| Эндпоинт | Кто вызывает | Файл |
|---|---|---|
| `POST /v1/device/code`, `POST /v1/device/token` | Side Service по просьбе часов (`pairStart`, `pairPoll`) | `PigeonDrop/app-side/pairing.js` |
| `POST /v1/messages` | Side Service, после получения всех частей записи от часов, с токеном устройства | `PigeonDrop/app-side/uploads.js` |
| `POST /v1/device/approve`, `GET /v1/device/pairing/:code`, `GET/DELETE /v1/devices`, `GET/DELETE /v1/messages` (`DELETE` без id удаляет все записи), `GET /v1/storage`, `GET /v1/messages/:id/audio`, `GET /v1/messages/archive` (zip со всеми записями, без сжатия, оригиналы `.opus`), `/v1/auth/*`, `/v1/me` | Человек, на странице `/pair` (не часы и не Side Service) | `backend/internal/httpapi/pair.js` |
