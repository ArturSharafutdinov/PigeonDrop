# CLAUDE.md

Guidance for Claude Code (claude.ai/code) and other coding agents working in this repository. Humans: start with [`README.md`](README.md) and [`CONTRIBUTING.md`](CONTRIBUTING.md).

## Repo layout

Independent projects side by side, connected only by the runtime data flow described below (no shared `package.json`, no monorepo tooling):

- **`PigeonDrop/`**: the Zepp OS 4.0 Mini Program (device app + Side Service). The core deliverable.
- **`backend/`**: the Go server. Go 1.26, `net/http`, PostgreSQL via `pgx`, goose migrations, `sqlc` queries, OpenAPI-first with `oapi-codegen` (`backend/api/openapi.yaml` is the source of truth for the contract; run `make generate` after editing it or the SQL in `internal/db/queries`). It has people: registration by invitation code, email + password sign-in with cookie sessions, password change (`/v1/auth/*`, `/v1/me`; operator commands `pigeondrop invite|user`). Watches are paired with an account (RFC 8628 device flow, `/v1/device/*`), authenticate with a revocable device token and upload to `/v1/messages`, where every recording has an owner; a small page at `/pair` is the UI for sign-in, pairing, devices and playback. With `STT_URL` set, every new recording also joins a speech recognition queue in PostgreSQL (`transcriptions`, in the same transaction as the message) and a worker inside `serve` turns the recordings into text one at a time through the service in `stt/`; the text is in `GET /v1/messages` and on `/pair`. With `TELEGRAM_BOT_TOKEN` set, a bot (`internal/telegram`, long polling, no public address) links a person's Telegram chat to their account and every new recording of a linked account is sent to the chat as a voice message with its transcript under it, through a second queue in PostgreSQL (`telegram_deliveries`, filled in the transaction that stores the recording); every message carries a *Seen* button that deletes the recording's messages from the chat (only there, not on the server). Operator commands: `pigeondrop stt status|enqueue|retry|check`, `pigeondrop telegram check|status`. **The watch app speaks only this API.** Read [`backend/README.md`](backend/README.md) before working on it.
- **`stt/`**: the speech recognition service, a small Python HTTP service that turns a WAV into text with Parakeet TDT v3 (one recording at a time, token-protected, in its own container with 3 GB). The Go server feeds it through the PostgreSQL queue (`backend/internal/transcribe`). Tests (`cd stt && python3 -m unittest discover -s tests -t .`) use a fake model and need nothing installed; `stt/smoke.sh` (real recordings) and `stt/smoke-synthetic.sh` (made-up ones, used by CI) try the real image. The model's author must stay credited (CC BY 4.0, see `THIRD_PARTY_NOTICES.md`). See [`stt/README.md`](stt/README.md).
- **`tools/backup/`**: backup scripts for a deployment: a systemd-timer dump of the database, a restore check that loads a restored snapshot into a scratch database and verifies every recording's file, and instructions for a Backrest plan. Outside `backend/` on purpose, so that changing it does not trigger a deploy of the server. See [`tools/backup/README.md`](tools/backup/README.md).
- **`docs/`**: [`architecture.md`](docs/architecture.md) (the narrative overview: data flow, per-file responsibilities, the reasoning behind non-obvious decisions; **read it first** before non-trivial changes), [`api.md`](docs/api.md) (the HTTP contract the watch and the Side Service depend on; any server change must keep it intact), [`deployment.md`](docs/deployment.md), [`ci-cd.md`](docs/ci-cd.md), [`troubleshooting.md`](docs/troubleshooting.md) (problems met on real devices and servers, with what fixed them; add new ones there), [`adr/`](docs/adr/) (decision records) and [`research/`](docs/research/) (the speech recognition comparison and its benchmark harness).
- **`.claude/`**: project settings for Claude Code: a hook that blocks edits to protected files and the `zeppos` skill (general Zepp OS knowledge and the differences between its documentation and real devices). See [`.claude/README.md`](.claude/README.md).

## Language

Everything in the repository is in **English**: code, comments, documentation, test names, commit messages and pull requests. Russian exists only as a second UI language (the watch app, the `/pair` page, the Telegram bot) and as test data. `scripts/check-language.py` enforces this in CI: Cyrillic and CJK letters are allowed only in the files listed in it (the Russian text tables, test fixtures, the benchmark's phrases). The user-facing language of a conversation follows the user; files stay English.

## Git

Work goes through branches and pull requests, not straight to `main`. Commit your own work after finishing a task or a meaningful part of one. Messages are in English, short (an imperative subject line, optionally one line of detail) and say what was done. Stage only the files that belong to the change: the index may hold unrelated entries, so prefer explicit pathspecs. Pull requests have an English title and body (what was done, what to look at first, how it was verified, what is not verified). Use `gh pr create`; never read a token out of the keyring. Base a new branch on `main` once its parent PR is merged, and check `git log origin/main..<branch>` after any merge before assuming `main` has the work.

## Commands

### PigeonDrop (watch app)

Run from `PigeonDrop/`. Uses the Zepp OS `zeus` CLI (`npm install -g @zeppos/zeus-cli`).

**First-time setup**: `PigeonDrop/config.js` is gitignored; it holds the server URL, which does not belong in the repository. Copy `config.example.js` to `config.js` and fill in your own `SERVER_URL` before building. It is a plain JS module read at build time by Rollup, not a `.env` file; the watch has no runtime `process.env`.

```bash
zeus dev          # run in the Zepp OS simulator
zeus preview      # QR code to side-load onto a real watch via the Zepp app
zeus build        # a .zab package under PigeonDrop/dist/
zeus cache clean  # when UI or icon changes do not seem to take effect
npm test          # watch-app tests
```

**Do not run `zeus preview` unless asked**: the person scans the QR code themselves; just tell them when it is needed.

`npm test` runs `test/*.test.mjs` (plain `node:test`, no install needed). The tests load the app's real source files with the `@zos/*` modules stubbed (`test/helpers/load.mjs` rewrites each import; an unmapped import fails the test on purpose). They cover the chunked upload protocol and its failure modes, the shared player and queue state, the main page's screen hold, the settings, pairing and storage pages, the English and Russian texts, and that `config.example.js` has every constant the code imports. They run on stubs, so they do not replace checking screen, Bluetooth and memory behaviour on the watch. The tests run the screens in English; `test/i18n.test.mjs` also checks Russian.

### backend (Go server)

Run from `backend/`. Needs Go 1.26+ and the PostgreSQL server binaries (the dev database is a throwaway cluster that never touches other databases).

```bash
scripts/dev-db.sh up     # PostgreSQL on 127.0.0.1:55432, data in backend/.dev
make test                # go test -race ./...; tests create and drop their own databases (REQUIRE_DB=1 makes a missing database fail instead of skip)
make check               # gofmt + vet + tests + generated-code check, what CI runs
make lint                # golangci-lint, the version CI runs
make vuln                # govulncheck
make generate            # after editing api/openapi.yaml or internal/db/queries; CI fails if generated code is stale
make run                 # server on :3000 against the dev database
```

To reach a local server from a real watch and phone, expose it with any HTTPS tunnel; put the resulting URL in **both** `PigeonDrop/config.js`'s `SERVER_URL` and the server's `DEFAULT_SERVER_URL` environment variable (the server builds the pairing QR address from its own public address). Never ask for or enter a tunnel's auth token yourself.

`STORAGE_DIR` controls where recordings live (in `messages/` inside it; `./data` by default, `/data` in the Docker image).

### CI/CD

`.github/workflows/ci.yml` runs the Go backend tests (real PostgreSQL 17, race detector, generated code up to date, lint, govulncheck), the watch-app tests plus a `zeus build`, shell and secret scans, the deploy-script and backup-script tests, the language check, and the speech recognition service's tests (in a pull request that touches `stt/` it also builds the image and tries it with the production limits on made-up recordings). To save Actions minutes a pull request runs only the jobs for the parts it touches (the `changes` job; a change to `ci.yml` runs everything), a new push cancels the older run, and pushes to branches without a PR run nothing; a push to `main` or a manual run runs everything. A push to `main` after which `backend/` or `.github/scripts/` differs from what is deployed then builds `backend/Dockerfile` in GitHub Actions, pushes it to GHCR and calls the Coolify API (`.github/scripts/coolify-deploy.sh`), which waits for the deployment and, once Coolify confirms it, tags that image `:deployed`. "What is deployed" is the commit in the revision label of the `:deployed` image (`.github/scripts/image-changed.sh`), deliberately not the previous push: GitHub cancels all but the newest of the runs waiting in a queue, so two merges seconds apart used to lose the first one's deploy. The deploy jobs run only in the upstream repository and only with their secrets (`COOLIFY_URL`, `COOLIFY_TOKEN`, `COOLIFY_APP_UUID`, and `COOLIFY_STT_APP_UUID` for the recognition service); without them the image is still pushed and the deploy step only warns. Details: [`docs/ci-cd.md`](docs/ci-cd.md) and [`docs/deployment.md`](docs/deployment.md). Never ask anyone to paste a token into a chat.

## Architecture

### Three-node data flow

```
Watch (Zepp OS device app)  --BLE-->  Phone (Side Service, inside Zepp App)  --HTTPS-->  backend/
```

1. The hardware shortcut button on the watch starts and stops recording (`PigeonDrop/page/index.js`), saved to the Mini Program's private storage via `@zos/fs`.
2. On stop, the recording is sent to the phone over BLE via a vendored `MessageBuilder` channel **in numbered 15 KB chunks, one `request()` at a time, waiting for each reply** (`PigeonDrop/utils/uploadQueue.js`; see the constraint below for why). Every chunk carries the watch's device token (`PigeonDrop/utils/device.js`, received when it was paired); a watch that is not paired sends nothing and its recordings wait in the queue.
3. The Side Service (`PigeonDrop/app-side/index.js`) collects the chunks in memory (`PigeonDrop/app-side/uploads.js`) and, once the last one arrives, packs the recording into Ogg/Opus and `fetch()`es it (base64 in JSON, `{ messageId, audio }`) to `SERVER_URL + '/v1/messages'` with `Authorization: Bearer <device token>`. The Side Service keeps no token itself.
4. `backend/` finds the device by the token's hash, stores the standard Ogg/Opus file under the message's id for the device's owner, converts it to `.wav`, and answers. Repeats of the same `messageId` from the same device are harmless. A refused token (revoked device) is answered 401, which the Side Service passes to the watch as `unauthorized`; the watch forgets the token and says so.
5. The Side Service returns the server's result as the reply to the last chunk (a success carries `storage`: how full the account is; a 413 comes back as `fileError`, a 429 as `rateLimited`); the watch marks the recording uploaded only on that reply and shows progress and errors on its screen. A reply channel is the only way to observe Side Service behaviour at all, since **Side Service `console.log` output is never visible anywhere on the phone or in the Zepp app** (the watch's own "JS App Log" only shows device-side logs).

`@zos/ble/TransferFile` is deliberately not used: its Side Service `FileObject` only exposes metadata (name, path, size) with **no way to read the file bytes**. `MessageBuilder` is the only channel that carries readable data.

### Pairing the watch (QR code + device token)

Main page → Settings (`page/settings.js`) → Pair the watch opens `page/pair.js`. It asks the server for a pair of codes through the Side Service (`app-side/pairing.js`; requests `pairStart` and `pairPoll` over `MessageBuilder`'s `request()`/`response()` channel), shows a QR code for `<server>/pair?code=...` plus the short code as text, and polls every few seconds. The person opens the page on the phone, signs in, compares the code with the watch's screen and approves; the next poll hands the watch its device token once, and `utils/device.js` stores it (`device.json` via `@zos/fs`). The screen is held on while waiting (bounded by the code's 10-minute life). Contract: [`docs/api.md`](docs/api.md); server side: [`backend/README.md`](backend/README.md). Nothing about pairing is optional: an unpaired watch uploads nothing.

### `PigeonDrop/shared/`: vendored library, not an npm dependency

`message.js` (device side), `message-side.js` (Side Service side), `event.js`, `defer.js` and `data.js` implement `MessageBuilder`, copied from the official `zepp-health/zeppos-samples` repository (Apache-2.0, see `PigeonDrop/shared/LICENSE`). It auto-chunks and reassembles arbitrary payloads over BLE (raw BLE messages are size-limited; `MessageBuilder` hides that). Treat the directory as third-party code and prefer patching around it over editing it, except for the already-applied changes that each file's header lists: `message-side.js` falls back to a no-op logger when the global `Logger` is undefined, and `DEBUG` is `false` in both `message.js` and `message-side.js` (upstream ships `true`, which hex-dumps every BLE packet into the log and made large sends crawl).

### Zepp OS-specific constraints that shape the code

The project skill `.claude/skills/zeppos` holds the general Zepp OS knowledge: how to look things up in the official documentation, samples and API declarations (`scripts/setup.sh`), and the differences between the documentation and real devices (`references/gotchas.md`). Use it before writing code against `@zos/*`. This section keeps what is specific to PigeonDrop.

- **App structure**: `app.json` (`configVersion: v3`) declares a device app (`page/index.js`, `page/list.js`, `page/settings.js`, `page/pair.js`, `page/storage.js`) and a separate Side Service (`app-side/index.js`) that runs inside the phone's Zepp app with no UI and its own lifecycle (`onInit`/`onRun`/`onDestroy`; it is not continuously alive).
- **Texts**: every string a person reads comes from `i18n/en.js` and `i18n/ru.js` through `t(key, values)` (`i18n/index.js`); the language is the watch's (`getLanguage()`), English unless it is Russian. Lines are broken by hand to fit the round display, so a new text needs a line length check in both languages (`test/i18n.test.mjs`).
- **Round display**: the target device is 480×480 px, radius 240. Rectangles near the top and bottom edge get clipped by the bezel; keep element bounds within a ~230 px radius safe zone (see `page/list.js` layout constants).
- **One live `Player` at a time**: the hardware only supports a single live `@zos/media` `Player` instance. Creating a new one per playback throws `cannot read property 'addEventListener' of undefined` on the second play. Every page (and `app.js`) is built into its own bundle with its own copy of each module it imports, so a module variable cannot be shared between pages: `utils/player.js` keeps the one `Player` in `getApp()._options.globalData`, adds its listeners once and forwards events to the callbacks of the page that is playing. The same applies to the upload queue's live state (the recording being written, the running sweep with its expiring lease, the listener), kept in `globalData.uploads` by `utils/uploadQueue.js`; see `.claude/skills/zeppos/references/gotchas.md`.
- **Custom `.opus` framing**: files recorded via `@zos/media`'s recorder are **not** standard Ogg/Opus containers. Each packet is `[8-byte header][opus payload]` repeated back to back, where the header's **first 4 bytes are the payload length, big-endian** (the other 4 are unidentified and ignored). Verified empirically against real recordings; Zepp's FAQ page (`guides/faq/opus-to-mp3.md` in the documentation repository) describes the same layout. Payloads are SILK wideband, mono, 20 ms per packet, decoding to 16 kHz 16-bit PCM. That is what the watch stores and sends over BLE. The phone's Side Service (`app-side/uploads.js` → `utils/oggOpus.js`) wraps the packets, unchanged and without re-encoding, into a standard Ogg/Opus file (RFC 3533/7845: OpusHead, OpusTags, 50 packets per page, pre-skip 0) before posting to the server, so every server gets a normal file; a recording cut off mid-packet is trimmed to its complete packets instead of failing. A recording that cannot be wrapped is answered with `fileError` and skipped by the watch's queue rather than blocking it. The Go server's reader (`backend/internal/audio`) reads both formats; standard tools (`ffmpeg`) open the wrapped file but not the raw Zepp one. The packer is verified against an independent reader and ffmpeg's strict decoder; its speed and memory on a real phone for a 60 s recording have not been measured (only a 2 s one).
- **`device:os.mic` permission** must be declared in `app.json`'s `permissions` or recording throws `Permission Denied device:os.mic` at runtime; the documentation does not mention it.
- **`QRCODE` widget background sizing**: always set `bg_x/bg_y/bg_w/bg_h` together with `x/y/w/h`, centered (see `page/pair.js`); without them the background is far larger than the code and bleeds past the round bezel (seen on a real device only).
- **Never send a recording as one `MessageBuilder` message.** `call()` pushes every ~3.6 KB BLE packet in one synchronous loop with no backpressure; a 60 s recording (~212 KB as base64, ~60 packets) overran the BLE send queue, `ble.send` returned `false`, and the resulting exception was swallowed by an unhandled promise: uploads failed silently, and the work and memory involved made app start slow and the list page crash. Uploads therefore go in chunks of `CHUNK_BYTES` (must stay a multiple of 3 so the chunks' base64 concatenates) with a `request()` per chunk; keep it that way and re-test with a recording of 60 s or more on the device.
- **"No answer" means two different things, and the screen says which.** A watch that gets no reply cannot tell a Zepp app that is stuck from a phone that has no internet, and they are fixed differently, so they are told apart where they are seen (`utils/linkProblem.js` has the texts). Before every sweep `utils/uploadQueue.js` sends the phone a `ping` (10 s, one retry; any reply at all means the phone is there); silence ends the sweep with `{ state: 'error', kind: 'phone' }` and the screen tells the person to restart the Zepp app. A phone that is there but cannot reach the server answers `noServer: true` (no connection, no answer in time, or a 502/503/504 from the proxy), which the queue turns into `kind: 'server'`. That only works because the phone gives its own calls a deadline (`app-side/timeout.js`: 30 s for the upload, 10 s for pairing) that is always shorter than the watch's wait (60 s for the last chunk, 15 s for pairing requests, 30 s for other chunks): keep that order when changing either. Everything else still shows its own reason. Settings has a *Check connection* button (`app-side/serverCheck.js`): the phone does `GET /healthz`, then an empty `POST /v1/messages` with the device token (400 = accepted, nothing stored), and the status line says in a few words which step broke; the "no connection to the server" screen also prints the short reason in brackets. The timing values are estimates and the texts have not been checked on a real round display.
- **Close file descriptors as `closeSync({ fd })`.** The bare-number form leaves the descriptor open and the device only has a few, so after several uploads `openSync` fails ("cannot open file"). `utils/uploadQueue.js` also treats an unreadable file as that file's own problem (the sweep skips it and continues, the file stays queued), never treats a failed `statSync` as an empty file (that would delete the recording), and falls back to `readFileSync` when `openSync` fails. Settings has a *Clear memory* button (`clearAllRecordings`) that wipes recordings and the queue.
- **Screen sleep kills the recording.** Zepp OS sleeps the screen and ~10 s later closes the Mini Program, so an unattended long recording is lost and never queued for upload. `page/index.js` therefore holds the screen on while recording (`utils/screen.js`: `setPageBrightTime`, `pauseDropWristScreenOff`, `pausePalmScreenOff` from `@zos/display`, all bounded by `MAX_RECORDING_SECONDS`), auto-stops at that limit, and closes the file in `onDestroy` if the page is torn down mid-recording. Any upload also holds it, for a `UPLOAD_SCREEN_HOLD_MS` (60 s) window: armed on stop and by the first chunk of any sweep (so old queued recordings sent at app start are covered too), renewed by upload progress once under half is left, ended early when the queue empties, left to run out after an error (so the reason can be read), and replaced by the next recording's hold. Do not remove any of these without re-testing a long recording on the device.
- **Storage warning.** The server keeps at most 100 MiB of recordings per account (`STORAGE_ACCOUNT_BYTES`), deletes the oldest ones when a new one does not fit, and says so in the upload answer (`storage.state`: `ok`, `nearly_full` from 90%, `full` when it just deleted something). It cannot push to the watch, so the watch learns from that answer: `utils/uploadQueue.js` keeps the state (`utils/storageState.js`, `storage.json`) and, when it is news (it just became `nearly_full`, once; or `full`, every time, since each is a deletion), reports an `alert` with its last event; an alert that has not been shown is kept until it is. `page/index.js` then opens `page/storage.js` (state passed as the page parameter): a page of its own, because a label on the main page printed over the status text and the buttons (seen on a real watch). The page buzzes once (`VIBRATOR_SCENE_DURATION_LONG`, 1 s), holds the screen for 10 s and goes `back()` to the main page by itself; it is not opened at app start, and an alert that arrives during a recording waits until the recording stops. A refused token or a new pairing clears the remembered state. Other limits the watch has to handle: 413 (recording over 512 KiB: skipped like an unreadable file) and 429 (more than 60 uploads an hour from this device: the sweep stops, recordings wait). The page's look and the buzz on a real round display are unverified.
- **Configurable values live in `PigeonDrop/config.js`**, not hardcoded: `MAX_RECORDINGS` (oldest recordings pruned via `utils/recordings.js` once exceeded), `MAX_RECORDING_SECONDS` (longest single recording; also bounds how long the screen is held on), and `SERVER_URL` (the server for pairing and uploads).
