## 0. Кратко

1. **Нагрузка не выбирает язык.** Ваш вопрос «подойдёт ли Node.js, если пользователей будет много» решается цифрами: при 1 000 пользователей пик составляет ≈ 0,12 запроса в секунду (раздел 6 анализа), а перевод записи в 60 с из Opus в WAV занимает **25–31 мс** на ядре моего Mac **[проверено]**. Даже если ядро VPS в 10 раз медленнее, это ≈ 0,3 с на сообщение и около 4 % одного ядра на пике при 1 000 пользователей **[оценка на основе замера]**. Тот же порядок цифр у любого из рассмотренных языков.
2. **Opus-декодер не отсеял ни одного из главных кандидатов.** Я запустил декодирование вашей настоящей записи на 59,84 с в **пяти** библиотеках на трёх языках: все справились; две дали результат **бит-в-бит** с эталоном (раздел 13). Для Rust и JVM декодеры существуют, но я их не запускал.
3. **Отсеивают лицензии и вес, а не язык.** Из готовых движков цепочек `n8n` и `Windmill` нельзя взять основой платного SaaS по их лицензиям **[проверено по тексту лицензии / источник]**, а `Temporal` слишком тяжёл для вашего бюджета памяти **[вторично]**.
4. **Брокер сообщений и Redis не нужны.** В каждой экосистеме есть очередь на PostgreSQL (`pg-boss`, `River`, `Oban`, `Graphile Worker`), а PostgreSQL у вас уже есть **[источник]**.
5. **Хранилище объектов на старте не нужно.** MinIO, привычный выбор для самостоятельного хостинга, по вторичным источникам архивирован в феврале 2026 **[вторично]**. Диск за интерфейсом и квота дешевле и надёжнее.
6. **Сборку лучше вынести из VPS.** Для общего VPS правильнее собирать образ в GitHub Actions и передавать Coolify готовый (так советует документация Coolify); сейчас в нашем CI Coolify собирает сам **[источник]**.
7. **Мой общий выбор:** TypeScript от часов до сервера, с запасным вариантом Go (раздел 11). Причины и то, что может это изменить, указаны в разделах 1 и 11.

## 1. Языки и рантаймы backend

### Что сравниваем

Шесть кандидатов. Почему не больше: PHP и Ruby я не включаю, потому что их преимущества (быстрые админки и формы) здесь закрывает frontend, а для фоновых задач и работы со звуком они слабее выбранных; C#/.NET не включён отдельной строкой, потому что по большинству пунктов совпадает с Kotlin/JVM (Opus-декодер там тот же Concentus). **[оценка]**

### Жёсткие критерии (H1–H4)

| Кандидат | H1: Opus-декодер | H2: память в покое (оценка) | H3: образ Docker | H4: драйвер PostgreSQL |
|---|---|---|---|---|
| **TypeScript / Node 24** | `opusscript` (libopus 1.4 в WASM) **[проверено]**, `opus-decoder`, `ogg-opus-decoder` (WASM, MIT) **[проверено]**, `@discordjs/opus` (нативный) **[оценка]** | **48,7 МБ** у прототипа без запросов **[проверено на Mac]**; с фреймворком и драйвером 100–200 МБ **[оценка]** | Наш образ 247 МБ **[проверено]** | `pg`, `postgres` и др. **[оценка]** |
| **Go** | `tphakala/go-opus` (чистый Go, бит-в-бит) и `pion/opus` (чистый Go) **[проверено]**; `hraban/opus` (cgo + libopus) **[источник]** | 10–30 МБ **[оценка]** | Статический бинарник, образ 20–40 МБ **[оценка]** | `pgx` **[оценка]** |
| **Python** | `soundfile` + libsndfile ≥ 1.0.29 читает Ogg/Opus **[проверено]**; `opuslib` (ctypes), `PyAV` **[оценка]** | 60–120 МБ **[оценка]** | Образ 150–300 МБ **[оценка]** | `psycopg` **[оценка]** |
| **Rust** | Чистый Rust: `opus-decoder`, `opuscule`; перевод libopus `unsafe-libopus`; привязки `opus`, `audiopus` **[источник]**; в `Symphonia` декодера Opus **нет** **[источник]** | 5–20 МБ **[оценка]** | 20–50 МБ **[оценка]** | `sqlx`, `tokio-postgres` **[оценка]** |
| **Kotlin / JVM** | `Concentus` (чистый Java; близко к libopus 1.1.2, примерно 40–50 % скорости нативного) **[вторично]** | 200–500 МБ **[оценка]** | 200–350 МБ **[оценка]** | JDBC **[оценка]** |
| **Elixir** | Только нативные привязки (NIF) к libopus **[оценка, не проверено]** | 60–120 МБ **[оценка]** | 100–200 МБ **[оценка]** | `postgrex` **[оценка]** |

**Вывод по H1–H4.** Все шесть проходят H2–H4 с большим запасом (бюджет — 1,5–2 ГБ на всё). По H1 нет отсеявшихся, но есть различия в **качестве решения**:

- в Node, Go и Python декодер подтверждён моим запуском на вашей записи;
- во всех экосистемах есть запасной путь через процесс `ffmpeg`: для `.ogg` → `.wav` это ≈ 95 мс вместе с запуском процесса **[проверено]**. Цена: образ вырастает на десятки мегабайт, и появляется бинарник, который читает недоверенные файлы (P8). Поэтому разбор Ogg и декодер лучше держать внутри процесса.

| Кандидат | Плюсы | Минусы |

> **Итог раздела 1.** Нагрузка не отсеивает язык, а Opus-декодер есть везде (проверено для Node, Go и Python). Это сужает выбор до **двух сильных вариантов:** TypeScript (один язык, переиспользование кода и тестов, быстрее до MVP) и Go (меньше ресурсов, проще безопасные исходящие запросы). Остальные хуже по весу или скорости работы без выигрыша для вашей задачи.

> **Мой выбор и почему (мнение).** **TypeScript на Node 24.** Решают три вещи. Во-первых, вес критерия B2: вся система, кроме приложения на другом устройстве, остаётся на одном языке, и Claude работает с ним без переключений. Во-вторых, переиспользование: упаковщик Ogg, тесты и Docker/CI уже есть. В-третьих, ваша главная тревога («хватит ли Node при росте») не подтверждается цифрами. **Что может это изменить:** если для вас важнее минимальная память и вы готовы к двум языкам, лучше **Go**; особенно если безопасность исходящих запросов (P2) окажется сложнее, чем ожидается, потому что на Go её проще сделать надёжной. Единственное, что в TS придётся делать осторожно, это запрет приватных адресов после разрешения имени (через `undici` и свою функцию разрешения) **[оценка]**.

## 2. Фреймворки и контракт API

### Что сравниваем

Как описывать API (источник правды) и на чём строить обработчики. Контракт нужен трёх видов: приём от часов и чужих серверов (публичный, D1/D11), API для веб-клиента и контракт «своего сервера» (который будут реализовывать посторонние).

### Подход к описанию контракта

| Подход | Суть | Плюсы | Минусы |
|---|---|---|---|
| **Код → OpenAPI** | Схемы пишутся в коде (Zod, TypeBox), документ OpenAPI генерируется | Одно место правды в коде; быстро; типы совпадают с проверкой на входе | Документ — побочный продукт; легко случайно изменить контракт |
| **OpenAPI → код** | Сначала файл OpenAPI, затем генерация типов и заглушек | Контракт осознанный, ревью по diff; клиенты для Swift/Kotlin генерируются | Больше церемоний; надо поддерживать генератор |
| **tRPC и подобные** | Типы напрямую между клиентом и сервером на TS | Очень быстро для своего frontend | **Не подходит для публичного контракта** и клиентов на других языках; закрывает путь к другим платформам (R11) |

### Фреймворки (для выбранного TypeScript; остальные кратко)

| Фреймворк | Плюсы | Минусы |
|---|---|---|
| **Fastify** **[оценка]** | Зрелый, быстрый, схемы JSON/TypeBox/Zod, плагин OpenAPI, хорошая поддержка очередей и `pg` | Свой стиль плагинов; нужно изучить |
| **Hono** **[оценка]** | Лёгкий, современный, `zod-openapi` | Моложе Fastify; меньше готовых плагинов под Node |
| **NestJS** **[оценка]** | Структура «из коробки», DI, OpenAPI | Тяжёлый, много церемоний; для малого сервиса излишне |
| Go: `chi` + `huma`/`oapi-codegen`; Python: `FastAPI` (OpenAPI встроен) **[оценка]** | — | — |

### Что важно независимо от выбора

- **Публичный контракт приёма — отдельный маленький файл OpenAPI** (`POST /v1/messages` и связанное), версионируемый и с эталонной реализацией; для Ogg/Opus его уже можно описать (раздел `POST /messages` в `API_SPEC.md`).
- **Ошибки — машинные коды**, а не фразы (D12); переводит клиент.
- **Идемпотентность:** ключ «устройство + идентификатор сообщения», а не глобальный `fileName` (D1).
- **Наш тест сервера (`server/test/server.test.js`) работает по HTTP снаружи** и не зависит от языка реализации. Его можно превратить в **контрактный тест**, который прогоняется против любого нового сервера: это страховка при смене стека.

> **Итог раздела 2.** Для веб-API достаточно «код → OpenAPI»; для **публичного** контракта приёма стоит вести OpenAPI-файл вручную. tRPC исключён из-за будущих клиентов. Из фреймворков выбор — Fastify или Hono; NestJS избыточен.

> **Мой выбор и почему (мнение).** **Fastify**, схемы на Zod или TypeBox, OpenAPI из кода; для приёма — отдельный OpenAPI-файл. Fastify зрелее Hono и лучше документирован; для проекта «вы + Claude» важнее предсказуемость, чем новизна.

## 3. База данных: доступ, миграции, схема

### Что сравниваем

СУБД решена: **PostgreSQL** (Q11), отдельная база и пользователь на проект. Версию нужно узнать. Здесь выбираем способ работы с ней.

### Варианты доступа (для TypeScript; **[оценка]**)

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Drizzle ORM** | Схема в TS, миграции генерируются, близок к SQL, лёгкий; есть адаптер у Better Auth | Моложе; бывают изменения API |
| **Kysely** | Типизированный конструктор запросов; ближе всего к чистому SQL; Better Auth использует его внутри | Миграции и схему описываете отдельно |
| **Prisma** | Много обучающих материалов | Тяжелее; собственный слой генерации; лишний уровень там, где хватает SQL |
| **Голый SQL** (`pg`) + файлы миграций | Максимум контроля, нет магии | Больше ручной работы и ошибок; типы вручную |

Инструменты миграций: встроенные у Drizzle, а также `dbmate`, `node-pg-migrate`, Atlas. Принцип независимо от выбора: **миграции — файлы в репозитории**, применяются явным шагом при выкладке, а не «как-нибудь при старте» (две копии сервера не должны мигрировать одновременно).

### Схема данных (набросок, **[оценка]**)

| Сущность | Что хранит | Заметки |
|---|---|---|
| `accounts` | Пользователь: почта, хеш пароля, тип (free/paid), язык | Хеш Argon2id (раздел 9) |
| `devices` | Устройство: аккаунт, имя, хеш токена, платформа, дата привязки | Токен хранится только в виде хеша; можно отозвать |
| `messages` | Сообщение: аккаунт, устройство, **идентификатор от клиента**, длительность, размер, путь к файлу, `expires_at` | Ключ идемпотентности `(device_id, client_message_id)` с уникальным индексом |
| `chains`, `chain_steps` | Цепочка пользователя и её шаги: тип, конфигурация, порядок | Секреты ссылкой, не в тексте конфигурации |
| `secrets` | Токены ботов и ключи: шифртекст, версия ключа | Шифрование на стороне приложения (раздел 10) |
| `runs`, `run_steps` | Запуск цепочки и результат каждого шага | История с ограниченным сроком жизни (N6) |
| очередь | Таблицы выбранной библиотеки очередей | Раздел 4 |

**Изоляция данных (P9).** Каждый запрос фильтруется по аккаунту; в качестве второго рубежа можно включить **Row Level Security** PostgreSQL, чтобы ошибка в запросе не показала чужую запись **[оценка]**. Это дешёвая страховка стоимостью в несколько политик.

**Срок хранения (R5).** Поле `expires_at` и фоновое задание, которое удаляет файл и запись; квота диска считается по сумме размеров в БД и проверяется до приёма.

> **Итог раздела 3.** Выбор слоя доступа во многом вкусовой: Drizzle и Kysely одинаково годятся. Важнее: уникальный индекс на идентификатор от клиента, шифрование секретов, ограниченный срок жизни истории, второй рубеж изоляции через RLS и миграции как файлы.

> **Мой выбор и почему (мнение).** **Drizzle** + файлы миграций в репозитории: схема живёт рядом с типами, а библиотека входа (раздел 9) умеет с ним работать. Если вам больше по душе SQL, Kysely почти равноценен.

## 4. Фоновые задачи

### Что сравниваем

Очередь нужна для надёжности и разгрузки (R6): сообщение принимается быстро, цепочка выполняется в фоне с повторами. Ограничение: **без нового сервиса** (память общего VPS). Задержка до 5 минут допустима (R13).

### Варианты

| Вариант | Что это | Плюсы | Минусы |
|---|---|---|---|
| **pg-boss** (Node) | Очередь на PostgreSQL. MIT; нужен Node ≥ 22.12 и PostgreSQL ≥ 13 **[источник]** | `SKIP LOCKED`, повторы с нарастающей паузой, расписание, очередь недоставленных, зависимости заданий, метрики OpenTelemetry **[источник]**; без нового сервиса | Одна библиотека — привязка к Node |
| **Graphile Worker** (Node) | Очередь на PostgreSQL с `LISTEN/NOTIFY`, `SKIP LOCKED`, повторами и расписанием; MIT **[источник]** | Мгновенное пробуждение по `NOTIFY` | Меньше возможностей из коробки, чем у pg-boss **[оценка]** |
| **Свой SQL** (`SKIP LOCKED`) | Таблица заданий и цикл воркера | Нет зависимостей, полный контроль | Вы сопровождаете повторы, пропавшие задания, метрики; легко ошибиться **[оценка]** |
| **River** (Go) | Очередь на PostgreSQL; MPL-2.0; транзакционная постановка, уникальные задания, веб-интерфейс, периодические задания **[источник]** | Лучшее из «в БД» для Go | Только для Go |
| **Oban** (Elixir) | Очередь на PostgreSQL; открытая часть Apache 2.0; воркфлоу, лимиты и пакеты только в платной Pro **[источник]** | Очень зрелый | Только Elixir; ключевые возможности платные |
| **Procrastinate** (Python) | Очередь на PostgreSQL **[оценка]** | Нативно для Python | Только Python |
| **BullMQ** + Redis | Очередь на Redis | Быстрая, популярная | **Новый сервис** (Redis) и память; для 0,12 запроса в секунду избыточно **[оценка]** |
| **Temporal** | Платформа «надёжного исполнения»; MIT | Мощная модель ожидания и повторов | Тяжёлая: минимальная установка 2 ядра и 4 ГБ, несколько внутренних сервисов и БД **[вторично]**; не вписывается в бюджет H2 |
| **Hatchet** | Оркестратор задач и DAG; MIT; **только PostgreSQL**, без Redis и RabbitMQ; SDK для TS, Go, Python, Ruby **[источник]** | Подходит под ваши требования к числу сервисов; DAG на вырост | Отдельный сервис внутри VPS; требования к памяти в документации не нашёл **[источник]** |
| **Inngest** | Оркестрация шагов; сервер под SSPL с переходом в Apache 2.0 через 3 года; с 2025 года умеет PostgreSQL **[вторично]** | Удобная модель | Лицензия не OSI-открытая (SSPL): риск для вас как SaaS **[вторично]** |

### Принципы, которые не зависят от выбора

- **Доставка «как минимум один раз» и идемпотентные шаги.** Повтор шага не должен посылать второе сообщение в Telegram (идентификатор запуска + шага).
- **Постановка задания в той же транзакции, что и запись сообщения.** Тогда не бывает «сообщение записано, а задание потеряно»; в River это сделано как раз для этого **[источник]**; для выбранной библиотеки это нужно проверить (не нашёл подтверждения у pg-boss).
- **Видимость:** возраст самого старого задания и число недоставленных (D10).
- **Пауза между повторами растёт, с небольшим случайным сдвигом**; таймаут на шаг.

> **Итог раздела 4.** Для вашего масштаба достаточно очереди **в PostgreSQL**: она не добавляет сервисов. В TS это `pg-boss` (или `Graphile Worker`), в Go — `River`. Redis и брокеры избыточны; Temporal слишком тяжёл; Hatchet стоит помнить как вариант, если цепочки станут ветвиться.

> **Мой выбор и почему (мнение).** **pg-boss** (при TS) или **River** (при Go). Оба держат всё в вашей PostgreSQL, зрелые, с повторами и метриками. Свой SQL я не советую: на повторах и потерянных заданиях ошибаются чаще всего.

## 5. Файловое хранилище

### Что сравниваем

Где лежат записи (Ogg/Opus ≈ **2,2 КБ/с**, 60 с ≈ 133 КБ **[проверено]**). Диск — главное ограничение вашего VPS (≈ 67 ГБ свободно на все проекты).

### Варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Локальный диск за интерфейсом** (`put/get/delete/stat`) | Простейший; быстрый; ни одного нового сервиса; работает и в Coolify (том) | Один сервер; квота и копии на вас; нет раздачи по сети |
| **S3-совместимое облако** (Backblaze B2, Cloudflare R2, Wasabi и др.) | Не занимает диск VPS; копии «из коробки»; масштабируется | Задержка и плата за трафик/операции; зависимость от внешнего сервиса; B2 у вас уже есть, но для копий **[оценка]** |
| **S3 на своём VPS** (SeaweedFS — Apache-2.0; Garage — AGPLv3; RustFS — Apache-2.0) | Свой контроль, API S3 | Новый сервис и память; **MinIO**, традиционный выбор, по вторичным источникам в режиме поддержки с декабря 2025 и архивирован в феврале 2026 **[вторично]**; для вашего объёма избыточно |
| **В самой PostgreSQL** (`bytea`, large objects) | Транзакционность, одна копия | Раздувает базу и её копии; для 14,5 ГБ/год (S2) не нужно **[оценка]** |

### Что важно независимо от выбора

- **Интерфейс хранилища** с самого начала (`put/get/delete`), чтобы позже подключить S3 без переписывания цепочек.
- **Хранить Ogg/Opus как есть; WAV делать по требованию** и кэшировать на короткий срок (в 14 раз больше по месту, раздел 6 анализа).
- **Квота:** счётчики по аккаунтам в БД + контроль общего диска; жёсткий потолок на уровне ОС (отдельный том, квота XFS) нужно проверить на вашем VPS **[оценка]**.
- **Копии:** Backrest + B2 для тома с записями и `pg_dump` базы проекта; проверка восстановления обязательна (D10).
- **Удаление по сроку:** фоновое задание, раздел 3.

> **Итог раздела 5.** Для MVP — **диск за интерфейсом**: самое простое, и объём (14,5 ГБ/год при 1 000 пользователей без сроков хранения) в ваш бюджет укладывается. S3 подключается позже без переделок. Свой S3-сервер не нужен; MinIO выбирать не стоит.

> **Мой выбор и почему (мнение).** **Диск с интерфейсом `Storage`**, квоты в БД, WAV по требованию. S3 (B2 или R2) — первый шаг, если диск станет тесным; новый сервис на VPS для этого не нужен.

## 6. Исполнитель цепочек

### Что сравниваем

Линейная цепочка из 2–4 узлов (конвертация → Telegram, позже распознавание и внешние API); настраиваемые блоки; изоляция пользователей (R7, D5, D6). Вопрос: писать свой исполнитель или взять готовый движок.

### Готовые решения

| Решение | Лицензия | Подходит как основа SaaS? | Заметки |
|---|---|---|---|
| **n8n** | Sustainable Use License: использовать или менять можно только для **собственных внутренних деловых нужд или некоммерчески**; распространять только бесплатно и некоммерчески; файлы `.ee.` требуют отдельной корпоративной лицензии **[проверено по тексту лицензии]** | **Нет**: нельзя предлагать как сервис другим | Отсеян по лицензии |
| **Windmill** | AGPLv3 и Apache-2.0 для сборки без «enterprise»; для коммерческого перераспространения и управляемого сервиса нужна коммерческая лицензия; 1 воркер на 1 vCPU и 1–2 ГБ **[источник]** | **Нет** без договора; тяжёл для вашего бюджета | Отсеян по лицензии и ресурсам |
| **Activepieces** | Community-версия MIT; корпоративные функции под отдельной коммерческой лицензией; в compose-файлах Postgres и Redis **[источник]** | Возможно, но с оговорками: нужен Redis, собственный слой секретов и изоляции; встраивание, вероятно, платное **[не подтверждено]** | Много интеграций («pieces» — npm-пакеты на TS), но вы строите свой продукт, а не их |
| **Node-RED** | Apache-2.0 **[проверено]** | Нет: редактор для одного пользователя, без изоляции и аккаунтов **[оценка]** | Подходит для личных автоматизаций, не для SaaS |
| **Temporal** | MIT | Технически да, **но тяжёл** (2 ядра и 4 ГБ на минимальную установку) **[вторично]** | Это платформа надёжного исполнения, а не редактор цепочек |
| **Hatchet** | MIT; только PostgreSQL **[источник]** | Да как движок под вашим интерфейсом (DAG, надёжные задачи) | Отдельный сервис; пригодится, если цепочки станут сложными |
| **Inngest** | SSPL → Apache-2.0 через 3 года **[вторично]** | Рискованно по лицензии | — |

### Свой исполнитель

Линейная цепочка — это немного: реестр типов узлов, запись запуска и шагов, очередь, повторы и таймауты.

| Что делает | Как |
|---|---|
| Хранит цепочку | Таблицы `chains`, `chain_steps` (раздел 3); тип узла + конфигурация + ссылка на секрет |
| Запускает | Задание в очереди (раздел 4) после приёма сообщения; в нём шаги по порядку |
| Передаёт данные | Один объект контекста (сообщение, результат прошлого шага), типизированный |
| Шаблоны текста для Telegram | Простая подстановка `{{duration}}` без исполнения кода |
| Повторы и таймауты | Политика на шаг; идемпотентность по `(запуск, шаг)` |
| История и отладка | `runs`, `run_steps` с ошибкой и временем (N6); «тестовый запуск узла» (N12) |
| Безопасность | Запрет приватных адресов для исходящих запросов узлов (P2), лимиты размера ответа и времени |

**Оценка объёма:** ядро исполнителя — несколько сотен строк плюс узлы **[оценка]**; основная работа — не в исполнителе, а в узлах, редакторе и безопасности.

**Когда пересматривать:** если понадобятся ветвления, циклы и параллельные ветки, имеет смысл вынести исполнение в Hatchet или добавить слой DAG поверх своей очереди, а не переходить на n8n.

> **Итог раздела 6.** `n8n` и `Windmill` отсеяны **лицензиями**, `Temporal` — весом, `Node-RED` — отсутствием многопользовательности. `Activepieces` и `Hatchet` технически возможны, но добавляют сервисы и зависимость ради функций, которых линейной цепочке не нужно. **Свой исполнитель** на очереди в PostgreSQL проще и безопаснее.

> **Мой выбор и почему (мнение).** **Свой линейный исполнитель** поверх `pg-boss` (раздел 4). Его объём мал, а важнейшее (изоляция пользователей, секреты, защита исходящих запросов) пришлось бы писать вокруг любого готового движка всё равно.

## 8. Локализация во всех клиентах

| **FormatJS (`react-intl`)** | Стандартный ICU «из коробки» | Только React-мир |
| **Lingui** | Каталоги в формате `.po` по умолчанию, компилируемые сообщения, маленький размер **[оценка]** | Меньше материалов, чем у i18next |
| **vue-i18n / Paraglide** | Для Vue и Svelte соответственно **[оценка]** | — |

### Один источник строк

Раз Zepp OS требует `.po`, а Lingui и платформы переводов (Weblate, Crowdin) читают `.po`, **общий формат `.po` в репозитории** может стать единым источником для часов и web **[оценка, не проверено]**. Что для этого нужно в любом случае: **единые ключи**, **автоматическая проверка «нет перевода»** в CI и **проверка английских текстов живым человеком** (рынок англоязычный, D12).

> **Итог раздела 8.** Для часов формат задан платформой (`.po`); для web выбор свободный. Выгодно держать **один формат и одни ключи** везде, где возможно, и проверять отсутствие переводов в CI. Главный открытый вопрос: как Zepp OS обращается с множественными формами и запасным языком; ответ получим только на часах.

> **Мой выбор и почему (мнение).** **`.po` в репозитории как общий формат**, `Lingui` или `i18next` для web, коды вместо фраз в API, проверка непереведённых ключей в CI. Платформу переводов (Weblate и подобное) пока не нужно: два языка и один владелец проще вести файлами.

## 9. Вход, сессии и токены устройств

### Что нужно (Q6, Q13, P4)

Вход людей по **почте и паролю**; веб-клиент на одном домене с API; **устройства** (часы) со своими токенами; привязка устройства к аккаунту; письма (подтверждение и сброс пароля) нужны позже, почтовый сервис выбирается перед публикацией.

### Web: сессии и пароли

- **Пароли:** хеш **Argon2id**; OWASP предписывает минимум **19 МиБ памяти, 2 прохода, 1 поток** (допустимы эквивалентные сочетания, например 46 МиБ и 1 проход) **[проверено]**.
- **Сессия:** запись в PostgreSQL + **непрозрачный случайный токен** в cookie `HttpOnly; Secure; SameSite=Lax`; защита от CSRF; на одном домене CORS не нужен **[оценка]**.
- **Ограничения:** частота попыток входа, блокировка перебора, смена токена при входе, завершение всех сессий при смене пароля.

### Библиотеки (для TypeScript)

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Better Auth** | Рекомендован как преемник `Lucia` **[вторично]**; есть плагины, поддержка Drizzle и PostgreSQL; **плагин авторизации устройств** по RFC 8628 и плагин для передачи токена в заголовке **[источник]** | Молодая, быстро меняется (версия 1.7 уже вышла); перед внедрением нужно проверить открытые проблемы **[источник]** |
| **Auth.js** | Распространена | Ориентирована на OAuth и Next.js **[оценка]** |
| **Свой код на примитивах** (Argon2id, таблица сессий) | Ноль зависимостей, полный контроль; `Lucia` как раз стала учебным руководством («Copenhagen Book») после объявления о прекращении поддержки в марте 2025 **[вторично]** | Больше кода и ответственности (сотни строк плюс тесты) |
| **Внешний IdP** (Keycloak, Authentik, Zitadel, Ory Kratos) | Богатые возможности (вход через Google и т. д.) | Отдельные сервисы и память; для почты и пароля избыточно **[оценка]** |

### Токены устройств

Ваш текущий порядок (часы показывают QR с кодом → пользователь открывает страницу на телефоне) по смыслу совпадает с **RFC 8628 «Device Authorization Grant»**: устройство без удобного ввода показывает пользователю код и адрес, а сама ждёт, пока пользователь подтвердит его на втором устройстве **[проверено]**.

- Сервер выдаёт **длинный непрозрачный токен устройства**; в БД лежит **только его хеш**; токен можно отозвать; права ограничены приёмом сообщений.
- Устройство отправляет токен с каждым запросом; Side Service хранит его в доступном ему хранилище.
- Секрет «своего сервера» (D11) — отдельный и не равен токену устройства.
- Код привязки живёт недолго и одноразовый; число попыток ограничено.

> **Итог раздела 9.** Для входа нужны **Argon2id**, серверные сессии в cookie и ограничение перебора; для устройств — схема из RFC 8628 с хешированными, отзываемыми токенами. Выбор: молодая готовая библиотека (Better Auth) против собственного небольшого модуля на примитивах.

> **Мой выбор и почему (мнение).** **Better Auth для веб-входа** (почта и пароль, сессии) и **собственный небольшой модуль токенов устройств** (или их плагин после проверки). Так вы не пишете безопасность с нуля там, где задача стандартная. Условие: перед внедрением посмотреть версию и открытые проблемы; если библиотека окажется нестабильной, замена на свой код не потребует менять схему данных.

## 10. Развёртывание на общем VPS

### Что сравниваем

Как выкладывать и как не навредить соседям (R12, P18). В вашем Coolify уже есть всё нужное; вопросы в том, **где собирать образ**, как ограничить ресурсы и где хранить секреты.

### Где собирать образ

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Coolify собирает из Git на VPS** (сейчас так в нашем CI) | Просто настроить; не нужен реестр | Сборка даёт **пики CPU и памяти на общем VPS** (в Coolify есть отдельный раздел про сбои сервера во время сборки) **[источник]** |
| **Образ собирает GitHub Actions → реестр → Coolify тянет готовый** (тип «Docker Image», запуск по webhook после проверок) | Сборка вне VPS; Coolify только запускает; проверки и сборка в одном конвейере | Нужен реестр (GHCR и подобные); немного больше настройки **[источник]** |
| **Отдельный сервер сборки Coolify** | Полное разделение | Нужен **отдельный чистый сервер** и реестр; недоступно для Docker Compose; у вас один VPS **[источник]** |

### Ограничения ресурсов и среда

| Тема | Что делаем |
|---|---|
| Процессор и память | В Coolify: **Configuration → Resource Limits** (число CPU, в том числе дробное, и память) **[источник]**. Начальные значения: 1 CPU и 512 МБ на приложение; уточнить по замерам |
| Диск | Отдельный том для записей; квота на уровне ОС (отдельная файловая система или квота XFS) **[оценка]**; квоты по аккаунтам в БД |
| PostgreSQL | Общий экземпляр, **отдельные база и пользователь на проект**, ограниченные права (Q11); версию узнать |
| Миграции | Отдельный шаг при выкладке, а не при каждом старте |
| Проверка здоровья | В образе уже есть (`/setup`); для нового сервера — свой маршрут `/healthz` |
| Секреты пользователей | Шифрование **на стороне приложения** (например, AES-256-GCM, ключ в окружении Coolify, версия ключа в записи) **[оценка]**, чтобы копии БД не содержали токенов ботов открытым текстом |
| Копии | Backrest + B2 для тома с записями; ночной `pg_dump` базы проекта; **проверка восстановления** (Q15) |
| Наблюдаемость | Диск, память, возраст самого старого задания; уведомления Coolify; при желании Uptime Kuma **[оценка]**. Логи без содержимого сообщений |
| Журналы Docker | Ограничить размер и число файлов, чтобы журналы не съели диск **[оценка]** |

### Что из текущего конвейера останется при смене стека

- **Схема остаётся:** проверки → образ → вызов API Coolify → ожидание результата. Если выберем TypeScript, Dockerfile и CI почти не меняются.
- **Если выберем Go или другой язык:** Dockerfile и тесты придётся переписать; **контрактный HTTP-тест** (раздел 2) переносится.
- **Рекомендуемая правка уже сейчас:** перейти на сборку образа в GitHub Actions и деплой готового образа (вторая строка таблицы). Это изменит `.github/workflows/ci.yml` и способ создания приложения в Coolify.

> **Итог раздела 10.** Coolify умеет ограничивать CPU и память и принимать готовый образ по webhook, поэтому **сборку лучше вынести из VPS** в GitHub Actions, а Coolify оставить запуск. Отдельный сервер сборки вам не подходит (нужен второй сервер). Ключевые решения: лимиты ресурсов, отдельный том с квотой, шифрование секретов на стороне приложения, копии с проверкой восстановления.

> **Мой выбор и почему (мнение).** **Образ из GitHub Actions в GHCR, Coolify тянет готовый**, лимиты 1 CPU и 512 МБ на старте, отдельный том для записей, шифрование секретов в приложении. Сборка на самом VPS вернёт пики нагрузки, о которых вы же предупреждали в анализе (раздел 1.2).

## 11. Три сквозных набора

Выбор тем 1–10 связан: ниже три согласованные «сборки». Для каждой указано, чем она хороша и что придётся делать.

| | **A. TypeScript везде** | **B. Go + TypeScript** | **C. Python + TypeScript** |
|---|---|---|---|
| Backend | Node 24, Fastify | Go, `chi` + `huma` | FastAPI |
| Очередь | `pg-boss` | `River` | `Procrastinate` **[оценка]** |
| Доступ к БД | Drizzle | `pgx` + `sqlc` **[оценка]** | SQLAlchemy **[оценка]** |
| Opus-декодер | `opus-decoder` или `opusscript` **[проверено]** | `go-opus` или `pion/opus` **[проверено]** | `soundfile` **[проверено]** |
| Вход | Better Auth + токены устройств | Свой код (`scs` + Argon2id) **[оценка]** | Свой код или `Authlib` **[оценка]** |
| Frontend | React + Vite | React + Vite | React + Vite |
| Языков в проекте | **1** (TS) | 2 | 2 |
| Общий код с клиентом и текущим прототипом | **Да** (упаковщик Ogg, тесты, CI) | Нет | Нет |
| Память в покое | ≈ 100–200 МБ **[оценка]** | ≈ 20–50 МБ **[оценка]** | ≈ 100–200 МБ **[оценка]** |
| Безопасные исходящие запросы (P2) | Реализуем осторожно (`undici`) | **Проще всего** | Средне |
| Скорость до MVP **[оценка]** | **Быстрее всего** | Средне | Быстро |
| Главный риск | Одна нить (на 25 мс в сообщении не критично), нужно следить за типами на входе | Второй язык; чисто-Go декодеры молодые | Память, динамическая типизация |

**Что может изменить выбор в пользу Go (набор B):**

- вы хотите минимум памяти и один статический бинарник;
- проверка безопасности исходящих запросов (P2) на TS окажется сложнее ожидаемого;
- вас не смущает второй язык, а общий с часами код вам не важен.

**Что говорит за A:** один язык и один набор типов от часов до интерфейса, готовые тесты и CI, самая быстрая дорога к MVP, а нагрузка (раздел 0) не создаёт причин для смены.

> **Итог раздела 11.** Наборы A и B одинаково жизнеспособны; C заметно слабее для вашей задачи. **A выигрывает в скорости и простоте**, **B — в ресурсах и безопасности исходящих запросов**.

## Итог документа

1. **Нагрузка не отсеивает ни один язык**: пик при 1 000 пользователей — около 0,12 запроса в секунду, перевод 60 секунд Opus в WAV занимает десятки миллисекунд. Ваше сомнение насчёт Node в смысле производительности цифрами не подтверждается.
2. **Opus-декодер подтверждён запуском** на настоящей записи для Node (две библиотеки), Go (две) и Python (одна); у двух результат совпадает бит-в-бит. Для Rust и JVM он есть, но не запускался.
3. **Лицензии отсеивают готовые движки цепочек**: `n8n` и `Windmill` нельзя положить в основу платного SaaS. Остаётся **свой линейный исполнитель** на очереди в PostgreSQL (`pg-boss` или `River`); Redis, брокер и S3-сервер на VPS не нужны.
4. **Два сильных набора:** **A — TypeScript везде** (один язык, общий код и тесты, быстрее до MVP) и **B — Go + TypeScript** (меньше памяти, проще безопасные исходящие запросы). C (Python) слабее.
5. **Мой выбор — набор A**, с заменой на B, если для вас важнее ресурсы и безопасность исходящих запросов, чем один язык.
6. **Развёртывание:** образ собирать в GitHub Actions, Coolify только запускает готовый, лимиты 1 CPU и 512 МБ на старте, отдельный том с квотой, шифрование секретов в приложении, копии с проверкой восстановления.
7. **От вас нужно одно главное решение (набор A или B)**; остальное имеет значения по умолчанию (раздел 12) и не блокирует начало.
