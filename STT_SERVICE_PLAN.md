# Сервис расшифровки записей: проект и план реализации

_Версия 1.0 · 2026-10-10 · Статус: **проект, ничего не реализовано**; решения владельца учтены (раздел 1)_

Как превратить принятую запись в текст на вашем VPS: очередь, воркер, контейнер с моделью, изменения в базе и API, развёртывание, порядок работ и тесты. Выбор модели и её измеренные характеристики описаны в [`STT_COMPARISON.md`](STT_COMPARISON.md) (раздел 7); здесь только то, как встроить её в сервер. Пометки: **[проверено]** измерено или прочитано в коде, **[оценка]** мой расчёт, **[не проверено]** допущение, которое проверяется на шаге 0.

## 1. Решения владельца и границы

Решено 2026-10-10:

1. **Модель работает в отдельном контейнере на Python** (Parakeet TDT v3, `onnx-asr`, как в замере). Сервер на Go отправляет ему WAV по HTTP.
2. **Расшифровываются все новые записи автоматически.** Старые не трогаем; поставить их в очередь можно командой оператора.
3. **Записи по одной**, через очередь в PostgreSQL на VPS.
4. **Облако не используется**: звук не покидает VPS.
5. **Параллельной обработки нет: одна запись за раз, один поток обработки, одна копия модели.** Контейнеру модели 3 ГБ памяти без подкачки (подтверждено 2026-10-10 после замеров, `STT_COMPARISON.md`, 7.4–7.5). Сколько ядер давать, покажет проверка на VPS (1 или 2).

Входит в работу: очередь, воркер, контейнер модели, таблица результатов, показ текста в API и на странице `/pair`, команды оператора, развёртывание, тесты.

Не входит (но проект их не закрывает): цепочки (Telegram и др.), которые будут брать текст; выбор языка пользователем; повторная расшифровка другой моделью (поля для неё заложены, интерфейса нет); разбор по говорящим; перевод.

## 3. Архитектура

```
 часы ──BLE──▶ телефон ──HTTPS──▶ POST /v1/messages ─────────────┐ (как сейчас, не меняется для часов)
                                                                  ▼
 ┌────────────────────────── контейнер сервера (Go, 512 МиБ) ─────────────────────────┐
 │  приём: файл <id>.opus ─▶ транзакция: строка messages + строка transcriptions(pending)
 │                                   │ сигнал «есть работа» (канал) и опрос раз в 2 с
 │  воркер очереди (одна горутина) ◀─┘
 │    1. берёт самую старую готовую задачу (FOR UPDATE SKIP LOCKED), ставит аренду
 │    2. читает <id>.opus ─▶ audio.ToWAV
 │    3. POST WAV ─────────────────────────────────────────────┐
 │    4. записывает текст (или повтор / ошибку) в transcriptions │
 │  API и страница /pair показывают состояние и текст            │
 └──────────────────────────────────────────────────────────────┼─────────────────────┘
                                                                 ▼ внутренняя сеть, порт не публикуется
                              ┌──────── контейнер stt (Python, лимит 3 ГБ) ────────┐
                              │  POST /v1/transcribe (WAV) ─▶ JSON {text, ...}     │
                              │  GET /healthz (200 только когда модель загружена)   │
                              │  один запрос за раз, второй получает 429            │
                              └─────────────────────────────────────────────────────┘
```

Граница ответственности: **вся логика очереди, повторов и хранения в Go-сервере, модель контейнера ничего не знает про пользователей, записи и базу.** Поэтому модель или поставщика меняют заменой контейнера (или адаптера `Transcriber`), а очередь остаётся.

## 4. Принятые решения и почему

| Вопрос | Решение | Почему | Отвергнуто |
|---|---|---|---|
| Очередь | Таблица `transcriptions` в PostgreSQL, выборка `FOR UPDATE SKIP LOCKED`, собственный воркер | Один вид задач и один потребитель; нет новых зависимостей и чужой схемы; состояние читается обычным SQL. **Это отход от `STACK_COMPARISON.md` (там для Go советовали River)**: River окупится, когда появятся цепочки с несколькими видами задач; тогда эту таблицу можно перенести | River сейчас: лишняя зависимость и собственные таблицы ради одного типа задач |
| Где воркер | Горутина в `pigeondrop serve`, как уже сделано для `purgeExpired` | Не нужен третий контейнер и третий деплой; позже выносится отдельной командой `pigeondrop worker` тем же кодом | Отдельный процесс сразу |
| Постановка в очередь | В той же транзакции, что и строка `messages` | Нельзя потерять задачу и нельзя поставить задачу на несуществующую запись | Отдельная постановка после ответа часам |
| Повторы одной и той же отправки | Задача создаётся только при новой строке (`fresh`) | Дубликат отправки не даёт второй расшифровки | |
| Передача звука | WAV в теле HTTP-запроса; контейнер превращает его в массив в памяти, без временного файла | Модель ест только звук (PCM), а не Opus: декодировать Opus придётся в любом случае, и в Go это уже есть (`ToWAV`, около 30 мс), причём для обоих форматов записи, включая старый `zepp`. В образе модели нет ни одного декодера Opus (см. раздел 2). WAV сам описывает себя (частота, каналы), его проверяет контейнер и принимают другие движки | Отправлять `.opus` и декодировать в Python (подробно ниже); общий том с `.opus`; сырой PCM вместо WAV (экономия 44 байт) |
| Один за раз | Воркер последователен, контейнер модели дополнительно отвечает 429, если уже занят | Защита при перекрытии старого и нового контейнера во время редеплоя | Пул воркеров |
| Хранение результата | Текст в той же базе, в таблице `transcriptions` | Копируется резервными копиями, удаляется каскадом вместе с записью | Файл `.txt` рядом с аудио |
| Сеть модели | Порт не публикуется, общий секрет `STT_TOKEN` | Расшифровка не должна быть доступна из интернета | Открытый порт |
| Если `STT_URL` пуст | Расшифровка выключена, записи в очередь не ставятся | Сервер работает без контейнера модели (разработка, тесты) | |

**Почему не отправлять `.opus` в модель напрямую.** Модель работает со звуковой волной, поэтому Opus в любом случае должен быть раскодирован; вопрос только где. Сейчас это делает Go (`ToWAV`, около 30 мс на минутную запись, без внешних программ). Раскодировать в Python можно, но это требует добавить в образ `libsndfile` (пакет `soundfile`) или `ffmpeg`: ещё один разбор чужих файлов внутри контейнера и ещё одна зависимость, которую нужно собирать и обновлять. Выигрыш один: запрос меньше (около 140 КиБ вместо 1,9 МБ на минуту звука), но он идёт между контейнерами одного сервера, и это ничего не стоит. Проигрыш ещё один: старый формат записи `zepp` стандартные библиотеки не читают, его всё равно пришлось бы раскодировать в Go, и логика разошлась бы на два места. Поэтому: **Go раскодирует, контейнер получает WAV**. К этому вопросу стоит вернуться, только если изменится то, что сейчас верно (облако, принимающее Ogg/Opus, или перенос всего на Go).

## 5. Данные

Миграция `00005_transcriptions.sql` (черновик):

```sql
CREATE TABLE transcriptions (
    message_id   uuid        PRIMARY KEY REFERENCES messages (id) ON DELETE CASCADE,
    state        text        NOT NULL CHECK (state IN ('pending', 'running', 'done', 'failed', 'skipped')),
    -- Попытки, в которых виновата сама запись или сервис модели ответил ошибкой. Недоступность сервиса не считается.
    attempts     integer     NOT NULL DEFAULT 0,
    run_after    timestamptz NOT NULL,            -- раньше этого момента задачу не брать (пауза между повторами)
    locked_until timestamptz,                     -- аренда: пока не истекла, running не отнимают
    enqueued_at  timestamptz NOT NULL,
    started_at   timestamptz,
    finished_at  timestamptz,
    text         text,
    language     text,                            -- что определила модель, если сказала
    engine       text,                            -- чем сделан текст, например parakeet-tdt-0.6b-v3-int8
    audio_ms     integer,
    stt_ms       integer,                         -- сколько считала модель (для расчёта нагрузки)
    error_code   text,                            -- not_decodable, too_long, rejected, too_many_failures, file_missing
    CHECK ((state = 'done') = (text IS NOT NULL))
);
-- Очередь: только то, что ещё не закончено, по порядку постановки.
CREATE INDEX transcriptions_queue_idx ON transcriptions (enqueued_at) WHERE state IN ('pending', 'running');
```

- Принадлежность пользователю берётся через `messages.user_id` (соединением), как у остальных запросов: в самих запросах, чтобы обработчик не мог забыть проверку.
- **Все моменты времени передаёт Go** (`s.now()`), а не `now()` базы: как у `received_at`, и тесты могут подставлять часы.
- Текст очищается перед записью: PostgreSQL не хранит NUL, управляющие символы кроме перевода строки убираются (`plainText` из `recordings.go` уже делает похожую проверку), длина не больше 20 000 знаков.
- Пустой текст это нормальный успех (тишина): состояние `done`, текст `''`. Страница пишет «речь не обнаружена».

## 6. Жизненный цикл задачи

| Из | В | Когда |
|---|---|---|
| (нет) | `pending` | запись принята и её можно декодировать |
| (нет) | `skipped` (`not_decodable`) | запись принята, но не декодируется (`has_wav = false`) |
| (нет) | `skipped` (`too_long`) | запись длиннее `STT_MAX_AUDIO_SECONDS`: сервер принимает файлы до 512 КиБ (около 3,7 минуты), а память проверена только до 60 секунд, поэтому такую модели не отправляем |
| `pending` | `running` | воркер взял задачу: `attempts + 1`, аренда `STT_TIMEOUT + 30 с` |
| `running` | `done` | модель вернула текст (даже пустой) |
| `running` | `pending` | временный сбой: пауза `run_after`, см. ниже |
| `running` | `pending` | аренда истекла (процесс умер): задачу берёт следующий опрос |
| `running` | `failed` | запись отвергнута (`rejected`) или попыток 5 (`too_many_failures`) |
| `failed` | `pending` | пользователь нажал «повторить» или оператор |

**Четыре вида сбоя, различаются обязательно.** Простой модели на час не должен сжечь попытки у всех записей, но и запись, на которой модель виснет или падает, не должна крутиться вечно.

| Вид | Признак | Что делаем |
|---|---|---|
| Недоступна | **соединения не было**: отказ в соединении, нет имени, 502/503/504, 503 «модель загружается» | возвращаем в `pending`, **попытку не считаем** (`attempts - 1`), размыкаем выключатель |
| Занята | 429 от контейнера | возвращаем в `pending` через 5 с, попытку не считаем |
| Не получилось у этой записи | запрос принят, а ответа нет или он плохой: **таймаут, обрыв посреди запроса** (контейнер убит по памяти), 500, ответ без текста | `attempts` остаётся, пауза 30 с, 2 мин, 10 мин, 1 ч, 6 ч; на пятой неудаче `failed / too_many_failures` |
| Отвергнута | 400/413 (не WAV, слишком длинная) | сразу `failed / rejected`, без повторов |

**Выключатель** (на сбой «недоступна»): воркер перестаёт брать задачи на 15 с, затем 30, 60, … до 5 минут, и пишет в журнал один раз за простой, а не на каждый опрос. После первого успешного ответа сбрасывается.

**Защита от запоздавшего результата:** запись результата выполняется как `UPDATE ... WHERE message_id = $1 AND state = 'running' AND attempts = $n`. Если за это время задачу отняли (истекла аренда) или запись удалили, обновлено будет 0 строк, и результат отбрасывается, а не затирает чужой.

## 7. Алгоритм воркера

```
цикл:
  ждать: сигнал от приёма | тик 2 с | завершение контекста
  если выключатель разомкнут → продолжить
  задача = Claim(now, аренда)                 // один UPDATE ... FOR UPDATE SKIP LOCKED
  если нет → продолжить
  файл = Messages.Open(<id>.opus)
      ErrNotFound: строки уже нет (удалена) → ничего не делать; строка есть → failed(file_missing)
  wav, err = audio.ToWAV(файл)                 // не удалось → skipped(not_decodable)
  результат, err = Transcriber.Transcribe(ctx с таймаутом STT_TIMEOUT, wav)
  по виду ошибки: Complete | Release(без попытки) + выключатель | Retry(пауза) | Fail
```

- **Остановка сервера** (SIGTERM при редеплое): воркер перестаёт брать задачи, текущую возвращает в `pending` сразу, новым контекстом (основной уже отменён), с возвратом попытки. Ждать конца расшифровки не нужно: сервер останавливается за 20 секунд, а расшифровка может идти дольше.
- **Два сервера на время редеплоя:** `SKIP LOCKED` и аренда не дают взять одну задачу дважды; контейнер модели дополнительно пускает один запрос за раз.
- **Удаление и вытеснение по квоте во время расшифровки:** строка пропадает каскадом, результат отбрасывается (защита выше). Лишней работы на одну запись не больше, чем длится одна расшифровка.
- **Порядок:** по времени постановки, от старых к новым. Справедливость между пользователями (чтобы один не занял очередь) не нужна, пока пользователей единицы; вернуться к ней, когда появятся чужие аккаунты (раздел 12, этап 6).
- **Задержка до результата:** опрос раз в 2 с плюс сигнал от приёма; на пустой очереди текст появляется через 1–3 секунды после записи в основном за счёт самой модели **[оценка]**.

## 8. Контейнер модели (`stt/`)

Протокол (внутренний, версия `v1`):

| Запрос | Ответ |
|---|---|
| `POST /v1/transcribe`, `Content-Type: audio/wav`, WAV 16 кГц, 16 бит, моно, `Authorization: Bearer $STT_TOKEN`, `X-Request-Id` | `200 {"text", "language", "engine", "audio_ms", "stt_ms"}` |
| (тот же, неверный звук или длиннее `MAX_AUDIO_SECONDS`) | `400 {"code": "bad_audio"}` или `413 {"code": "too_long"}` |
| (во время расшифровки другой записи) | `429 {"code": "busy"}` и `Retry-After` |
| (пока грузится модель) | `503 {"code": "loading"}` |
| `GET /healthz` | `200` только когда модель загружена (для проверки Coolify) |

Устройство: Python 3.12, **только стандартная библиотека для HTTP** (`ThreadingHTTPServer`), `onnx-asr` версии как в стенде (`0.12.0`), модель в образе (`HF_HUB_OFFLINE=1`), блокировка на один запрос (`acquire(blocking=False)` → 429), WAV разбирает модуль `wave`. Не пишет в журнал ни звук, ни текст, только идентификатор запроса, длительности и код. Работает не от root, корневая файловая система только для чтения, `/tmp` в памяти.

Ресурсы: память 3 ГБ без подкачки (`memory` равен `memory-swap`), процессор 1–2 ядра. Предел длины `MAX_AUDIO_SECONDS` (65) контейнер проверяет сам, как вторую линию защиты; первую ставит Go-сервер (`STT_MAX_AUDIO_SECONDS`, по `duration_ms` записи). Память проверена только до 60 секунд, дальше этого предела не поднимать без нового замера. При урезании записи до 30 с оба предела понижаются вместе с продуктовым.

**[проверено]** `onnx-asr` 0.12.0 принимает массив `float32` прямо из памяти, поэтому временный файл не нужен: контейнер разбирает WAV модулем `wave`, проверяет частоту (16 кГц), число каналов (1) и разрядность (16 бит) и передаёт массив модели. Проверено на собранном образе (этап 1, `stt/smoke.sh`): 21 запись по 2 круга через настоящий протокол, все 21 текст совпали с результатами стенда, который читает файлы.

## 9. Go: код

Новый пакет `backend/internal/transcribe`:

```go
type Transcriber interface {
    Transcribe(ctx context.Context, wav []byte) (Result, error)
}
type Result struct {
    Text, Language, Engine string
    AudioMs, SttMs         int
}
// Ошибка несёт вид, по которому воркер решает, что делать (раздел 6).
type Error struct{ Kind Kind; Err error }
type Kind int // Unavailable, Busy, Failed, Rejected
```

| Файл | Что |
|---|---|
| `transcriber.go` | интерфейс, `Result`, `Error` и разбор вида ошибки |

Нет поля у записи, которой не было в очереди. **Отступление от первой редакции плана:** при выключенной расшифровке уже готовые тексты и состояния остаются видны (они принадлежат человеку), а не прячутся. Добавление поля совместимо со старыми клиентами |

## 11. Развёртывание и эксплуатация

- **Второй образ.** Каталог `stt/` в корне репозитория (вне `backend/`, чтобы его правки не пересобирали сервер). Образ `ghcr.io/artursharafutdinov/pigeondrop-stt`, собирается в GitHub Actions, как основной (модель около 640 МБ запечена внутрь, образ около 1,6 ГБ; скачивание модели при сборке кэшируется слоем).
- **Второе приложение в Coolify** (тип Docker Image), лимиты: память 3g, `memory and swap` 3g, процессор 1–2, публичного домена нет. Токен `STT_TOKEN` вы задаёте в обоих приложениях сами (я токены не прошу).
- **Деплой в CI.** `backend-changed.sh` сейчас жёстко проверяет `backend` и `.github/scripts`, а задача деплоя одна. Нужно обобщить: параметры «какие пути», «какой образ», «какой UUID приложения» (второй секрет, `COOLIFY_STT_APP_UUID`) и вторая задача `deploy-stt` с собственной меткой `:deployed`. Тесты этих скриптов (`.github/scripts/test`) расширяются.
- **Включение.** Сначала выкатывается контейнер модели, затем сервер с `STT_URL`. Пока `STT_URL` пуст, ничего не меняется для пользователей. Отключение расшифровки это очистка `STT_URL` (задачи остаются в таблице, ничего не теряется).
- **Резервные копии.** Тексты попадают в дамп базы (`tools/backup`) без изменений. Как и записи, они остаются в копиях до 12 месяцев после удаления. Для публикации это нужно описать в политике конфиденциальности (флаг уже стоит в `tools/backup/README.md`).
- **Нагрузка на общий VPS.** Контейнер модели ограничен по процессору и памяти; дамп БД в 03:15 и снимок Backrest в 03:20–03:30 UTC идут в том же окне и могут замедлить расшифровку, не ломая её (повторы, таймаут 90 с).
- **Наблюдение.** `stt status`; предупреждение в журнале, когда самая старая ожидающая задача старше 15 минут. Автоматический сигнал (Healthchecks) позже.
- **Лицензия.** Parakeet распространяется под CC-BY-4.0: нужно указать авторство в документации продукта (этап 4).

## 13. Тесты (ядро надёжности)

Тесты очереди идут на настоящем PostgreSQL (как остальные, `testdb`) с подменным `Transcriber` и подменными часами.

| Сценарий | Ожидание |
|---|---|
| Новая запись | одна строка `pending` в той же транзакции; откат приёма откатывает и задачу |
| Повторная отправка той же записи | второй задачи нет |
| Недекодируемая запись | `skipped / not_decodable`, модель не вызывается |
| Модель недоступна на старте и час после | ни одна попытка не сгорела, после восстановления записи расшифрованы по порядку |
| Модель ответила 500 пять раз подряд | паузы 30 с … 6 ч, затем `failed / too_many_failures` |
| Модель ответила 400 | сразу `failed / rejected`, без повторов |
| 429 «занята» | возврат без потери попытки, повтор через 5 с |
| Таймаут модели или обрыв посреди запроса | попытка горит; запись, на которой модель виснет или падает, после пяти попыток `failed`, а не крутится вечно |
| Отказ в соединении | попытка не горит |
| Запись длиннее `STT_MAX_AUDIO_SECONDS` | `skipped / too_long`, модель не вызывается |
| Сервер упал посреди расшифровки | после истечения аренды задачу берёт следующий запуск |
| Два воркера одновременно | каждую задачу берёт ровно один (`SKIP LOCKED`), без дублей результата |
| Запоздавший результат | после потери аренды запись результата не меняет строку |
| Запись удалена во время расшифровки | результат отброшен, ошибок и «висящих» строк нет |
| Вытеснение по квоте во время расшифровки | то же |
| Файл пропал при живой строке | `failed / file_missing` |
| SIGTERM | текущая задача сразу `pending`, попытка возвращена |
| Тишина | `done` с пустым текстом |
| Текст с NUL и управляющими символами | очищен, запись проходит |
| Очень длинный текст | обрезан по пределу |
| Пачка из 1 000 задач | обрабатывается по одной, по порядку, без роста памяти сервера |
| Выключено (`STT_URL` пуст) | ни задач, ни обращений к сети |

Проверка мутациями, как у резервных копий: ломать по одной защите (аренду, проверку `attempts`, различение недоступности и сбоя, транзакционную постановку) и убеждаться, что тест это ловит.

## 14. Риски и открытые вопросы

| Риск | Что делаем |
|---|---|
| **Память VPS.** Контейнеру нужно 3 ГБ, а в среднем свободно около 5 ГБ, в пик неизвестно | Лимит 3 ГБ решён; шаг 0 (`tools/stt-vps-check/`) меряет доступную память машины в пик и не даёт проверке отнять память у соседей; если выйдет мало, вы упоминали возможность докупить 4 ГБ |
| **Сеть между приложениями Coolify** | Шаг 0; запасной вариант: оба ресурса в одной сети назначения или один compose-ресурс |
| **Скорость на VPS хуже, чем на Mac** | Таймаут 90 с рассчитан с запасом на минутную запись при замедлении в 3–5 раз; шаг 0 проверяет |
| **Python-сервис** | Второй язык в репозитории (стенд замеров уже на нём); сервис небольшой, без фреймворков, под тестами |
| **Качество** | Ошибки на шёпоте, в шуме и на английских именах (`STT_COMPARISON.md`, 7.3); поэтому пометка на странице и сохранение `engine` в каждой строке, чтобы смену модели можно было объяснить |
| **Тексты как персональные данные** | Удаляются каскадом с записью и при удалении аккаунта; попадают в архив, если решим положить `.txt`; остаются в копиях до года |
| **Предел записи станет 30 с** | пределы длины и потолок памяти уменьшатся; проект от этого не меняется (замер 30 с идёт) |
| **Запись длиннее 60 с (модифицированный клиент)** | Сервер принимает до 512 КиБ; такие записи пропускаются (`too_long`), память модели не рискует |
| **Рост до нескольких пользователей** | FIFO без справедливости; этап 6 |
| **Недоступность модели надолго** | Очередь копится в таблице, ограничена квотой аккаунтов (вытесненные записи уходят и из очереди); пользователь видит «ожидает», загрузка с часов не страдает |
