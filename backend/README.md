# Backend (Go)

Сервер PigeonDrop на Go: принимает записи с часов, хранит их, конвертирует и (позже) запускает цепочки. Заменил Node-прототип, который лежал в `server/` (удалён 2026-10-04, остался в истории git). Выбор стека: [`STACK_COMPARISON.md`](../STACK_COMPARISON.md), набор B.

**Состояние:** приём записей с часов (`POST /v1/messages`: Ogg/Opus и прежний формат Zepp, идемпотентность в пределах устройства, пределы и автоудаление самых старых записей), регистрация по коду приглашения, вход по почте и паролю, сессии в cookie, смена пароля (`/v1`, см. ниже). Часы привязываются к аккаунту и отправляют записи со своим токеном; человек видит и слушает только свои записи на странице `/pair`. Дальше: цепочки (очередь, Telegram), «свой сервер».

## Быстрый старт

Нужны Go 1.26+ и серверные программы PostgreSQL (`brew install postgresql@16`). Сервер требует PostgreSQL 13 или новее (`gen_random_uuid()`); на VPS стоит 17, в CI тесты идут против 17, локально достаточно 16.

```bash
cd backend
scripts/dev-db.sh up        # своя временная PostgreSQL на 127.0.0.1:55432, данные в .dev/ (чужие базы не трогает)
make test                   # тесты; базу берут из TEST_DATABASE_URL, по умолчанию из dev-db.sh
make run                    # сервер на :3000, миграции применяются при старте
curl localhost:3000/healthz
scripts/dev-db.sh down      # остановить
```

Тесты сами создают отдельную базу со случайным именем и удаляют её. Если базы нет, тесты пропускаются; с `REQUIRE_DB=1` (так в CI) они падают.

## Структура

| Путь | Что там |
|---|---|
| `api/openapi.yaml` | **Контракт HTTP API: источник правды.** Код под него генерируется |
| `internal/api` | Сгенерированные типы и маршруты (`make generate`); руками не править |
| `internal/httpapi` | Обработчики (`auth.go` — вход и сессии; `devices.go` — привязка часов и токены; `recordings.go` — записи с владельцем; `pair.go` с файлами `pair.*` и воспроизведение звука — маршруты для браузера, написанные вручную) и общие middleware (логи, перехват паники, JSON-ошибки, лимит тела запроса, защита от запросов с чужих сайтов) |
| `internal/auth` | То, что не требует базы и HTTP: хеш пароля Argon2id, случайные токены, коды приглашений, проверка почты и пароля, ограничитель попыток |
| `internal/audio` | Разбор Ogg/Opus и формата Zepp, декодирование Opus (чистый Go), WAV. Тестовые записи в `testdata/` синтетические; как их пересоздать, написано в `generate.mjs` |
| `internal/storage` | Хранилище файлов за интерфейсом: сейчас каталог на диске, позже, возможно, S3 |
| `internal/transcribe` | Расшифровка записей: клиент сервиса распознавания (`stt/`), очередь в PostgreSQL и воркер, который берёт записи по одной |
| `internal/config` | Настройки из переменных окружения |
| `internal/db` | Пул соединений и применение миграций; `queries/` — SQL-запросы, из которых sqlc генерирует `dbgen/` |
| `internal/testdb` | Отдельная база для каждого теста |
| `migrations/` | SQL-миграции (goose); встроены в бинарник |
| `cmd/pigeondrop` | Точка входа: `serve`, `migrate`, `healthcheck`, `version` и команды оператора `invite`, `user`, `stt` |
| `tools/` | Отдельный модуль с генераторами (oapi-codegen, sqlc, goose), чтобы не раздувать зависимости сервера |

## Команды

```bash
make generate   # после правки api/openapi.yaml или SQL-запросов в internal/db/queries
make check      # gofmt + go vet + тесты (то же, что CI)
make build      # bin/pigeondrop
```

Команды самой программы:

```bash
pigeondrop serve            # HTTP-сервер
pigeondrop migrate up       # применить миграции
pigeondrop migrate status   # состояние миграций
pigeondrop healthcheck      # код 0, если локальный сервер отвечает (для HEALTHCHECK в Docker)
pigeondrop invite create    # новый код приглашения (печатается один раз), флаги -expires 168h -note "для кого"
pigeondrop invite list      # приглашения: свободно, использовано кем, просрочено
pigeondrop invite revoke ID # отозвать неиспользованное
pigeondrop user list        # пользователи
pigeondrop user set-password EMAIL   # новый пароль (спросит дважды или прочтёт из stdin); все сессии пользователя закончатся
pigeondrop stt status                # расшифровка: очередь по состояниям, сколько ждёт самая старая, неудачи, последняя ошибка
pigeondrop stt enqueue -missing      # поставить в очередь записи, которые в неё никогда не попадали (до включения расшифровки); -max-audio 65s
pigeondrop stt retry -failed         # вернуть в очередь все записи, на которых сдались (с нуля, в конец очереди)
```

|---|---|---|
| `DATABASE_URL` | — (обязательна) | Строка подключения к PostgreSQL |
| `PORT` | `3000` | Порт HTTP-сервера |
| `STORAGE_DIR` | `./data` (в образе `/data`) | Где лежат записи; в Docker это том |
| `DEFAULT_SERVER_URL` | `http://localhost:$PORT` | Публичный адрес сервера, по нему часы отправляют записи |
| `MIGRATE_ON_START` | `false` | Применять миграции при старте (для одного экземпляра); иначе запускайте `migrate up` отдельным шагом |
| `LOG_LEVEL` | `info` | `debug`, `info`, `warn`, `error` |
| `MAX_DB_CONNS` | `10` | Размер пула: PostgreSQL на VPS общий с другими проектами |
| `COOKIE_SECURE` | `true` | Cookie сессии только по HTTPS. `false` нужен лишь для разработки по обычному http (`make run` ставит сам) |
| `ALLOWED_ORIGINS` | — | Другие сайты (`https://app.example.com`, через запятую), чьи скрипты могут обращаться к `/v1` с сессией, например dev-сервер фронтенда |
| `STORAGE_ACCOUNT_BYTES` | `104857600` (100 МиБ) | Сколько места занимают записи одного аккаунта; сверх этого самые старые удаляются. Не меньше 100000 (защита от опечатки). Малый лимит удобен, чтобы проверить предупреждение на часах; запись, которая одна больше лимита, всё равно принимается, а остальные удаляются |
| `TRUST_PROXY_HEADERS` | `false` | Брать адрес клиента из `X-Forwarded-For` (для ограничения попыток входа). Включать только за прокси, который сам ставит заголовок (Traefik в Coolify) |
| `STT_URL` | — | Адрес сервиса распознавания речи (`http://имя:8000`, без пути и пароля). **Пусто: расшифровка выключена**, записи в очередь не ставятся, воркер не запускается |
| `STT_TOKEN` | — | Общий секрет с сервисом (`Authorization: Bearer`). Без `STT_URL` задавать нельзя (это опечатка: расшифровка молча осталась бы выключенной) |
| `STT_TIMEOUT` | `90s` | Сколько ждать одного ответа сервиса, от `1s` до `10m`. Аренда записи во время работы воркера равна этому значению плюс 30 секунд |
| `STT_MAX_ATTEMPTS` | `5` | Сколько попыток, засчитываемых записи, прежде чем отказаться от неё (1–20) |
| `STT_MAX_AUDIO_SECONDS` | `65` | Самая длинная запись, которую отправляют модели. Память модели измерена до 60 секунд; длиннее принимаются и хранятся, но не расшифровываются (`too_long`) |

Если в базе есть неприменённые миграции, `serve` не стартует и говорит об этом.

Записи лежат в `STORAGE_DIR/messages`. Журнал пишется в stdout в формате JSON.

## Аккаунты и вход (`/v1`)

Описание запросов — в `api/openapi.yaml`. Здесь то, чего в нём нет: как это устроено и как этим пользоваться.

**Регистрация только по приглашению.** Оператор (вы) создаёт код командой `pigeondrop invite create` и передаёт человеку; тот регистрируется по `POST /v1/auth/register` (код, почта, пароль). Код одноразовый и по умолчанию живёт неделю. В базе лежит только его хеш: копия базы не даёт рабочих приглашений. Код тратится в одной транзакции с созданием пользователя: ошибка (почта занята, пароль слабый) его не сжигает, а если двое придут с одним кодом одновременно, аккаунт получит только один из них.

**Первый пользователь.** Приглашение нужно и ему, поэтому после первого запуска: `pigeondrop invite create` на сервере. В образе нет оболочки, и она не нужна: `docker exec <контейнер> /pigeondrop invite create` (для пароля — `docker exec -it <контейнер> /pigeondrop user set-password почта`). Терминал Coolify для этого не годится: в образе нет `sh`.

**Пароли.** Argon2id (19 МиБ, 2 прохода, 1 поток: нижняя из рекомендованных OWASP настроек, выбрана ради общего VPS), не больше четырёх хешей одновременно. Параметры хранятся внутри хеша, поэтому при их смене пароль перехешируется сам при следующем входе. Длина от 12 символов (считаются символы, а не байты) до 256 байт, перед хешированием текст приводится к NFKC, чтобы один и тот же пароль с разных клавиатур совпадал. **Чего нет:** проверки по списку известных утёкших паролей.

**Сессии.** Случайный токен (256 бит) лежит в cookie `HttpOnly; SameSite=Lax` (по HTTPS ещё `Secure` и имя с префиксом `__Host-`), в базе только его SHA-256. Сессия живёт 30 дней с последнего использования, продлевается не чаще раза в час и не дольше 90 дней со входа. Смена пароля завершает все остальные сессии пользователя. Просроченные удаляются раз в час.

**Защита от подбора.** В памяти сервера (после перезапуска счётчики обнуляются, а при нескольких экземплярах сервера у каждого свои; для одного небольшого сервера этого достаточно): 5 неудачных входов на почту за 15 минут, 20 на адрес клиента за 15 минут, 10 неверных кодов приглашения на адрес за час; после этого ответ 429 с `Retry-After`. Считаются и несуществующие почты, поэтому по ответам не узнать, кто зарегистрирован; неизвестная почта стоит серверу столько же времени, сколько неверный пароль. Адрес IPv6 считается по сети /64.

**Запросы с чужих сайтов.** Для путей `/v1` небезопасные запросы (POST и т. п.) с чужим `Origin` или `Sec-Fetch-Site: cross-site` получают 403 `forbidden_origin` (стандартная проверка `http.CrossOriginProtection`); приложения и `curl` этих заголовков не шлют и проходят.

**Ошибки** в `/v1` несут машинный код (`code`): клиент переводит их сам, текст в `error` на английском и для журнала.

**Чего пока нет:** писем (подтверждение почты, сброс пароля: сброс делает оператор командой `user set-password`), смены почты и языка, удаления аккаунта, списка и отзыва отдельных сессий, входа через сторонние сервисы.

## Часы: привязка и токены устройств (`/v1/device/*`, `/v1/devices`)

Раньше часы называли себя «кодом» (просто идентификатор, не секрет), и сервер принимал записи от кого угодно. Теперь часы доказывают, чьи они, **токеном устройства**; привязка устроена как RFC 8628 (Device Authorization Grant): устройство без удобного ввода показывает код, человек подтверждает его на телефоне.

```
часы ──(через телефон)──► POST /v1/device/code      { clientName }
                          ◄── deviceCode (секрет часов), userCode (BCDF-GHJK), verificationUriComplete, expiresIn 600, interval 5
часы показывают QR (verificationUriComplete) и userCode, опрашивают раз в 5 с:
часы ──────────────────► POST /v1/device/token      { deviceCode }  →  { status: "pending" }
человек: открывает /pair?code=..., входит, сверяет код с часами, нажимает «Привязать»
                          POST /v1/device/approve    { userCode, name }      (по cookie сессии)
часы ──────────────────► POST /v1/device/token      →  { status: "approved", deviceToken, deviceId }   (один раз)
```

- **Токен** — `pdd_` и 43 случайных символа (256 бит). В базе только SHA-256; восстановить его нельзя. Если ответ с токеном потерялся по дороге, привязку нужно начать заново, а лишнее устройство на странице можно отозвать.
- **Код для человека** — 8 согласных из 20 (по совету RFC 8628: без гласных и путаницы 0/O, 1/I), 34 бита. Это безопасно только потому, что код живёт 10 минут, а неверные догадки ограничены: 10 на пользователя за 15 минут. Подтверждение даёт ещё 2 минуты на получение токена.
- **Защита от подмены.** Ссылку на подтверждение можно сделать так, что она укажет на чужие часы; страница показывает код крупно и просит сверить его с экраном часов. Название часов приходит от самих часов и показывается только как текст.
- **Ограничения:** выдача кодов — 10 на адрес за 10 минут (каждая оставляет строку в базе), опрос с несуществующим кодом — 30 на адрес за 15 минут, опрос чаще раза в 3 секунды отклоняется (429 и `Retry-After`) и не засчитывается.
- **Отзыв:** `DELETE /v1/devices/{id}` (со страницы). Токен перестаёт работать сразу, записи устройства остаются. Просроченные привязки удаляются раз в час.
- Токен идёт заголовком `Authorization: Bearer ...` (схема `deviceAuth` в `api/openapi.yaml`). Сессия человека устройству не нужна, а токен устройства человеку не заменяет сессию.

## Записи (`/v1/messages`)

Запись принимает только устройство с токеном: `POST /v1/messages { messageId, audio }`. У каждой записи есть владелец, а идемпотентность считается **в пределах устройства** (`messageId` — имя файла на часах): у двух устройств могут быть одинаковые имена и они не пересекутся.

- Файл лежит в `STORAGE_DIR/messages` и назван по id сообщения (`<id>.opus`, как получено). Имя, которое прислал клиент, никогда не становится путём. Запись сохраняется, даже если декодировать её не удалось (`hasWav: false`: проигрывателя на странице нет, оригинал скачать можно). **WAV для браузера не хранится:** при каждом воспроизведении он делается из оригинала (минутная запись около 30 мс, одновременно не больше четырёх), поэтому на диске только то, что считается в лимит. `<id>.wav` от прежней версии, если остался, удаляется вместе с записью.
- Человек видит только своё: `GET /v1/messages` (новые сверху, постранично по `before`), `GET /v1/messages/{id}/audio` (WAV по умолчанию или `?format=original`; с диапазонами, чтобы плеер перематывал), `GET /v1/messages/archive` (все записи человека одним zip, см. ниже), `DELETE /v1/messages/{id}` (строка и файлы). Проверка владельца сидит в самом SQL-запросе, а не в обработчике, поэтому забыть её нельзя; чужая запись для всех запросов — «не найдено».
- **Архив всех записей.** `GET /v1/messages/archive` отдаёт zip с оригиналами всех записей человека (`.opus` ровно в том виде, как получены), без сжатия (звук уже сжат), стандартной библиотекой `archive/zip`; **рядом с записью, у которой готов непустой текст, лежит `.txt` с тем же именем** (UTF-8, текст и перевод строки; сжимается, в отличие от звука; тишина, ожидание и неудача файла не получают); пишется потоком, файл за файлом, поэтому в памяти целиком не лежит. Файлы названы по времени получения (`PigeonDrop-2026-10-08_12-30-15.opus`, UTC, как и при скачивании одной записи; записи одной секунды получают `_2`, `_3`), сам архив по времени запроса (`PigeonDrop-<дата>_<время>.zip`). Старые записи идут первыми. Записей нет: `404 not_found`. Файл, который пропал между чтением списка и упаковкой, пропускается с предупреждением в журнале; ошибка чтения посреди потока обрывает архив без оглавления, и распаковщики видят, что он неполный. Максимум архива — лимит аккаунта (100 МиБ), поэтому срок записи ответа продлевается по 2 минуты на каждый файл, а не один раз на весь ответ. Прохождение больших архивов по медленной связи не проверялось.
- **Лимиты загрузки.** Запись не больше 512 КиБ (минута звука около 140 КиБ): больше, `413` с кодом `payload_too_large`; тело запроса ограничено так же (около 770 КБ вместо общих 8 МиБ). С одного устройства не больше 60 загрузок в час (считается каждый запрос, повторы тоже): сверх, `429` и `Retry-After`. Это защита от зациклившихся часов и украденного токена; без неё автоудаление ниже дало бы им вытеснить настоящие записи мусором. Счётчик в памяти процесса, как у остальных ограничителей.
- **Хранилище аккаунта: 100 МиБ**, меняется переменной `STORAGE_ACCOUNT_BYTES`. Считаются только файлы оригиналов (сумма `bytes_received`, считается в базе, а не хранится счётчиком). Новая запись принимается всегда: если она не помещается, самые старые записи аккаунта удаляются (строка и файл) ровно настолько, чтобы она поместилась. Всё это (вставка, удаление старых, подсчёт) происходит в одной транзакции под блокировкой строки пользователя, поэтому параллельные загрузки с нескольких часов не превысят лимит; файлы удалённых строк стираются после фиксации (при сбое между этим остаются лишние файлы, но не строки без файлов). Ответ на загрузку несёт `storage` (`ok`, `nearly_full` от 90%, `full`, если пришлось удалять) и `pruned`; по нему часы предупреждают человека. Сервер сам не может написать на часы. Человек освобождает место сам: удаляет записи по одной или кнопкой «Удалить все записи» (`DELETE /v1/messages`), использование видно на странице и в `GET /v1/storage`.
- Маршруты Node-прототипа без `/v1` (`/messages`, `/accounts`, `/setup`, `/uploads`) удалены 2026-10-04. Таблицы `accounts` и `processed_uploads` в схеме остались: код их не использует, а удаление данных необратимо, поэтому их уберёт отдельная миграция, когда владелец проверит, что в них пусто.

## Расшифровка записей (очередь)

Включается переменной `STT_URL`. Устройство и проект целиком: [`../STT_SERVICE_PLAN.md`](../STT_SERVICE_PLAN.md); сам сервис: [`../stt/README.md`](../stt/README.md).

- **Постановка.** Новая запись получает строку в `transcriptions` в той же транзакции, что и строка `messages`: записи нельзя принять без места в очереди, а при откате загрузки не остаётся ни записи, ни файла, ни места в очереди (часы повторят). Повтор той же отправки второй строки не создаёт. Запись, которая не декодируется или длиннее `STT_MAX_AUDIO_SECONDS`, получает состояние `skipped` с причиной и модели не отправляется. Строка уходит вместе с записью (удаление человеком, вытеснение по квоте, удаление аккаунта): текст нигде не переживает свою запись.
- **Воркер.** Одна горутина рядом с HTTP-сервером берёт самую старую готовую запись (`FOR UPDATE SKIP LOCKED`, поэтому два сервера на время редеплоя не возьмут одну и ту же), раскодирует оригинал в WAV (`audio.ToWAV`) и отправляет сервису. Новая запись будит воркер сразу, иначе он проверяет очередь раз в 2 секунды. Загрузка с часов расшифровку не ждёт.
- **Состояния** (`transcriptions.state`): `pending` (ждёт, не раньше `run_after`), `running` (взята воркером, пока не истекла аренда `locked_until`), `done` (текст есть, он может быть пустым: тишина), `failed` и `skipped` (причина в `error_code`: `not_decodable`, `too_long`, `rejected`, `too_many_failures`, `file_missing`).
- **Сбои различаются по тому, чья вина** (`internal/transcribe/client.go`): сервис недоступен (запрос не дошёл до конца, 502/503/504, неверный токен или адрес) и «занят» (429) попытку **не засчитывают**, а недоступность ещё и останавливает воркера на 15 секунд, 30, 1 минуту … до 5 минут (простой сервиса не сжигает попытки у всей очереди); таймаут, обрыв после отправки и 500 попытку **засчитывают** (запись, на которой модель виснет или падает, не должна повторяться вечно), паузы 30 секунд, 2 минуты, 10 минут, 1 час, 6 часов, затем `failed`; отказ сервиса принять запись (400, 413) сразу `failed`.
- **Надёжность.** Если воркер умер, аренда истекает, и запись берут снова (попытка засчитана; если так случилось больше раз, чем разрешено, запись объявляется `failed`, не доходя до модели). Результат записывается только если запись всё ещё принадлежит этой попытке: опоздавший результат после смены владельца или удаления записи отбрасывается. При остановке сервера (SIGTERM) воркер сразу возвращает запись в очередь вместе с попыткой.
- **Журнал.** По записи: идентификатор, номер попытки, идентификатор вызова (его же пишет сервис), длительности и число знаков. Текста записи в журнале нет.
- **Проверка на настоящих частях.** Тесты очереди идут на настоящем PostgreSQL с подменной моделью (в них проверены сбои, гонки, аренда и остановка; каждая защита проверена поломкой). Сквозной тест `internal/transcribe/e2e_test.go` пропускается без переменных и работает с запущенным сервисом `stt/` (настоящая модель): `STT_E2E_URL=http://127.0.0.1:18000 STT_E2E_TOKEN=... STT_E2E_FILE=запись.opus STT_E2E_WANT='ожидаемый текст' go test -run EndToEnd ./internal/transcribe/`.
- **Текст в API.** `GET /v1/messages` отдаёт у каждой записи необязательное поле `transcript` (`state`, и когда есть, `text`, `engine`, `language`, `finishedAt`, `errorCode`; контракт в `api/openapi.yaml`). Поля нет у записи, которой не было в очереди (принята до включения расшифровки и не добавлена командой оператора). Поле показывается и при выключенной расшифровке, пока строки в таблице есть: готовые тексты принадлежат человеку и не пропадают от того, что оператор убрал `STT_URL`. Сообщение сервиса об ошибке (`last_error`) наружу не отдаётся.
- **Повтор.** `POST /v1/messages/{id}/transcribe` возвращает `failed`-запись человека в очередь (`202` и новое состояние `pending`; попытки с нуля, в конец очереди, воркер будится). Остальным состояниям повтор ничего бы не дал, поэтому `409 conflict`: ожидает или расшифровывается, готово, `skipped` (не декодируется или слишком длинная), у записи нет строки в очереди, или расшифровка выключена на сервере (иначе запись ждала бы вечно). Чужая запись и несуществующая: `404 not_found`. Отдельного ограничения частоты нет: повторить можно только `failed`-запись, а после повтора она уже `pending`, так что второй запрос подряд получает `409`.
- **Команды оператора** (`pigeondrop stt ...`, внутри контейнера или где доступна база; воркер сервера подхватывает работу сам в течение 2 секунд): `status` (число записей по состояниям, возраст самой старой ожидающей, сколько сдались за сутки, последняя неудача с сообщением сервиса), `enqueue -missing` (старые записи без строки в очереди; по возрасту, самые старые первыми, в конец очереди; те, что не декодируются или длиннее `-max-audio`, сразу `skipped`; без флага команда ничего не делает), `retry -failed` (все `failed`; `skipped` не трогает). Если `STT_URL` в окружении команды не задан, она об этом предупреждает: возможно, сервер без него и очередь некому разбирать.
- **Страница `/pair`** показывает под записью «Ждёт расшифровки…», «Расшифровывается…», текст, «Речь не обнаружена.», «Не удалось расшифровать. Повторить» или причину пропуска; пока на странице есть ожидающие записи, она раз в 3 секунды перечитывает список (на скрытой вкладке не спрашивает, при показе спрашивает сразу). Над списком подпись об авторстве модели и о том, что текст может содержать ошибки.
- **Авторство модели.** Текст делает NVIDIA Parakeet TDT 0.6B v3 (`nvidia/parakeet-tdt-0.6b-v3`, лицензия [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/)), в виде, в каком её опубликовал istupakov для библиотеки `onnx-asr` (конвертация в ONNX, `istupakov/parakeet-tdt-0.6b-v3-onnx`, вариант int8). Мы модель не дообучали и сами не меняли. Подпись с названием, лицензией и ссылкой стоит на странице `/pair`; её нельзя убирать, пока используется модель; в будущем фронтенде и в политике конфиденциальности авторство нужно сохранить.
- **Тексты как персональные данные.** Лежат в той же базе, попадают в её резервные копии (`tools/backup`) и остаются там до года после удаления записи; удаляются каскадом вместе с записью и при удалении аккаунта; попадают в архив «Скачать всё». Это нужно описать в политике конфиденциальности до публикации.
- **Проверка.** Тесты на настоящем PostgreSQL (`internal/httpapi/transcripts_test.go`, `cmd/pigeondrop/stt_test.go`): каждое состояние в списке, чужой текст не виден никому, повтор (все допустимые и недопустимые состояния, чужие записи, без сессии и с токеном часов, чужой сайт, выключенная расшифровка), порядок очереди после повтора, архив с текстами; страница проверена в браузере на настоящем сервере и контейнере модели (повтор, ожидание и появление текста сами).

## Страница `/pair`

Три маленьких статических файла (`pair.html`, `pair.js`, `pair.css`), без сборки: вход или регистрация по приглашению, подтверждение кода с часов, список устройств с «Отозвать», список записей с плеером, текстом записи (см. раздел о расшифровке), «Скачать оригинал» и «Удалить», кнопка «Скачать всё» рядом с заголовком «Записи» (обычная ссылка на архив, браузер сам скачивает; скрыта, пока записей нет), сколько места занято (с предупреждением от 90%) и «Удалить все записи». Это временная замена настоящему фронтенду; текст только по-русски. Политика безопасности страницы строгая (`default-src 'none'`, свои скрипт и стиль, никаких встроенных), поэтому в разметке нельзя ни встроенных обработчиков, ни `style=`: тест это проверяет. Всё, что приходит от сервера или часов, выводится как текст, а не как разметка.

**Чего пока нет:** разных квот для разных тарифов (лимит один на всех: 100 МиБ), защиты ещё не доставленных записей от автоудаления (когда появятся цепочки, придётся решить, нужна ли она), удаления файлов при удалении пользователя (самого удаления пользователей тоже пока нет), переименования устройства, тихого обновления токена.

## Правила работы

- Код и комментарии в нём — на английском, документы — на русском.
- Контракт меняем **сначала в `api/openapi.yaml`**, затем `make generate`, затем код. То же с SQL: запрос пишем в `internal/db/queries`, код получаем от sqlc. CI проверяет, что сгенерированное совпадает с закоммиченным.
- Вход считаем недоверенным: каждая длина проверяется, неразобранное — ошибка, а не паника (для разборщиков есть fuzz-тесты: `go test -run '^$' -fuzz FuzzPackets ./internal/audio`).
- Миграции только вперёд и только новыми файлами; уже применённые не правим.
- Изменения идут через ветки и pull request-ы.
