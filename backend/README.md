# Backend (Go)

Сервер PigeonDrop на Go: принимает записи с часов, хранит их, конвертирует и (позже) запускает цепочки. Заменяет Node-прототип из `server/`. Выбор стека: [`STACK_COMPARISON.md`](../STACK_COMPARISON.md), набор B.

**Состояние:** сервер полностью повторяет контракт Node-прототипа (`API_SPEC.md`): приём записей `POST /messages` (Ogg/Opus и прежний формат Zepp, WAV, идемпотентность), аккаунты по коду, страница настройки, список и скачивание записей. Это проверено теми же HTTP-тестами, что и прототип (`server/test`, задача `backend-contract` в CI). Сверх контракта прототипа есть люди: регистрация по коду приглашения, вход по почте и паролю, сессии в cookie, смена пароля (`/v1`, см. ниже). Дальше: токены устройств, цепочки.

## Быстрый старт

Нужны Go 1.26+ и серверные программы PostgreSQL (`brew install postgresql@16`).

```bash
cd backend
scripts/dev-db.sh up        # своя временная PostgreSQL на 127.0.0.1:55432, данные в .dev/ (чужие базы не трогает)
make test                   # тесты; базу берут из TEST_DATABASE_URL, по умолчанию из dev-db.sh
make run                    # сервер на :3000, миграции применяются при старте
curl localhost:3000/healthz
scripts/dev-db.sh down      # остановить
```

Тесты сами создают отдельную базу со случайным именем и удаляют её. Если базы нет, тесты пропускаются; с `REQUIRE_DB=1` (так в CI) они падают.

## Структура

| Путь | Что там |
|---|---|
| `api/openapi.yaml` | **Контракт HTTP API: источник правды.** Код под него генерируется |
| `internal/api` | Сгенерированные типы и маршруты (`make generate`); руками не править |
| `internal/httpapi` | Обработчики (`messages.go`, `accounts.go`, `auth.go` — вход и сессии, а `uploads.go` — маршруты для браузера, написанные вручную) и общие middleware (логи, перехват паники, JSON-ошибки, лимит тела запроса, защита от запросов с чужих сайтов) |
| `internal/auth` | То, что не требует базы и HTTP: хеш пароля Argon2id, случайные токены, коды приглашений, проверка почты и пароля, ограничитель попыток |
| `internal/audio` | Разбор Ogg/Opus и формата Zepp, декодирование Opus (чистый Go), WAV. Тестовые записи в `testdata/` синтетические; как их пересоздать, написано в `generate.mjs` |
| `internal/storage` | Хранилище файлов за интерфейсом: сейчас каталог на диске, позже, возможно, S3 |
| `internal/config` | Настройки из переменных окружения |
| `internal/db` | Пул соединений и применение миграций; `queries/` — SQL-запросы, из которых sqlc генерирует `dbgen/` |
| `internal/testdb` | Отдельная база для каждого теста |
| `migrations/` | SQL-миграции (goose); встроены в бинарник |
| `cmd/pigeondrop` | Точка входа: `serve`, `migrate`, `healthcheck`, `version` и команды оператора `invite`, `user` |
| `tools/` | Отдельный модуль с генераторами (oapi-codegen, sqlc, goose), чтобы не раздувать зависимости сервера |

## Команды

```bash
make generate   # после правки api/openapi.yaml или SQL-запросов в internal/db/queries
make check      # gofmt + go vet + тесты (то же, что CI)
make build      # bin/pigeondrop
```

Команды самой программы:

```bash
pigeondrop serve            # HTTP-сервер
pigeondrop migrate up       # применить миграции
pigeondrop migrate status   # состояние миграций
pigeondrop healthcheck      # код 0, если локальный сервер отвечает (для HEALTHCHECK в Docker)
pigeondrop invite create    # новый код приглашения (печатается один раз), флаги -expires 168h -note "для кого"
pigeondrop invite list      # приглашения: свободно, использовано кем, просрочено
pigeondrop invite revoke ID # отозвать неиспользованное
pigeondrop user list        # пользователи
pigeondrop user set-password EMAIL   # новый пароль (спросит дважды или прочтёт из stdin); все сессии пользователя закончатся
```

## Настройки (переменные окружения)

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `DATABASE_URL` | — (обязательна) | Строка подключения к PostgreSQL |
| `PORT` | `3000` | Порт HTTP-сервера |
| `STORAGE_DIR` | `./data` (в образе `/data`) | Где лежат записи; в Docker это том |
| `DEFAULT_SERVER_URL` | `http://localhost:$PORT` | Публичный адрес сервера, по нему часы отправляют записи |
| `MIGRATE_ON_START` | `false` | Применять миграции при старте (для одного экземпляра); иначе запускайте `migrate up` отдельным шагом |
| `LOG_LEVEL` | `info` | `debug`, `info`, `warn`, `error` |
| `MAX_DB_CONNS` | `10` | Размер пула: PostgreSQL на VPS общий с другими проектами |
| `COOKIE_SECURE` | `true` | Cookie сессии только по HTTPS. `false` нужен лишь для разработки по обычному http (`make run` ставит сам) |
| `ALLOWED_ORIGINS` | — | Другие сайты (`https://app.example.com`, через запятую), чьи скрипты могут обращаться к `/v1` с сессией, например dev-сервер фронтенда |
| `TRUST_PROXY_HEADERS` | `false` | Брать адрес клиента из `X-Forwarded-For` (для ограничения попыток входа). Включать только за прокси, который сам ставит заголовок (Traefik в Coolify) |

Если в базе есть неприменённые миграции, `serve` не стартует и говорит об этом.

Записи лежат в `STORAGE_DIR/uploads` (как у Node-прототипа, поэтому его том подходит без переноса). Журнал пишется в stdout в формате JSON.

## Аккаунты и вход (`/v1`)

Описание запросов — в `api/openapi.yaml`. Здесь то, чего в нём нет: как это устроено и как этим пользоваться.

**Регистрация только по приглашению.** Оператор (вы) создаёт код командой `pigeondrop invite create` и передаёт человеку; тот регистрируется по `POST /v1/auth/register` (код, почта, пароль). Код одноразовый и по умолчанию живёт неделю. В базе лежит только его хеш: копия базы не даёт рабочих приглашений. Код тратится в одной транзакции с созданием пользователя: ошибка (почта занята, пароль слабый) его не сжигает, а если двое придут с одним кодом одновременно, аккаунт получит только один из них.

**Первый пользователь.** Приглашение нужно и ему, поэтому после первого запуска: `pigeondrop invite create` на сервере. В образе нет оболочки, и она не нужна: `docker exec <контейнер> /pigeondrop invite create` (для пароля — `docker exec -it <контейнер> /pigeondrop user set-password почта`). Терминал Coolify для этого не годится: в образе нет `sh`.

**Пароли.** Argon2id (19 МиБ, 2 прохода, 1 поток: нижняя из рекомендованных OWASP настроек, выбрана ради общего VPS), не больше четырёх хешей одновременно. Параметры хранятся внутри хеша, поэтому при их смене пароль перехешируется сам при следующем входе. Длина от 12 символов (считаются символы, а не байты) до 256 байт, перед хешированием текст приводится к NFKC, чтобы один и тот же пароль с разных клавиатур совпадал. **Чего нет:** проверки по списку известных утёкших паролей.

**Сессии.** Случайный токен (256 бит) лежит в cookie `HttpOnly; SameSite=Lax` (по HTTPS ещё `Secure` и имя с префиксом `__Host-`), в базе только его SHA-256. Сессия живёт 30 дней с последнего использования, продлевается не чаще раза в час и не дольше 90 дней со входа. Смена пароля завершает все остальные сессии пользователя. Просроченные удаляются раз в час.

**Защита от подбора.** В памяти сервера (после перезапуска счётчики обнуляются, а при нескольких экземплярах сервера у каждого свои; для одного небольшого сервера этого достаточно): 5 неудачных входов на почту за 15 минут, 20 на адрес клиента за 15 минут, 10 неверных кодов приглашения на адрес за час; после этого ответ 429 с `Retry-After`. Считаются и несуществующие почты, поэтому по ответам не узнать, кто зарегистрирован; неизвестная почта стоит серверу столько же времени, сколько неверный пароль. Адрес IPv6 считается по сети /64.

**Запросы с чужих сайтов.** Для путей `/v1` небезопасные запросы (POST и т. п.) с чужим `Origin` или `Sec-Fetch-Site: cross-site` получают 403 `forbidden_origin` (стандартная проверка `http.CrossOriginProtection`); приложения и `curl` этих заголовков не шлют и проходят. Старые маршруты (`/messages`, `/accounts`) проверке не подчиняются: их зовёт телефон, и контракт не меняется.

**Ошибки** в `/v1` несут машинный код (`code`): клиент переводит их сам, текст в `error` на английском и для журнала. У старых маршрутов ответы прежние.

**Чего пока нет:** писем (подтверждение почты, сброс пароля: сброс делает оператор командой `user set-password`), смены почты и языка, удаления аккаунта, списка и отзыва отдельных сессий, входа через сторонние сервисы.

## Правила работы

- Код и комментарии в нём — на английском, документы — на русском.
- Контракт меняем **сначала в `api/openapi.yaml`**, затем `make generate`, затем код. То же с SQL: запрос пишем в `internal/db/queries`, код получаем от sqlc. CI проверяет, что сгенерированное совпадает с закоммиченным.
- Вход считаем недоверенным: каждая длина проверяется, неразобранное — ошибка, а не паника (для разборщиков есть fuzz-тесты: `go test -run '^$' -fuzz FuzzPackets ./internal/audio`).
- Миграции только вперёд и только новыми файлами; уже применённые не правим.
- Изменения идут через ветки и pull request-ы.

## Docker

```bash
docker build -t pigeondrop-backend backend
```

Образ собирается в один статический бинарник, работает не от root; состояние (`STORAGE_DIR=/data`) нужно хранить на томе.
