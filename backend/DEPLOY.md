# Деплой Go-сервера на VPS через Coolify и CI/CD

Сервер из `backend/` собирается в Docker-образ **в GitHub Actions**, образ кладётся в реестр GitHub (GHCR), а Coolify на вашем VPS только скачивает готовый образ и запускает его. Так сборка Go не нагружает общий VPS. Приложение для часов так не выкладывается: оно публикуется через Zepp. Node-прототип из `server/` не выкладывается совсем.

## Как это работает

```
git push в main (затрагивает backend/ или .github/scripts/)
   └─ GitHub Actions (.github/workflows/ci.yml)
        ├─ backend, backend-contract, deploy-script — проверки
        └─ deploy — только если проверки прошли
             1. собирает backend/Dockerfile и кладёт образ в GHCR:
                ghcr.io/artursharafutdinov/pigeondrop-backend:<коммит> и :latest
             2. просит Coolify выкатить приложение и ждёт результата;
                Coolify скачивает :latest и перезапускает контейнер
```

- Пуш, который не трогает `backend/`, образ не пересобирает и сервер не перезапускает. Ручной запуск («Run workflow») выкатывает всегда.
- Образ складывается в GHCR **даже если секретов Coolify ещё нет**: задача пишет предупреждение и завершается успешно. Поэтому первый образ появляется сам, ещё до того, как приложение создано в Coolify.
- Деплой **считается неудачным**, если Coolify сообщил о провале: задача в GitHub станет красной.
- Тег с коммитом нужен для отката и чтобы знать, что запущено: `pigeondrop version` печатает этот коммит.

## Настройка один раз

### 1. Образ появляется в GHCR

Влейте PR с этим конвейером в `main`: изменение в `.github/scripts/` запустит задачу `deploy`, она соберёт образ и положит его в GHCR (Coolify-секретов ещё нет, это нормально). Проверка: на странице репозитория справа **Packages** появится `pigeondrop-backend`. Пакет остаётся **приватным**, оставьте его таким.

Если образ не появился, запустите вручную: **Actions → CI/CD → Run workflow**.

### 2. VPS: доступ на чтение образа

Приватный образ Coolify скачивает с учётными данными Docker самого сервера. Один раз по SSH:

1. На GitHub: **Settings → Developer settings → Personal access tokens → Tokens (classic) → Generate new token**, единственное право **`read:packages`**. Токен показывается один раз; в чат его не присылайте.
2. На VPS: `docker login ghcr.io -u ArturSharafutdinov` и вставьте токен в ответ на запрос пароля.

### 3. PostgreSQL: отдельная база и роль

У вас уже есть PostgreSQL в Coolify. Заведите в нём отдельные роль и базу для PigeonDrop, чтобы сервер не имел доступа к базам других проектов.

1. В Coolify откройте этот PostgreSQL и вкладку **Terminal**, там выполните `psql -U <пользователь>` (пользователь и пароль указаны на странице базы, обычно `postgres`).
2. Придумайте пароль, например `openssl rand -hex 24`. Только буквы и цифры: пароль идёт внутри адреса, и спецсимволы пришлось бы экранировать.
3. Выполните:
   ```sql
   CREATE ROLE pigeondrop LOGIN PASSWORD '<пароль>';
   CREATE DATABASE pigeondrop OWNER pigeondrop;
   ```
   Больше ничего не нужно: серверу не требуются права суперпользователя и расширения, миграции создают только таблицы и индексы в своей базе.
4. Внутренний адрес базы: на странице PostgreSQL в Coolify есть **Postgres URL (internal)** вида `postgres://postgres:…@<имя-контейнера>:5432/postgres`. Вам нужен `<имя-контейнера>`. Из него складывается адрес для приложения:
   ```
   postgres://pigeondrop:<пароль>@<имя-контейнера>:5432/pigeondrop?sslmode=disable
   ```
   `sslmode=disable` потому, что трафик не выходит за внутреннюю сеть Docker. Приложение и база должны находиться в одной сети Docker (в Coolify по умолчанию это так, если оба на одном сервере и в одной «destination»).

### 4. Coolify: создать приложение

1. **Project → New → Resource → Docker Image** (в разделе Docker Based).
2. **Image**: `ghcr.io/artursharafutdinov/pigeondrop-backend`, **Tag**: `latest`.
3. **Ports Exposes: `3000`**. **Ports Mappings оставьте пустым**: наружу сервер должен выходить только через прокси Coolify (Traefik), потому что ниже включается доверие заголовку `X-Forwarded-For`.
4. **Domains**: `https://<ваш-поддомен>`. У DNS-провайдера нужна A-запись поддомена на IP вашего VPS. Сертификат выпустит Traefik сам.
5. **Environment Variables** (все как обычные, не «build variable»):

   | Имя | Значение |
   |---|---|
   | `DATABASE_URL` | адрес из шага 3 |
   | `DEFAULT_SERVER_URL` | `https://<ваш-поддомен>` без слеша на конце. Это публичный адрес: по нему строится ссылка в QR-коде привязки |
   | `TRUST_PROXY_HEADERS` | `true` (адрес клиента для ограничения попыток входа берётся из `X-Forwarded-For`; верно, пока наружу нет прямого порта) |
   | `MIGRATE_ON_START` | `true` (одна копия приложения; миграции применятся при старте) |

   Остальное по умолчанию: куки только по HTTPS (`COOKIE_SECURE=true`), хранилище 100 МиБ на аккаунт (`STORAGE_ACCOUNT_BYTES`), пул базы 10 соединений (`MAX_DB_CONNS`: PostgreSQL общий с другими проектами, при необходимости уменьшите). Полный список: `backend/README.md`.
6. **Persistent Storage → Add → Volume Mount**: имя `pigeondrop-data`, Destination Path `/data`. Именно **Volume**, а не Directory: контейнер работает не от root и сможет писать только в том, что Docker создал по образу. В `/data` лежат сами записи. Без тома они пропадут при первом же деплое.
7. **Resource Limits** (вкладка Configuration). Значения с единицами `b`, `k`, `m` или `g`; `0` означает «без ограничения»:

   | Поле | Значение |
   |---|---|
   | CPU limit | `1` |
   | CPU set | пусто |
   | CPU weight | `1024` (по умолчанию) |
   | Memory reservation | `128m` |
   | Memory limit | `512m` |
   | Memory and swap limit | `512m` (столько же, сколько Memory limit: контейнер не уходит в подкачку, а при нехватке памяти его перезапустят, и это не замедлит весь VPS) |
   | Swappiness | `60` (по умолчанию; без подкачки значения не имеет) |

   Откуда цифры. Измерено на настоящем контейнере: в покое сервер занимает около 30 МиБ. Под залпом из 32 одновременных входов (каждый хеш Argon2 берёт 19 МиБ) и 32 одновременных прослушиваний контейнер с лимитом 128 МиБ был убит из-за нехватки памяти. Контейнер с лимитом 256 МиБ выдержал пять таких залпов подряд и после них занимал около 50 МиБ. Для вашего использования такая нагрузка нереальна, поэтому 512 МиБ это двойной запас. Лимит только потолок: занято будет столько, сколько нужно. Один процессор с большим запасом: вход (Argon2) занимает доли секунды, перекодирование минутной записи около 30 мс.
8. **Health check в Coolify не включайте.** В образе нет `curl`, и такая проверка всегда будет считать контейнер нездоровым. Проверку задаёт сам образ (`/pigeondrop healthcheck`).
9. Запустите приложение кнопкой **Deploy** и проверьте:
   ```bash
   curl https://<ваш-поддомен>/healthz
   ```
   Ответ `{"ok":true}`. В логах приложения (Coolify, вкладка Logs) должна быть строка `migrations applied` с `count: 4`.

### 5. Coolify: токен для API

1. **Settings → Advanced → API Access** включить, если выключено.
2. **Keys & Tokens → API tokens** создать токен с правами `read` и `deploy` (больше не нужно). Токен показывается один раз.
3. UUID приложения: он в адресной строке на странице приложения (`.../application/<UUID>`).

### 6. GitHub: секреты

Репозиторий → **Settings → Secrets and variables → Actions → New repository secret**, три секрета:

| Имя | Значение |
|---|---|
| `COOLIFY_URL` | адрес вашего Coolify, например `https://coolify.example.com` |
| `COOLIFY_TOKEN` | токен из шага 5 |
| `COOLIFY_APP_UUID` | UUID приложения |

Токен храните только там и в чат не присылайте.

### 7. Первый пользователь

Регистрация только по приглашению, поэтому первое приглашение создаёт оператор на сервере. По SSH на VPS:

```bash
docker ps --filter ancestor=ghcr.io/artursharafutdinov/pigeondrop-backend:latest --format '{{.ID}}  {{.Names}}  {{.Status}}'
docker exec <ID> /pigeondrop invite create -note owner
```

Первая команда находит текущий контейнер по образу (имя меняется при каждом деплое, поэтому ID из старой записи не подойдёт); в статусе должно быть `Up … (healthy)`. В образе нет оболочки: запускайте `/pigeondrop` напрямую, а не `sh`.

Первой строкой команда печатает код, второй (в stderr) срок его действия: 7 дней. Откройте `https://<ваш-поддомен>/pair`, вкладка «Регистрация», введите код, почту и пароль не короче 12 символов. Дальше приглашения можно создавать так же; список и другие команды оператора (`invite list`, `user set-password`): `backend/README.md`.

### 8. Переключить часы на новый сервер

1. В `PigeonDrop/config.js` поставьте `SERVER_URL = 'https://<ваш-поддомен>'`.
2. `cd PigeonDrop && zeus preview`.
3. На часах: **Настройки → Привязать часы**, QR-код откройте на телефоне (теперь по HTTPS), войдите и подтвердите. Привязка к тестовому серверу на вашем Mac на новом сервере не действует: это другая база, часы привязываются заново.

## Повседневная работа

- **Выкладка** идёт сама: пуш в `main`, который трогает `backend/`, соберёт образ и перезапустит приложение. Миграции применяются при старте.
- **Откат:** в Coolify откройте приложение, поставьте **Tag** на нужный коммит (`ghcr.io/…-backend:<коммит>`, список тегов на странице пакета в GitHub) и нажмите **Deploy**. Вернуть `latest` можно тем же способом. Откат кода не откатывает миграции: прежняя версия должна работать с уже обновлённой схемой.
- **Логи:** в Coolify (вкладка Logs), одна JSON-строка на событие.
- **Одна копия.** Не запускайте две копии приложения: ограничители попыток и загрузок живут в памяти процесса, а миграции на старте рассчитаны на один процесс.
- **Резервные копии.** Записи на диске и их строки в базе связаны, поэтому копировать надо оба: том `pigeondrop-data` и базу `pigeondrop` (`pg_dump`). Подключается тем же способом, что и ваши другие проекты (Backrest).
- **Время:** контейнер работает в UTC.
- **Безопасность:** регистрация только по приглашению; пароли хранятся как Argon2id; токены часов в базе только хешами и отзываются со страницы `/pair`. Токен GitHub с `read:packages` и токен Coolify живут только на сервере и в секретах GitHub.

## Если что-то пошло не так

Три случая, которые встретились при первой настоящей выкладке.

**Coolify: `error from registry: unauthorized` при скачивании образа.** У Coolify нет рабочих учётных данных для `ghcr.io`. Скачивание идёт внутри служебного контейнера Coolify, которому передаётся `~/.docker/config.json` того пользователя, под которым Coolify подключается к серверу (**Servers → localhost → User**, обычно `root`). Проверка под этим пользователем (токены в выводе скрыты):
```bash
jq 'del(.auths[]?.auth)' ~/.docker/config.json
```
Должно быть `{ "auths": { "ghcr.io": {} } }`. Если `ghcr.io` нет, повторите `docker login ghcr.io -u ArturSharafutdinov` под этим же пользователем. Если есть `credsStore` или `credHelpers`, Docker хранит пароль в системном хранилище, а не в файле, и Coolify его не увидит. Проверьте скачивание вручную: `docker pull ghcr.io/artursharafutdinov/pigeondrop-backend:latest`. Если и оно даёт `unauthorized`, токен не классический, без `read:packages`, истёк или имя введено с опечаткой.

**Контейнер в статусе `Restarting`.** Сервер сам завершается с ошибкой при старте; причина в его логе: `docker logs --tail 30 <ID>` (или вкладка Logs в Coolify). Чаще всего:

| В логе | Причина и исправление |
|---|---|
| `configuration:` и строка вроде `DATABASE_URL is required` | Переменная не задана или названа с опечаткой, либо в значении остались `<` `>` или пробелы |
| `password authentication failed for user "pigeondrop"` | Пароль в `DATABASE_URL` не совпадает с паролем роли, либо роли нет (PostgreSQL отвечает одинаково). В терминале PostgreSQL: `\du`, затем `ALTER ROLE pigeondrop WITH LOGIN PASSWORD '…'` (или `CREATE ROLE …`) и тот же пароль в `DATABASE_URL`. Пароль только из букв и цифр, иначе адрес разберётся неверно |
| `database "pigeondrop" does not exist` | Не выполнена команда `CREATE DATABASE` из шага 3 |
| `no such host`, `connection refused`, `i/o timeout` | Неверное имя контейнера PostgreSQL в `DATABASE_URL` или приложение и база в разных сетях Docker |
| `permission denied` с путём `/data/…` | Хранилище подключено как папка хоста (Directory); нужен Volume Mount |

Проверить доступ к базе до перезапуска можно отдельным контейнером:
```bash
docker run --rm --network coolify postgres:17 psql "postgres://pigeondrop:ПАРОЛЬ@ИМЯ-КОНТЕЙНЕРА-БД:5432/pigeondrop?sslmode=disable" -c "select 1"
```

**`docker exec` отвечает «не тот контейнер» или «container is restarting».** Вы обращаетесь к старому контейнеру: при каждом деплое Coolify создаёт новый с новым именем. Найдите текущий командой из шага 7. Если он в статусе `Restarting`, смотрите предыдущий пункт.

## Что проверено, а что нет

Проверено на настоящих GitHub Actions и Coolify (2026-10-04):
- Задача `deploy` собирает образ и публикует его в GHCR (теги коммита и `latest`), затем вызывает API Coolify, ждёт результата и пишет `Deployed.`; так прошла выкладка после слияния PR с этой инструкцией.
- Coolify скачивает приватный образ (после `docker login` на сервере), приложение запускается, применяет миграции и отдаёт `/healthz` и `/pair` по HTTPS с действительным сертификатом.
- Регистрация по приглашению, привязка настоящих часов, загрузка записи и её воспроизведение в браузере.

Проверено только локально:
- Образ в Docker: не от root, на чистом томе, миграции, регистрация, привязка и загрузка, данные переживают перезапуск, проверка здоровья проходит; потолки памяти (128 МиБ убивает под залпом, 256 МиБ выдерживает).
- Скрипт `.github/scripts/coolify-deploy.sh` прогнан против имитации API Coolify во всех исходах (провал, отмена, старый Coolify с `GET`, неверный токен, зависание, нет секретов, Coolify недоступен); эти проверки идут и в CI (задача `deploy-script`).

Не проверено: откат сменой тега в Coolify, резервные копии, поведение при двух одновременных деплоях.
