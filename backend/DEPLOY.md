# Деплой Go-сервера на VPS через Coolify и CI/CD

Сервер из `backend/` собирается в Docker-образ **в GitHub Actions**, образ кладётся в реестр GitHub (GHCR), а Coolify на вашем VPS только скачивает готовый образ и запускает его. Так сборка Go не нагружает общий VPS. Приложение для часов так не выкладывается: оно публикуется через Zepp.

## Как это работает

```
git push в main (если backend/ или .github/scripts/ отличаются от выкаченного)
   └─ GitHub Actions (.github/workflows/ci.yml)
        ├─ backend, deploy-script — проверки
        └─ deploy — только если проверки прошли
             1. сравнивает коммит с тем, что выкачено (тег :deployed, см. ниже)
             2. собирает backend/Dockerfile и кладёт образ в GHCR:
                ghcr.io/artursharafutdinov/pigeondrop-backend:<коммит> и :latest
             3. просит Coolify выкатить приложение и ждёт результата;
                Coolify скачивает :latest и перезапускает контейнер
             4. когда Coolify подтвердил выкатку, ставит образу тег :deployed
```

- Нужна ли выкатка, решает сравнение с **выкаченным коммитом**, а не с предыдущим пушем (`.github/scripts/image-changed.sh`). Коммит образа лежит в его метке `org.opencontainers.image.revision`, а тег `:deployed` ставится только после того, как Coolify подтвердил выкатку. Поэтому пропущенное не теряется: если запуск отменили (два слияния подряд с разницей в секунды: GitHub оставляет из ожидающих только самый новый) или выкатка упала, следующий пуш, пусть даже с одной документацией, выкатит и это. Пуш, после которого `backend/` и `.github/scripts/` совпадают с выкаченным, образ не пересобирает и сервер не перезапускает. Не удалось выяснить, что выкачено (тега ещё нет, нет метки): выкатываем. Ручной запуск («Run workflow») выкатывает всегда.
- Образ складывается в GHCR **даже если секретов Coolify ещё нет**: задача пишет предупреждение и завершается успешно. Поэтому первый образ появляется сам, ещё до того, как приложение создано в Coolify.
- Деплой **считается неудачным**, если Coolify сообщил о провале: задача в GitHub станет красной.
- Тег с коммитом нужен для отката и чтобы знать, что запущено: `pigeondrop version` печатает этот коммит.
- Без секретов Coolify тег `:deployed` не ставится (выкатки не было), поэтому до настройки Coolify каждый пуш в `main` заново собирает образ и кладёт его в GHCR.

Рядом идёт вторая такая же цепочка (задача `deploy-stt`) для сервиса распознавания речи из `stt/`: свой образ `pigeondrop-stt`, своё приложение Coolify, свой тег `:deployed`. Её настройка: шаг 9 ниже.

## Настройка один раз

### 1. Образ появляется в GHCR

Влейте PR с этим конвейером в `main`: изменение в `.github/scripts/` запустит задачу `deploy`, она соберёт образ и положит его в GHCR (Coolify-секретов ещё нет, это нормально). Проверка: на странице репозитория справа **Packages** появится `pigeondrop-backend`. Пакет остаётся **приватным**, оставьте его таким.

Если образ не появился, запустите вручную: **Actions → CI/CD → Run workflow**.

### 2. VPS: доступ на чтение образа

Приватный образ Coolify скачивает с учётными данными Docker самого сервера. Один раз по SSH:

1. На GitHub: **Settings → Developer settings → Personal access tokens → Tokens (classic) → Generate new token**, единственное право **`read:packages`**. Токен показывается один раз; в чат его не присылайте.
2. На VPS: `docker login ghcr.io -u ArturSharafutdinov` и вставьте токен в ответ на запрос пароля.

### 3. PostgreSQL: отдельная база и роль

У вас уже есть PostgreSQL в Coolify. Заведите в нём отдельные роль и базу для PigeonDrop, чтобы сервер не имел доступа к базам других проектов.

1. В Coolify откройте этот PostgreSQL и вкладку **Terminal**, там выполните `psql -U <пользователь>` (пользователь и пароль указаны на странице базы, обычно `postgres`).
2. Придумайте пароль, например `openssl rand -hex 24`. Только буквы и цифры: пароль идёт внутри адреса, и спецсимволы пришлось бы экранировать.
3. Выполните:
   ```sql
   CREATE ROLE pigeondrop LOGIN PASSWORD '<пароль>';
   CREATE DATABASE pigeondrop OWNER pigeondrop;
   ```
   Больше ничего не нужно: серверу не требуются права суперпользователя и расширения, миграции создают только таблицы и индексы в своей базе.
4. Внутренний адрес базы: на странице PostgreSQL в Coolify есть **Postgres URL (internal)** вида `postgres://postgres:…@<имя-контейнера>:5432/postgres`. Вам нужен `<имя-контейнера>`. Из него складывается адрес для приложения:
   ```
   postgres://pigeondrop:<пароль>@<имя-контейнера>:5432/pigeondrop?sslmode=disable
   ```
   `sslmode=disable` потому, что трафик не выходит за внутреннюю сеть Docker. Приложение и база должны находиться в одной сети Docker (в Coolify по умолчанию это так, если оба на одном сервере и в одной «destination»).

### 4. Coolify: создать приложение

1. **Project → New → Resource → Docker Image** (в разделе Docker Based).
2. **Image**: `ghcr.io/artursharafutdinov/pigeondrop-backend`, **Tag**: `latest`.
3. **Ports Exposes: `3000`**. **Ports Mappings оставьте пустым**: наружу сервер должен выходить только через прокси Coolify (Traefik), потому что ниже включается доверие заголовку `X-Forwarded-For`.
4. **Domains**: `https://<ваш-поддомен>`. У DNS-провайдера нужна A-запись поддомена на IP вашего VPS. Сертификат выпустит Traefik сам.
5. **Environment Variables** (все как обычные, не «build variable»):

   | Имя | Значение |
   |---|---|
   | `DATABASE_URL` | адрес из шага 3 |
   | `DEFAULT_SERVER_URL` | `https://<ваш-поддомен>` без слеша на конце. Это публичный адрес: по нему строится ссылка в QR-коде привязки |
   | `TRUST_PROXY_HEADERS` | `true` (адрес клиента для ограничения попыток входа берётся из `X-Forwarded-For`; верно, пока наружу нет прямого порта) |
   | `MIGRATE_ON_START` | `true` (одна копия приложения; миграции применятся при старте) |

   Остальное по умолчанию: куки только по HTTPS (`COOKIE_SECURE=true`), хранилище 100 МиБ на аккаунт (`STORAGE_ACCOUNT_BYTES`), пул базы 10 соединений (`MAX_DB_CONNS`: PostgreSQL общий с другими проектами, при необходимости уменьшите). Полный список: `backend/README.md`.
6. **Persistent Storage → Add → Volume Mount**: имя `pigeondrop-data`, Destination Path `/data`. Именно **Volume**, а не Directory: контейнер работает не от root и сможет писать только в том, что Docker создал по образу. В `/data` лежат сами записи. Без тома они пропадут при первом же деплое.
7. **Resource Limits** (вкладка Configuration). Значения с единицами `b`, `k`, `m` или `g`; `0` означает «без ограничения»:

   | Поле | Значение |
   |---|---|
   | CPU limit | `1` |
   | CPU set | пусто |
   | CPU weight | `1024` (по умолчанию) |
   | Memory reservation | `128m` |
   | Memory limit | `512m` |
   | Memory and swap limit | `512m` (столько же, сколько Memory limit: контейнер не уходит в подкачку, а при нехватке памяти его перезапустят, и это не замедлит весь VPS) |
   | Swappiness | `60` (по умолчанию; без подкачки значения не имеет) |

   Откуда цифры. Измерено на настоящем контейнере: в покое сервер занимает около 30 МиБ. Под залпом из 32 одновременных входов (каждый хеш Argon2 берёт 19 МиБ) и 32 одновременных прослушиваний контейнер с лимитом 128 МиБ был убит из-за нехватки памяти. Контейнер с лимитом 256 МиБ выдержал пять таких залпов подряд и после них занимал около 50 МиБ. Для вашего использования такая нагрузка нереальна, поэтому 512 МиБ это двойной запас. Лимит только потолок: занято будет столько, сколько нужно. Один процессор с большим запасом: вход (Argon2) занимает доли секунды, перекодирование минутной записи около 30 мс.
8. **Health check в Coolify не включайте.** В образе нет `curl`, и такая проверка всегда будет считать контейнер нездоровым. Проверку задаёт сам образ (`/pigeondrop healthcheck`).
9. Запустите приложение кнопкой **Deploy** и проверьте:
   ```bash
   curl https://<ваш-поддомен>/healthz
   ```
   Ответ `{"ok":true}`. В логах приложения (Coolify, вкладка Logs) должна быть строка `migrations applied` с `count: 4`.

### 5. Coolify: токен для API

1. **Settings → Advanced → API Access** включить, если выключено.
2. **Keys & Tokens → API tokens** создать токен с правами `read` и `deploy` (больше не нужно). Токен показывается один раз.
3. UUID приложения: он в адресной строке на странице приложения (`.../application/<UUID>`).

### 6. GitHub: секреты

Репозиторий → **Settings → Secrets and variables → Actions → New repository secret**, три секрета:

| Имя | Значение |
|---|---|
| `COOLIFY_URL` | адрес вашего Coolify, например `https://coolify.example.com` |
| `COOLIFY_TOKEN` | токен из шага 5 |
| `COOLIFY_APP_UUID` | UUID приложения |

Токен храните только там и в чат не присылайте.

### 7. Первый пользователь

Регистрация только по приглашению, поэтому первое приглашение создаёт оператор на сервере. По SSH на VPS:

```bash
docker ps --filter ancestor=ghcr.io/artursharafutdinov/pigeondrop-backend:latest --format '{{.ID}}  {{.Names}}  {{.Status}}'
docker exec <ID> /pigeondrop invite create -note owner
```

Первая команда находит текущий контейнер по образу (имя меняется при каждом деплое, поэтому ID из старой записи не подойдёт); в статусе должно быть `Up … (healthy)`. В образе нет оболочки: запускайте `/pigeondrop` напрямую, а не `sh`.

Первой строкой команда печатает код, второй (в stderr) срок его действия: 7 дней. Откройте `https://<ваш-поддомен>/pair`, вкладка «Регистрация», введите код, почту и пароль не короче 12 символов. Дальше приглашения можно создавать так же; список и другие команды оператора (`invite list`, `user set-password`): `backend/README.md`.

### 8. Переключить часы на новый сервер

1. В `PigeonDrop/config.js` поставьте `SERVER_URL = 'https://<ваш-поддомен>'`.
2. `cd PigeonDrop && zeus preview`.
3. На часах: **Настройки → Привязать часы**, QR-код откройте на телефоне (теперь по HTTPS), войдите и подтвердите. Привязка к тестовому серверу на вашем Mac на новом сервере не действует: это другая база, часы привязываются заново.

### 9. Распознавание речи: второе приложение

Делается после шагов 1–8, когда сервер уже работает. Модель живёт в отдельном контейнере (`stt/`, образ `ghcr.io/artursharafutdinov/pigeondrop-stt`): серверу в его 512 МиБ она не по размеру. Сервер ходит к ней по внутренней сети Docker; наружу сервис выходить не должен. Пока `STT_URL` у сервера пуст, ничего не меняется: записи не ставятся в очередь и воркер не запускается.

Порядок важен: сначала образ и приложение, потом подключение сервера.

1. **Образ.** Слияние PR с этим конвейером запускает задачу `deploy-stt`: она соберёт образ (около 5–6 минут, модель в 640 МБ скачивается при сборке), запустит его с боевыми лимитами и положит в GHCR как `pigeondrop-stt` (приватный пакет). Секрета Coolify для него ещё нет, это нормально: шаг выкатки только предупредит. Проверка по SSH под тем пользователем, под которым Coolify подключается к серверу: `docker pull ghcr.io/artursharafutdinov/pigeondrop-stt:latest`. Токен `read:packages` из шага 2 подходит и для нового пакета; если выходит `unauthorized`, смотрите «Если что-то пошло не так».
2. **Токен сервиса.** Придумайте общий секрет двух приложений, например `openssl rand -hex 32`. Он нужен в двух местах (шаги 3 и 5); в чат его не присылайте.
3. **Coolify: создать приложение.** Тот же проект и тот же сервер, а сеть (**destination**) та же, что у приложения сервера. **New → Docker Image**:

   | Поле | Значение |
   |---|---|
   | Image / Tag | `ghcr.io/artursharafutdinov/pigeondrop-stt` / `latest` |
   | Ports Exposes | `8000`. Ports Mappings пусто |
   | **Domains** | **пусто.** Coolify может подставить сгенерированный адрес (sslip.io): сотрите его. Сервис должен быть доступен только по внутренней сети |
   | Environment Variables | `STT_TOKEN` = токен из шага 2 (обычная переменная, не «build variable»). Больше ничего: число потоков модели сервис берёт из лимита процессора |
   | Network → Network Aliases | `pigeondrop-stt`. Имя контейнера Coolify меняет при каждом деплое, а псевдоним остаётся: по нему сервер найдёт сервис. Если такого поля в вашей версии Coolify нет, напишите: придётся искать другой способ |
   | Persistent Storage | не нужно: модель внутри образа, сервис ничего не пишет на диск |
   | CPU limit | `2` (потолок, а не резерв: в простое контейнер ничего не берёт) |
   | CPU set | пусто |
   | CPU weight | `1024` |
   | Memory reservation | `1g` |
   | Memory limit | `3g` |
   | Memory and swap limit | `3g` (столько же: без подкачки) |

   Откуда цифры: измерено на вашем VPS (`STT_COMPARISON.md`, 7.7). Модель держит до 2,07 ГиБ собственной памяти и около 0,7 ГиБ кэша файлов; при 2 ГБ контейнер убивается (измерено на Mac). Два ядра: запись в минуту обрабатывается за 12 секунд (на одном ядре за 21), обычная запись за секунду-две. **Health check в Coolify не включайте.** Проверку задаёт сам образ; а включённая проверка, насколько я знаю, заставляет Coolify запускать новый контейнер до остановки старого, и на время переключения потребуется память под два контейнера (до 6 ГБ), тогда как на этом VPS доступно около 5,5 ГБ. Как именно ведёт себя ваш Coolify, я не проверяла.

   Нажмите **Deploy**. В логах приложения через 10–15 секунд появится строка `the model is loaded`.
4. **GitHub: секрет `COOLIFY_STT_APP_UUID`.** UUID берётся из адресной строки страницы приложения в Coolify (`.../application/<UUID>`); секрет добавляется там же, где остальные (шаг 6). Затем один раз запустите **Actions → CI/CD → Run workflow**: так образ получит тег `:deployed`, и дальше сервис выкатывается сам, когда меняется `stt/`. До этого каждый push в `main` пересобирает образ сервиса (минуты) и ничего не выкатывает.
5. **Подключить сервер.** В приложении сервера (не в новом) добавьте переменные: `STT_URL` = `http://pigeondrop-stt:8000` и `STT_TOKEN` = тот же токен. Остальные настройки (`STT_TIMEOUT` 90 с, `STT_MAX_ATTEMPTS` 5, `STT_MAX_AUDIO_SECONDS` 65) оставьте по умолчанию, они в `backend/README.md`. Перезапустите (Redeploy). В логах сервера появится строка `speech recognition is on`.
6. **Проверить связь.** Найдите текущий контейнер сервера, как в шаге 7, и выполните в нём:
   ```bash
   docker exec <ID> /pigeondrop stt check
   ```
   Команда отправляет сервису секунду тишины с теми же адресом и токеном, что у сервера, и пишет `ok: …` или причину. Базу она не трогает. Типичные ответы:

   | Ответ | Что значит |
   |---|---|
   | `ok: the service at … answered in …` | всё в порядке |
   | `HTTP 401` | токены в двух приложениях разные (или лишний пробел) |
   | `no such host` | псевдоним не применился или приложения в разных сетях Docker: проверьте шаг 3 и что у обоих одинаковая destination |
   | `connection refused`, `i/o timeout` | сервис не запущен или ещё грузит модель (первые 15 секунд) |
   | `HTTP 503`, `loading` | модель ещё загружается, повторите через несколько секунд |

7. **Проверить на деле.** Запишите фразу на часах. Через несколько секунд после загрузки текст появится на странице `/pair` под записью. Состояние очереди: `docker exec <ID> /pigeondrop stt status`.
8. **Старые записи (по желанию).** Записи, принятые до включения, сами не расшифровываются. Поставить их в очередь: `docker exec <ID> /pigeondrop stt enqueue -missing` (потом `stt status`: сколько осталось). Обычная запись обрабатывается за 1–2 секунды, то есть сто записей займут несколько минут.

**Отключить расшифровку:** уберите `STT_URL` у сервера и перезапустите. Новые записи не ставятся в очередь, воркер не запускается, готовые тексты остаются видны, ожидавшие остаются в таблице и продолжатся при включении. Приложение сервиса можно остановить.

**Что учесть.**
- Перезапуск сервиса безопасен: пока он недоступен, записи ждут, а попытки не сгорают (сервер делает паузы 15 секунд, 30, … до 5 минут). Записи не теряются и при перезапуске самого сервера.
- Сервис постоянно держит память модели: до 2,8 ГиБ из 3 ГБ лимита. На VPS доступно около 5,5 ГБ (при замере с 14 другими контейнерами); следите за остальными приложениями после включения.
- В окне резервных копий (03:15–03:30 UTC) расшифровка может идти медленнее, но не ломается.
- Откат образа сервиса: в приложении сервиса сменить **Tag** на `<коммит>` и нажать Deploy, как для сервера.

### 10. Telegram-бот (по желанию)

Записи привязанного аккаунта приходят в личный чат Telegram голосовым сообщением с расшифровкой в подписи. Бот работает внутри сервера (отдельного приложения в Coolify не нужно) и сам забирает сообщения у Telegram (long polling), поэтому публичный адрес ему не нужен. Нужно только, чтобы сервер мог открыть `https://api.telegram.org` (исходящий HTTPS); некоторые сети его блокируют, это проверяет шаг 3. Проект и порядок работ: [`TELEGRAM_BOT_PLAN.md`](../TELEGRAM_BOT_PLAN.md).

1. **Создать бота.** В Telegram откройте @BotFather, `/newbot`, задайте имя и username (он оканчивается на `bot`). BotFather выдаст токен: он нужен только в шаге 2, в чат и в репозиторий его не присылайте. Хорошо бы сразу выполнить `/setjoingroups` и выбрать Disable: бот работает только в личных сообщениях. Меню команд бот задаёт сам.
2. **Переменная.** В приложении сервера добавьте `TELEGRAM_BOT_TOKEN` со значением токена и перезапустите (Redeploy). В логах появятся строки `telegram bot is on` (с именем бота) и `telegram is on`. `TELEGRAM_WAIT` (сколько запись ждёт расшифровку, 3 минуты) и `TELEGRAM_TIMEOUT` (30 секунд) оставьте по умолчанию, они в `backend/README.md`.
3. **Проверить связь.** Найдите текущий контейнер сервера, как в шаге 7, и выполните в нём:
   ```bash
   docker exec <ID> /pigeondrop telegram check
   ```
   Команда спрашивает у Telegram, кто бот, и не задан ли у него webhook; базу не трогает и никому ничего не отправляет. Типичные ответы:

   | Ответ | Что значит |
   |---|---|
   | `ok: the bot @… answers` | всё в порядке |
   | `unavailable (401)`, `Unauthorized` | токен не тот (или лишний пробел, или бот удалён в BotFather) |
   | `cannot be used`, `i/o timeout`, `no such host` | сервер не достаёт до `api.telegram.org`: DNS или исходящий HTTPS закрыт |
   | `has a webhook set` | у этого бота задан webhook, и Telegram не отдаёт сообщения серверу; уберите его (метод `deleteWebhook` Bot API) или возьмите другого бота |

4. **Привязать чат.** Откройте `/pair`, войдите, в разделе «Telegram» нажмите «Привязать Telegram» и откройте ссылку в Telegram (лучше с телефона), нажмите Start. Бот ответит «Готово», а страница через несколько секунд покажет «Записи приходят в Telegram: @имя». Ссылка действует 10 минут и один раз.
5. **Проверить на деле.** Запишите фразу на часах. Через несколько секунд после загрузки (с расшифровкой около 10–20 секунд) в чате появится голосовое сообщение с текстом в подписи. Состояние очереди: `docker exec <ID> /pigeondrop telegram status` (сколько аккаунтов привязано, сколько записей ждёт, что пошло не так). Записи, принятые до привязки, не отправляются.
6. **Отключить.** Человек отключает себя на странице («Отключить») или командой `/stop` в чате. Для всех сразу: уберите `TELEGRAM_BOT_TOKEN` у сервера и перезапустите: раздела на странице нет, записи в очередь не ставятся, ожидавшие остаются в таблице и уйдут при включении (если привязка цела).

**Что учесть.**
- **Голос и текст уходят на серверы Telegram.** Человек делает это сам, привязав чат, и страница об этом говорит. В политике конфиденциальности это должно быть написано (она пока не написана).
- **Один токен, один процесс.** Два процесса с одним токеном не могут одновременно получать сообщения (Telegram отвечает 409). Пока при выкатке старый контейнер ещё жив, новый бот ждёт 15 секунд и повторяет; в журнале одно предупреждение на сбой. Привязка во время выкатки может занять лишние секунды.
- **Дубль возможен.** Если запрос к Telegram ушёл, а ответ не пришёл (обрыв, таймаут), запись повторяется по расписанию, и в чате может оказаться два одинаковых сообщения: у Telegram нет ключа идемпотентности.
- **Чат заблокировал бота.** Привязка выключается, на странице об этом сказано, записи не отправляются, пока человек не привяжет чат заново.

## Повседневная работа

- **Выкладка** идёт сама: пуш в `main`, который трогает `backend/`, соберёт образ и перезапустит приложение; то же для сервиса распознавания речи, когда меняется `stt/`. Миграции применяются при старте.
- **Откат:** в Coolify откройте приложение, поставьте **Tag** на нужный коммит (`ghcr.io/…-backend:<коммит>`, список тегов на странице пакета в GitHub) и нажмите **Deploy**. Вернуть `latest` можно тем же способом. Конвейер про ручной откат не знает: тег `:deployed` остаётся на последнем коммите, который выкатил он сам. Откат кода не откатывает миграции: прежняя версия должна работать с уже обновлённой схемой.
- **Логи:** в Coolify (вкладка Logs), одна JSON-строка на событие.
- **Одна копия.** Не запускайте две копии приложения: ограничители попыток и загрузок живут в памяти процесса, а миграции на старте рассчитаны на один процесс.
- **Резервные копии.** Записи на диске и их строки в базе связаны, поэтому копировать надо оба: том `pigeondrop-data` и базу `pigeondrop` (`pg_dump`). Это делают скрипты и план Backrest из [`tools/backup`](../tools/backup/README.md) (установка, расписание, проверка восстановления).
- **Время:** контейнер работает в UTC.
- **Безопасность:** регистрация только по приглашению; пароли хранятся как Argon2id; токены часов в базе только хешами и отзываются со страницы `/pair`. Токен GitHub с `read:packages` и токен Coolify живут только на сервере и в секретах GitHub.

## Если что-то пошло не так

Три случая, которые встретились при первой настоящей выкладке.

**Coolify: `error from registry: unauthorized` при скачивании образа.** У Coolify нет рабочих учётных данных для `ghcr.io`. Скачивание идёт внутри служебного контейнера Coolify, которому передаётся `~/.docker/config.json` того пользователя, под которым Coolify подключается к серверу (**Servers → localhost → User**, обычно `root`). Проверка под этим пользователем (токены в выводе скрыты):
```bash
jq 'del(.auths[]?.auth)' ~/.docker/config.json
```
Должно быть `{ "auths": { "ghcr.io": {} } }`. Если `ghcr.io` нет, повторите `docker login ghcr.io -u ArturSharafutdinov` под этим же пользователем. Если есть `credsStore` или `credHelpers`, Docker хранит пароль в системном хранилище, а не в файле, и Coolify его не увидит. Проверьте скачивание вручную: `docker pull ghcr.io/artursharafutdinov/pigeondrop-backend:latest`. Если и оно даёт `unauthorized`, токен не классический, без `read:packages`, истёк или имя введено с опечаткой.

**Контейнер в статусе `Restarting`.** Сервер сам завершается с ошибкой при старте; причина в его логе: `docker logs --tail 30 <ID>` (или вкладка Logs в Coolify). Чаще всего:

| В логе | Причина и исправление |
|---|---|
| `configuration:` и строка вроде `DATABASE_URL is required` | Переменная не задана или названа с опечаткой, либо в значении остались `<` `>` или пробелы |
| `password authentication failed for user "pigeondrop"` | Пароль в `DATABASE_URL` не совпадает с паролем роли, либо роли нет (PostgreSQL отвечает одинаково). В терминале PostgreSQL: `\du`, затем `ALTER ROLE pigeondrop WITH LOGIN PASSWORD '…'` (или `CREATE ROLE …`) и тот же пароль в `DATABASE_URL`. Пароль только из букв и цифр, иначе адрес разберётся неверно |
| `database "pigeondrop" does not exist` | Не выполнена команда `CREATE DATABASE` из шага 3 |
| `no such host`, `connection refused`, `i/o timeout` | Неверное имя контейнера PostgreSQL в `DATABASE_URL` или приложение и база в разных сетях Docker |
| `permission denied` с путём `/data/…` | Хранилище подключено как папка хоста (Directory); нужен Volume Mount |

Проверить доступ к базе до перезапуска можно отдельным контейнером:
```bash
docker run --rm --network coolify postgres:17 psql "postgres://pigeondrop:ПАРОЛЬ@ИМЯ-КОНТЕЙНЕРА-БД:5432/pigeondrop?sslmode=disable" -c "select 1"
```

**`docker exec` отвечает «не тот контейнер» или «container is restarting».** Вы обращаетесь к старому контейнеру: при каждом деплое Coolify создаёт новый с новым именем. Найдите текущий командой из шага 7. Если он в статусе `Restarting`, смотрите предыдущий пункт.
