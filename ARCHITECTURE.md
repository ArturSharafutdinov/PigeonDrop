# Архитектура PigeonDrop

_Обновлено: 2026-08-01, версия приложения: 0.1.0_

## 1. Что это

**PigeonDrop** — мини-программа (Mini Program) для Zepp OS 4.0, разработанная для смарт-часов **Amazfit Active 2 (Round)**. Идея простая: нажал аппаратную кнопку на часах — записал голосовое сообщение — оно само уехало на телефон и дальше на сервер.

Этот документ — обзор того, как всё устроено внутри, зачем сделаны именно такие решения, и что осталось доделать. Пишу его как «живой» документ: если архитектура заметно изменится — стоит вернуться и обновить.

**Текущий статус: рабочий прототип.** Всё, что описано ниже, реально протестировано на живом устройстве (запись → отправка → сервер → прослушивание), а не только в теории. При этом это не production-система — ограничения тоже честно перечислены (раздел 6).

## 2. Общая картина: три узла и путь одного сообщения

В системе три участника:

```
┌───────────────┐        BLE         ┌──────────────────┐      HTTP      ┌─────────────┐
│     Часы      │ ─────────────────▶ │      Телефон       │ ─────────────▶ │   Сервер    │
│  (Zepp OS)    │ ◀───────────────── │  (Side Service,    │ ◀───────────── │  (Node.js)  │
│               │   подтверждение    │  внутри Zepp App)  │                │             │
└───────────────┘                    └──────────────────┘                └─────────────┘
```

Путь одного голосового сообщения:

1. Пользователь нажимает кнопку на часах → начинается запись (`page/index.js`).
2. Повторное нажатие останавливает запись. Файл сохраняется на часах в `voice_messages/voice_<время>.opus`.
3. Часы отправляют файл на телефон по Bluetooth (BLE) через `MessageBuilder` — это единственный канал передачи (до 2026-08-01 рядом был ещё и `TransferFile`, см. раздел 4 — он удалён как бесполезный).
4. Телефон (Side Service, `app-side/index.js`) получает данные через `MessageBuilder` в виде обычного JS-объекта — и сразу отправляет их на сервер через `fetch()`, на адрес из `serverUrl` (если пользователь хоть раз синхронизировался — см. раздел 2.1 ниже) либо на бутстрап-адрес из `config.js`.
5. Сервер (`server/server.js`) сохраняет файл под именем по времени получения и сразу конвертирует его в `.wav` (`convert-to-wav.js`).
6. Телефон получает ответ от сервера и отправляет подтверждение обратно на часы — оно появляется в логе часов.

### 2.1. Настройка своего сервера (QR-код + аккаунт)

Пользователь может настроить, куда именно грузятся его записи, не пересобирая приложение — вместо хардкода `SERVER_URL` есть отдельный флоу:

1. На главном экране кнопка «Настройки» → экран `page/settings.js` с двумя кнопками: «Настройка сервера» и «Синхронизация».
2. «Настройка сервера» открывает `page/qrcode.js`: часы генерируют (или переиспользуют) уникальный код устройства, сохраняют его локально (`utils/account.js`, файл `account.json` через `@zos/fs`) и показывают QR-код, ведущий на веб-страницу (`WEB_APP_BASE_URL + '/setup?code=...'`). Параллельно отправляется запрос на регистрацию аккаунта на сервере.
3. Пользователь сканирует QR телефоном → открывается `server/public/setup.html` → выбирает «сервер по умолчанию» или вводит свой URL → сохраняет.
4. «Синхронизация» на часах запрашивает у сервера актуальный `serverUrl` для этого кода и сохраняет его локально — с этого момента новые записи грузятся именно туда.

Полный HTTP-контракт этого флоу (и `/messages`) описан в [`API_SPEC.md`](API_SPEC.md) — это источник истины для будущего переписывания бэкенда на Go, не зависящий от того, что часы вообще не знают, на чём написан сервер.

> **⚠ Важная деталь:** сервер аккаунтов и сервер по умолчанию для загрузки записей — **один и тот же адрес** (`SERVER_URL`/`DEFAULT_SERVER_URL`). Это осознанное решение: иначе была бы проблема курицы и яйца — как узнать адрес сервера аккаунтов, если сам этот адрес ещё не настроен.

## 3. Разбор по файлам и модулям

### Часы (`PigeonDrop/`)
- **`app.json`** — конфигурация мини-программы: имя, версия, разрешение на микрофон (`device:os.mic`), целевая форма экрана (круглая, 480px), список страниц.
- **`app.js`** — точка входа приложения на часах. Устанавливает одно-единственное BLE-соединение (`MessageBuilder`) на всё время жизни приложения и слушает подтверждения от телефона.
- **`page/index.js`** — главный экран. Одна физическая кнопка отвечает за два действия: клик — старт/стоп записи, долгое нажатие — воспроизвести последнюю запись. Есть кнопки перехода к списку записей и к настройкам.
- **`page/list.js`** — экран со списком всех сохранённых записей, каждая — отдельная кнопка с датой/временем, нажатие проигрывает именно её.
- **`page/settings.js`** — экран настроек: кнопки «Настройка сервера» (переход на `page/qrcode.js`) и «Синхронизация» (подтягивает актуальный `serverUrl` с сервера).
- **`page/qrcode.js`** — отдельный экран с центрированным QR-кодом (ссылка на веб-страницу настройки) и статусом регистрации аккаунта.
- **`utils/recordings.js`** — вся работа с файлами записей: как называть, как получить список (отсортированный, новые сверху), как удалять лишние сверх лимита.
- **`utils/account.js`** — код устройства (генерируется один раз, хранится в `account.json`) и текущий `serverUrl`, полученный синхронизацией.
- **`config.js`** — настраиваемые параметры: `MAX_RECORDINGS` (сейчас 5), `SERVER_URL` (бутстрап-адрес сервера/аккаунтов) и `WEB_APP_BASE_URL` (адрес веб-страницы настройки).

### Телефон (`PigeonDrop/app-side/`)
- **`app-side/index.js`** — Side Service, код, который выполняется внутри приложения Zepp на телефоне (без своего экрана). Принимает записи через `MessageBuilder` и отправляет их на сервер через `fetch()`; отдельно обрабатывает запросы регистрации аккаунта и синхронизации (`registerAccount`/`sync`) через `MessageBuilder`'s request/response-канал. Результат всегда отправляет обратно на часы.

### Общая библиотека (`PigeonDrop/shared/`)
Набор файлов (`message.js`, `message-side.js`, `event.js`, `defer.js`, `data.js`), перенесённый (не установленный через npm) из официального репозитория примеров Zepp OS. Это реализация `MessageBuilder` — канала обмена сообщениями между часами и телефоном, который сам режет большие данные на куски (BLE не умеет отправлять всё одним куском) и сам их собирает обратно на другой стороне. Помимо fire-and-forget `call()` (записи, подтверждения) есть ещё `request()`/`response()` — канал с ответом, на нём построены `registerAccount`/`sync`.

### Сервер (`server/`)
- **`server.js`** — простой HTTP-сервер на чистом Node.js (без внешних зависимостей на уровне самого сервера). Принимает `POST /messages` (загрузка записи) и `/accounts` (регистрация/чтение/обновление аккаунта), отдаёт `GET /setup` (веб-страница настройки).
- **`accounts-store.js`** — хранилище аккаунтов, один JSON-файл (`server/data/accounts.json`), без базы данных — соответствует роли `server/` как прототипа.
- **`public/setup.html`** — статическая веб-страница (без сборки, без фреймворков), открывается по QR с часов, позволяет выбрать сервер по умолчанию или свой.
- **`convert-to-wav.js`** — конвертер из внутреннего формата записи часов в обычный `.wav`, который можно открыть любым плеером.

Полный контракт всех эндпоинтов сервера — в [`API_SPEC.md`](API_SPEC.md), а не здесь: этот раздел объясняет структуру, а не байт-в-байт формат запросов/ответов.

## 4. Ключевые решения и почему это так устроено

Здесь — самое ценное: реальные проблемы, с которыми столкнулись, и как их решили. Это стоит знать перед тем, как что-то менять в этих местах.

> **Почему когда-то было две отправки одновременно (TransferFile и MessageBuilder) — и почему теперь одна**
> `TransferFile` — официальный, задокументированный способ передать файл с часов на телефон. Но выяснилось: у объекта файла на стороне телефона (Side Service) нет никакого способа прочитать его байты — только имя, путь и размер. Это подтверждено отдельным research-спайком с изучением документации и исходников. Реальная передача данных на сервер всегда шла через `MessageBuilder` — более низкоуровневый канал, где на телефон приходит настоящий читаемый буфер данных. `TransferFile` при этом какое-то время работал параллельно «на будущее» (вдруг пригодится), но раз он ничего не делал, кроме как молча копил файлы в хранилище телефона — его удалили полностью (2026-08-01).

> **Почему QR-виджет нужно явно ограничивать по размеру фона**
> `@zos/ui`'s `QRCODE`-виджет принимает не только `x/y/w/h` для самого кода, но и отдельные `bg_x/bg_y/bg_w/bg_h` для фоновой подложки. Если их не задать явно, фон рендерится намного больше самого QR и вылезает за пределы экрана, обрезаясь безелем — это не видно по типам/документации, только по факту на реальном устройстве. Оба размера (`page/qrcode.js`) теперь всегда задаются вместе, с общим центром.

> **Почему `.opus`-файл с часов нельзя открыть на компьютере напрямую**
> Записанный на часах `.opus` — это **не** стандартный Ogg/Opus контейнер, а собственный формат Zepp OS: каждый звуковой пакет идёт как `[4 байта длины][8 байт заголовка][сами данные]`, подряд, без привычных заголовков файла. Обычные плееры (и даже `ffmpeg` без танцев с бубном) такое не открывают. Пришлось написать конвертер (`convert-to-wav.js`) по официальному, но малоизвестному гайду Zepp именно на этот случай.

> **Почему плеер на часах создаётся один раз, а не при каждом воспроизведении**
> Первая версия создавала новый `Player` на каждое нажатие «воспроизвести». Со второго раза это падало с ошибкой `cannot read property 'addEventListener' of undefined` — оказалось, что железо часов позволяет держать живым только один `Player` одновременно, а предыдущий не успевал освободиться. Решение: создавать `Player` один раз и переиспользовать его для всех последующих воспроизведений.

> **Почему кнопки на экране не занимают весь экран**
> Экран часов круглый (480×480 пикселей, то есть радиус 240). Прямоугольная кнопка, придвинутая слишком близко к верхнему или нижнему краю, обрезается «безелем» — углы кнопки просто оказываются за пределами видимого круга. Это было замечено на реальном устройстве и исправлено расчётом: ширина и отступы кнопок подобраны так, чтобы все углы укладывались в безопасную зону радиусом примерно 230px.

> **Почему нельзя увидеть логи Side Service напрямую**
> Экран логов в приложении Zepp (JS App Log) показывает логи **часов**, но не логи кода, который выполняется на телефоне (Side Service). Поэтому для отладки телефон специально отправляет результат своей работы обратно на часы через `MessageBuilder` — так итог виден в логе, который точно работает.

> **Мелкая деталь: разрешение на микрофон**
> Нужное разрешение (`device:os.mic`) не удалось найти заранее ни в документации, ни в примерах — оно обнаружилось только через реальную ошибку `Permission Denied device:os.mic` при первом запуске записи на устройстве.

- ✅ Отправка записи на телефон через `MessageBuilder` (единственный канал — `TransferFile` удалён)
- ✅ Реальная загрузка записи с телефона на сервер через `fetch()`
- ✅ Сервер сохраняет файл и сразу конвертирует его в `.wav`
- ✅ Звук записи лично прослушан и подтверждён как корректный, без искажений
- ✅ Настройка своего сервера с телефона: QR-код + аккаунт + синхронизация, без пересборки часов

Всё протестировано вручную на одном реальном устройстве (Amazfit Active 2 Round). Автоматических тестов нет, production-эксплуатация не предполагалась на этом этапе.

## 6. Что дальше

### Ближайшее (закрыть пробелы в надёжности)

1. **Постоянная очередь загрузки на телефоне.** Сейчас если `fetch()` не удался (нет интернета, сервер недоступен) — запись просто теряется на этом шаге, повторной попытки нет. Техническое решение уже описано в `todo.md` (хранение очереди в `settingsStorage` в виде JSON) — здесь не дублирую, детали смотреть там.
2. **Заменить ngrok на постоянный адрес.** Текущий `SERVER_URL` — бесплатный ngrok-туннель, адрес которого меняется при каждом перезапуске.
3. **Переписать сервер на Go.** Тестовый Node-сервер не имеет авторизации, надёжного хранения данных и постоянного хостинга — только для локальной проверки. Планируется полноценный бэкенд на Go; HTTP-контракт, который он обязан воспроизвести, зафиксирован в [`API_SPEC.md`](API_SPEC.md) — часы и Side Service не должны требовать изменений при этом переезде.

### На перспективу

- Названия/теги для записей вместо просто даты и времени
- Автоматические тесты
- Настоящий multi-tenant хостинг с доп. функциями сервера по умолчанию (речь → текст, автоматизации в Telegram/WhatsApp и т.п.)
- Авторизация аккаунтов (сейчас код в `/accounts/*` — просто идентификатор, не секрет)

## 7. Дополнительно

**Короткий словарь терминов:**
- **Side Service** — код мини-программы, который выполняется на телефоне внутри приложения Zepp, без своего экрана.
- **BLE (Bluetooth Low Energy)** — протокол связи между часами и телефоном, через который идёт вся передача данных.
- **MessageBuilder** — вспомогательная библиотека (перенесённая из примеров Zepp) для обмена произвольными сообщениями между часами и телефоном по BLE, с автоматическим разбиением больших данных на части. Два канала: `call()` (fire-and-forget) и `request()`/`response()` (с ответом).
- **Аккаунт** — запись на сервере, привязанная к уникальному коду устройства (генерируется часами), хранящая выбранный пользователем `serverUrl`. Без авторизации — код не секрет, просто идентификатор.

**Где что лежит:**
```
amazfit/
├── PigeonDrop/     — сама мини-программа для часов
├── server/         — тестовый сервер на Node.js
├── todo.md         — черновик технического плана для очереди загрузки
├── API_SPEC.md     — контракт HTTP API сервера (актуален независимо от языка реализации)
└── ARCHITECTURE.md — этот документ
```

Стоит обновлять этот документ при значимых изменениях архитектуры — не после каждого коммита, а когда меняется что-то из описанного выше по существу.
