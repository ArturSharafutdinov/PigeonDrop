# Telegram-бот: проект и план реализации

_Версия 1.0 · 2026-10-11 · Статус: **проект; сделан этап 1 (клиент Bot API, настройки, `telegram check`)**, остальное не реализовано; решения владельца учтены (раздел 1)_

Как присылать новые записи в Telegram: голосовое сообщение с расшифровкой. Привязка чата к аккаунту, очередь отправки в PostgreSQL, воркер внутри сервера, страница `/pair`, настройки, порядок работ и тесты. Расшифровку делает сервис из `STT_SERVICE_PLAN.md`; здесь она только берётся из таблицы `transcriptions`.

## 1. Решения владельца и границы

Решено 2026-10-11:

1. **Один бот на весь сервис.** Бота создаёт владелец в @BotFather, токен кладёт в переменную окружения сервера (`TELEGRAM_BOT_TOKEN`), в чат и в репозиторий токен не попадает.
2. **У каждого пользователя свой чат.** На странице `/pair` кнопка «Привязать Telegram» даёт ссылку `t.me/<бот>?start=<одноразовый код>`; бот привязывает чат к аккаунту. Там же «Отключить».
3. **Одно сообщение: голосовое с расшифровкой в подписи.** Сервер ждёт текст не дольше нескольких минут (по умолчанию 3). Если текст не успел, распознавание выключено, упало или запись не пошла в модель, голосовое уходит без текста.
4. **Код живёт внутри сервера на Go** (`backend/internal/telegram`), как воркер распознавания. Новых контейнеров нет. Бот получает сообщения через long polling (`getUpdates`), публичный адрес для Telegram не нужен.

Входит в работу: клиент Bot API, привязка чата и команды бота, таблицы и очередь доставки, воркер, `/v1/telegram*` и раздел на странице, команды оператора (`pigeondrop telegram check|status`), развёртывание, тесты.

Не входит: цепочки с настройкой узлов (бот станет одним из их узлов позже), группы и каналы, несколько чатов на аккаунт, текст отдельным сообщением или правка подписи позже, настройка шаблона сообщения, старые записи (отправляются только записи, принятые после привязки), политика конфиденциальности (её текст ещё не написан, см. раздел 13).

## 2. Что известно (опора для решений)

| Факт | Статус |
|---|---|
| `sendVoice`: «.OGG file encoded with OPUS, or in .MP3 format, or in .M4A format (other formats may be sent as Audio or Document)». Загрузка через `multipart/form-data` до 50 МБ | [источник] `core.telegram.org/bots/api` (читала 2026-10-11) |
| Подпись к голосовому: 0-1024 символа; текст сообщения `sendMessage`: 1-4096 символов | [источник] там же |
| Отправка по URL для голосовых: `audio/ogg` и не больше 1 МБ; 1-20 МБ отправляются файлом. Нам не подходит, мы загружаем файл сами | [источник] «Sending files» |
| Лимиты частоты: в один чат не чаще 1 сообщения в секунду, в группе 20 в минуту, рассылка около 30 в секунду. При превышении приходит 429 | [источник] `core.telegram.org/bots/faq`; поле `retry_after` в ответе описано в `ResponseParameters` |
| Бот не может написать первым: ему нужен `chat_id`, который появляется, когда человек сам написал боту. Ссылка `t.me/<бот>?start=<код>`: код до 64 символов `A-Z a-z 0-9 _ -`, бот получает `/start <код>` | [источник] `core.telegram.org/bots/features` |
| Обновления хранятся на сервере Telegram до 24 часов; `getUpdates` и webhook взаимно исключают друг друга; второй `getUpdates` с тем же токеном вытесняет первый (ответ 409) | [источник] «Getting updates»; про 409 [вторично] |
| Токен входит в адрес запроса (`/bot<токен>/метод`). Стандартная ошибка Go печатает адрес целиком, значит ошибка сети может утащить токен в журнал | [источник] «Making requests»; следствие [оценка], проверяется тестом |
| Наши записи: стандартный Ogg/Opus, моно, в заголовке `OpusHead` указано 16 кГц, `pre-skip` 0, до 512 КиБ. Декодируются как 48 кГц моно (`ffprobe`) | [проверено] на записи `2026-10-11_07-30-17` |
| Пузырёк с волной получится ли из такого файла, документация не говорит | **не проверено**, этап 0 |
| Ответ на `VOICE_MESSAGES_FORBIDDEN` (получатель запретил голосовые в настройках приватности Premium) | [вторично], в документации Bot API нет; обрабатывается, но вживую не проверялось |
| Доступность `api.telegram.org` с вашего VPS | **не проверено**; покажет `pigeondrop telegram check` |
| Строка записи в `messages` и её очередь `transcriptions` создаются в одной транзакции; воркер распознавания работает по аренде и ограждению попыток | [проверено], `STT_SERVICE_PLAN.md` |

## 3. Архитектура

```
 приём записи ─▶ транзакция: messages + transcriptions(pending)
                                    + telegram_deliveries(pending)   ← только если у пользователя есть привязка
                                    │ сигнал «есть работа» и опрос раз в 2 с
 ┌─────────────────────── контейнер сервера (Go) ─────────────────────────────────────┐
 │  воркер доставки (одна горутина)                                                   │
 │   1. берёт самую старую готовую доставку (FOR UPDATE SKIP LOCKED), ставит аренду  │
 │      готова = текст уже есть/не будет (done, failed, skipped, строки нет)          │
 │                или прошло wait_until (по умолчанию 3 минуты)                       │
 │   2. читает <id>.opus, текст из transcriptions, чат из telegram_links              │
 │   3. sendVoice (подпись = текст, если он помещается) ─▶ api.telegram.org           │
 │      длинный текст: голосовое без подписи + sendMessage ответом                    │
 │   4. записывает sent / повтор / ошибку                                             │
 │                                                                                    │
 │  бот (одна горутина): getUpdates (long polling) ─▶ /start <код>, /stop, /help      │
 │   привязывает чат к аккаунту: telegram_links, telegram_link_codes                  │
 │                                                                                    │
 │  API: GET /v1/telegram, POST /v1/telegram/link, DELETE /v1/telegram ─▶ страница    │
 └────────────────────────────────────────────────────────────────────────────────────┘
```

Граница ответственности: Telegram знает только `chat_id`, аудио и текст, которые ему отправили. Вся логика очереди, повторов и привязки в Go-сервере. Клиент Bot API (`internal/telegram`) ничего не знает про пользователей и записи, как клиент распознавания.

## 4. Принятые решения и почему

| Решение | Почему | Что отвергнуто |
|---|---|---|
| Очередь в PostgreSQL, строка доставки создаётся в транзакции приёма | Запись, принятая при привязанном Telegram, не потеряется и не отправится дважды при перезапуске; тот же приём, что у распознавания | Отправка прямо из обработчика приёма (потеря при падении, ожидание текста держало бы запрос) |
| Long polling, а не webhook | Не нужен публичный адрес и секрет вебхука, локально проверяется без туннеля, одна горутина | Webhook: точка входа в интернет, туннель для разработки |
| Доставка ждёт текст до `TELEGRAM_WAIT` | Одно сообщение со всем, что нужно; потолок ожидания не даёт очереди распознавания задержать запись навсегда | Правка подписи позже (второй источник сбоев), текст отдельным сообщением (два уведомления) |
| Привязка одноразовым кодом из страницы | Аккаунт определяется тем, кто вошёл на страницу; бот не просит пароль или почту | Вход по почте и паролю в чате бота (пароль в переписке) |
| Один чат на аккаунт, один аккаунт на чат | Просто и без неожиданностей: новый `/start` заменяет привязку | Несколько чатов, группы |
| Подпись простым текстом, без `parse_mode` | Расшифровка может содержать любые символы; разметка сломала бы отправку | Markdown/HTML с экранированием |
| Длина считается в единицах UTF-16 | Так Telegram считает символы подписи; расчёт по рунам пропустил бы лишнее на эмодзи | Рунное сравнение |
| Повторы по образцу очереди распознавания | Те же понятия: аренда, ограждение попыток, паузы, «сервис недоступен не тратит попытку» | Новая схема |
| Токен не попадает в журнал и в тексты ошибок | Он часть адреса запроса | Печать ошибок как есть |

## 5. Данные

Миграция `00006_telegram.sql`.

**`telegram_links`**: привязка чата к аккаунту.

| Колонка | Смысл |
|---|---|
| `user_id` uuid PK, ссылка на `users`, `ON DELETE CASCADE` | один чат на аккаунт |
| `chat_id` bigint NOT NULL UNIQUE | один аккаунт на чат |
| `username`, `first_name` text | чтобы страница показала, к кому привязано; необязательны |
| `linked_at` timestamptz | |
| `blocked_at` timestamptz | бот заблокирован этим чатом; доставки пропускаются до новой привязки |

**`telegram_link_codes`**: одноразовые коды. Хранится только хеш (как приглашения), сам код показывается один раз в ссылке.

| Колонка | Смысл |
|---|---|
| `code_hash` bytea PK | SHA-256 кода (128 бит случайности, 22 символа base64url) |
| `user_id` uuid, `ON DELETE CASCADE` | чей код |
| `created_at`, `expires_at` timestamptz | жизнь 10 минут |
| `used_at`, `used_chat_id` | использованный код остаётся до чистки, чтобы повтор того же `/start` из того же чата (перезапуск посреди обработки) ответил «готово», а не «ссылка недействительна» |

Живой код у пользователя один: новая ссылка стирает неиспользованные старые.

**`telegram_deliveries`**: очередь доставки, одна строка на сообщение, по образцу `transcriptions`.

| Колонка | Смысл |
|---|---|
| `message_id` uuid PK, `ON DELETE CASCADE` | запись, которую отправляем |
| `state` | `pending`, `running`, `sent`, `failed`, `skipped` |
| `attempts`, `run_after`, `locked_until`, `enqueued_at`, `finished_at` | как у `transcriptions` |
| `wait_until` timestamptz | до этого момента ждём текст |
| `chat_id` bigint | чат, в который пошла первая отправка (повторы идут в тот же) |
| `voice_message_id` bigint | номер голосового в Telegram, когда оно уже отправлено; повтор после сбоя на втором шаге не шлёт голосовое второй раз |
| `with_text` boolean | ушёл ли текст (для оператора) |
| `error_code`, `last_error` | почему не отправлено; `last_error` только для оператора |

Коды `error_code`: `blocked` (чат заблокировал бота или исчез), `unlinked` (привязку сняли до отправки), `rejected` (Telegram отказал и повтор не поможет), `too_many_failures`, `file_missing`, `no_audio` (старый формат Zepp: Ogg нет, а текст пуст).

Строка доставки создаётся при приёме записи, только если у пользователя есть привязка без `blocked_at`. Привязка после приёма старые записи не отправляет.

## 6. Жизненный цикл доставки

```
        приём (есть привязка)
              │
              ▼
          pending ──▶ running ──▶ sent
            ▲  │         │
            │  │         ├──▶ pending (повтор: пауза, попытка вернулась или потрачена)
            │  │         ├──▶ failed  (Telegram отказал / попытки кончились)
            │  │         └──▶ skipped (blocked / unlinked / no_audio)
            │  └── в очередь, пока не готов текст и не прошёл wait_until
            └──── аренда истекла: воркер умер, берёт другой
```

Готовой считается доставка в `pending` с `run_after <= now` и либо без строки `transcriptions` в состоянии `pending`/`running` для этого сообщения, либо с `wait_until <= now`.

## 7. Алгоритм воркера

1. Взять самую старую готовую доставку (аренда `TELEGRAM_TIMEOUT` + 30 с, ограждение номером попытки).
2. Найти привязку пользователя. Нет её или есть `blocked_at`: `skipped` (`unlinked`/`blocked`).
3. Прочитать `<id>.opus` и формат сообщения. Формат Zepp (до упаковки на телефоне) в Ogg не обёрнут: голосовое не отправить. Есть текст: `sendMessage` с ним; текста нет: `skipped` (`no_audio`).
4. Взять текст: состояние `done` и не пусто, иначе без текста.
5. Текст ≤ 1024 (UTF-16): `sendVoice` с подписью. Длиннее: `sendVoice` без подписи, `voice_message_id` сохранить, затем `sendMessage` ответом на него (текст ≤ 4096, больше обрезается с «…»; запись в 65 с столько не даёт).
6. Между отправками в один чат не меньше 1 секунды.
7. Записать `sent`.

Ответы Telegram и что с ними делает воркер:

| Ответ | Вид | Что делаем |
|---|---|---|
| Сеть не дошла (DNS, отказ соединения), 502/503/504 | Unavailable | в очередь, попытка не тратится, паузы 15 с, 30 с, ... до 5 минут, одна запись в журнале на сбой |
| 401 (токен отклонён) | Unavailable | то же, но запись в журнале уровня error, чтобы владелец увидел |
| 429, `retry_after` | RateLimited | в очередь после паузы (не меньше `retry_after`), попытка не тратится, весь воркер ждёт столько же |
| 403 «bot was blocked by the user», «user is deactivated»; 400 «chat not found» | Blocked | у привязки ставится `blocked_at`, доставка `skipped` (`blocked`) |
| 400 `VOICE_MESSAGES_FORBIDDEN` | VoiceForbidden | то же сообщение сразу отправляется как документ (`sendDocument`) |
| Прочие 400 | Rejected | `failed` (`rejected`), повтор не поможет |
| Таймаут после отправки, оборванное соединение, непонятный ответ | Failed | попытка тратится, повтор с паузой (30 с, 2 мин, 10 мин, 1 ч, 6 ч); **исход неизвестен, возможен дубль**: у Telegram нет ключа идемпотентности |
| Остановка сервера | | запись возвращается в очередь без потери попытки (как у распознавания) |

Бот (`getUpdates`, `timeout=30`, только `message`): 409 (тот же токен забрал другой процесс, например старый контейнер при выкатке) означает паузу и повтор, а не падение. Каждое сообщение бота обрабатывается независимо; ошибка одного не останавливает остальные.

## 8. Привязка чата

1. Человек входит на `/pair`, нажимает «Привязать Telegram». `POST /v1/telegram/link` создаёт код и возвращает `https://t.me/<бот>?start=<код>`; имя бота сервер узнаёт у Telegram через `getMe` при старте.
2. Человек открывает ссылку и нажимает «Start». Бот получает `/start <код>`.
3. Бот проверяет: чат личный (не группа); код есть, не истёк, не использован. Привязывает чат (заменяя прежнюю привязку этого аккаунта и этого чата) и отвечает «готово».
4. Страница раз в 3 секунды спрашивает `GET /v1/telegram`, пока открыта ссылка, и показывает «Привязано к @имя».

Команды бота: `/start <код>` привязка, `/start` без кода объясняет, что делать, `/stop` отвязка, `/help`. Ответы бота на двух языках (русский и английский) по языку аккаунта, а до привязки по `language_code` из Telegram.

Безопасность привязки:

- Код одноразовый, живёт 10 минут, хранится хешем, 128 бит. Угадать его нельзя.
- Если кто-то получит чужую ссылку до использования, он привяжет свой Telegram к чужому аккаунту и будет получать его записи. Поэтому ссылка показывается только вошедшему человеку, живёт недолго, а страница всегда показывает, к какому Telegram привязан аккаунт, и даёт «Отключить».
- Бот отвечает только в личных чатах.
- Запрос создания ссылки ограничивается как другие запросы, оставляющие строки в базе.

Что уходит в Telegram: само голосовое и его расшифровка, на серверы Telegram. Человек делает это сам, привязав чат. В документации сервиса надо сказать об этом прямо (политика конфиденциальности, раздел 13).

## 9. API и страница

Все три метода требуют вход через cookie (`cookieAuth`).

| Метод | Ответ |
|---|---|
| `GET /v1/telegram` | `{ available, botUsername?, link? }`. `available: false`, если токен бота не задан; тогда страница раздела не показывает. `link`: `{ username?, firstName?, linkedAt, blocked }` |
| `POST /v1/telegram/link` | `{ url, expiresAt }`; 503 с кодом `unavailable`, если бот выключен |
| `DELETE /v1/telegram` | 204, повторный вызов тоже 204 |

Новый код ошибки `unavailable` в `ErrorCode`. Раздел «Telegram» на `/pair`: статус, кнопка «Привязать Telegram» (ссылка открывается в новой вкладке), после неё опрос раз в 3 секунды (на скрытой вкладке опрос стоит, как у расшифровок), «Отключить».

## 10. Настройки и эксплуатация

| Переменная | Смысл |
|---|---|
| `TELEGRAM_BOT_TOKEN` | токен от @BotFather; пусто: бот выключен, раздела на странице нет, доставок нет |
| `TELEGRAM_WAIT` | сколько ждать текст (1 с..30 мин, по умолчанию 3m) |
| `TELEGRAM_TIMEOUT` | таймаут вызова Telegram (по умолчанию 30s) |
| `TELEGRAM_API_URL` | адрес Bot API (по умолчанию `https://api.telegram.org`); для тестов и локального Bot API-сервера |

Команды оператора (в контейнере сервера):

- `pigeondrop telegram check`: `getMe` (имя бота), проверка, что webhook не задан, ошибки с подсказками. Базу не трогает.
- `pigeondrop telegram status`: сколько привязок и заблокированных, доставок по состояниям, возраст самой старой ожидающей, последняя неудача.

Токен задаёт владелец в Coolify (переменная окружения приложения сервера), как `STT_TOKEN`. В журналах нет ни токена, ни текста расшифровок, ни `chat_id`.

## 11. План работ

| Этап | Что | Как проверяется |
|---|---|---|
| 0 | Ручная проверка формата: настоящие записи через `sendVoice` в личный чат | ответ Telegram содержит `voice` (а не `document`/`audio`), длительность верна, пузырёк с волной проигрывается; результат в раздел 2 |
| 1 | Этот проект; клиент Bot API (`internal/telegram`), переменные окружения, `pigeondrop telegram check` | тесты с поддельным Bot API; токена нет в ошибках |
| 2 | Привязка: миграция (`telegram_links`, `telegram_link_codes`), бот с командами, `/v1/telegram*`, раздел на `/pair` | настоящий PostgreSQL; страница в браузере; привязка боевым ботом |
| 3 | Доставка: `telegram_deliveries`, приём в транзакции, воркер, `telegram status` | настоящий PostgreSQL, отказы Telegram по таблице раздела 7; мутационные проверки |
| 4 | Развёртывание: переменная в Coolify, шаг в `backend/DEPLOY.md`, `CLAUDE.md`, `ARCHITECTURE.md`; запись с часов до чата | `telegram check` на VPS, реальная запись с часов |

Каждый этап отдельным PR. Этапы 2 и 3 не зависят от этапа 0, пока Telegram принимает наши файлы; если нет, в этап 3 добавится перепаковка заголовка.

## 12. Тесты

- Поддельный Bot API (`httptest`): `getMe`, `getUpdates`, `sendVoice`, `sendDocument`, `sendMessage` с заданными ответами: успех, 429 с `retry_after`, 403, 400 (все виды), 401, 409, 5xx, обрыв посреди ответа, медленный ответ.
- Токен не появляется ни в одной ошибке, ни в журнале (проверка поиском по выводу).
- Настоящий PostgreSQL: приём создаёт доставку только при привязке; ожидание текста и срок `wait_until`; аренда и ограждение; повтор после сбоя второго шага не шлёт голосовое второй раз; удаление сообщения убирает доставку; код привязки одноразовый и истекает; повтор `/start` из того же чата отвечает «готово»; привязка второго аккаунта к тому же чату заменяет первую.
- Границы длины подписи (1024 и 4096 единиц UTF-16, эмодзи).
- Мутационные проверки каждого решения, как в этапах 3-5 распознавания.
- Вручную: этап 0 и этап 4 с боевым ботом. Правки подписи, группы и `VOICE_MESSAGES_FORBIDDEN` вживую не проверяются.

## 13. Риски и открытые вопросы

| Риск | Что делаем |
|---|---|
| Telegram не принимает наши Ogg как голосовое (нестандартный заголовок) | этап 0 до всего остального; запасной путь: перепаковка заголовка (`pre-skip`, частота) в Go |
| `api.telegram.org` недоступен с VPS | `telegram check` на этапе 4 до включения; бот выключен без токена |
| Дубль сообщения после обрыва на отправке | принято: у Telegram нет идемпотентности; повтор только для неизвестного исхода; редкий случай |
| Два процесса с одним токеном (выкатка новой версии при старой) | 409 означает паузу; в Coolify проверить порядок остановки |
| Чужая ссылка привязки | раздел 8: короткая жизнь, одноразовость, показ привязки на странице |
| Расшифровка пришла позже срока ожидания | голосовое ушло без текста; текст виден на странице; правка подписи вне работы |
| Политика конфиденциальности | текст не написан (отложено владельцем 2026-10-11); он должен сказать, что при привязке записи и расшифровки уходят в Telegram |
| Старые записи в формате Zepp без обёртки | доставляется только текст; такие записи появляются лишь от старой версии приложения |

## 14. Что нужно от владельца

1. Создать бота в @BotFather и положить токен в локальный файл `backend/.dev/telegram.env` (одна строка `TELEGRAM_BOT_TOKEN=...`, файл не попадает в git), для проверки этапа 0 и 2. Токен в чат не присылать.
2. Написать боту `/start` (по этому сообщению определится ваш `chat_id` для этапа 0).
3. На этапе 4: добавить `TELEGRAM_BOT_TOKEN` в переменные окружения приложения сервера в Coolify и перезапустить.
