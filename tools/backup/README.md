# Резервные копии PigeonDrop

Ежедневная копия того, что нельзя восстановить из кода: **базы `pigeondrop`** (в общем PostgreSQL на VPS) и **записей** (том `pigeondrop-data`, файлы `messages/<id>.opus`). Копировать надо оба вместе: строка в таблице `messages` и файл записи связаны, одно без другого не работает.

Схема та же, что у another-project (`tools/backup` в её репозитории): две независимые половины, которые друг о друге не знают. Systemd-таймер на хосте делает `pg_dump` в файл. Backrest (он уже работает на VPS в Docker) по расписанию делает restic-снимок этого каталога и тома записей в репозиторий `b2` на Backblaze B2. Backrest не получает доступа к Docker-сокету: он только читает каталоги.

```
systemd-таймер (03:15 UTC)
  └─ /usr/local/bin/pigeondrop-db-dump.sh
       └─ docker exec <postgres> pg_dump  →  /var/backups/pigeondrop/pigeondrop.sql
                                             /var/backups/pigeondrop/BACKUP_INFO

Backrest, план `b2-pigeondrop` (03:20 UTC), репозиторий `b2`
  ├─ /backup/pigeondrop-db    ←  /var/backups/pigeondrop                      (только чтение)
  └─ /backup/pigeondrop-data  ←  /var/lib/docker/volumes/<том>/_data          (только чтение)
```

| UTC | Что |
|---|---|
| 02:00 | Coolify копирует свою базу |
| 03:00 | дамп another-project |
| 03:15 | план `b2-another-project-db` (секунды) и **дамп PigeonDrop** |
| 03:20 | **план `b2-pigeondrop`** |
| 03:30 | план `vps` (весь сервер) |

Планы пишут в один репозиторий, а `forget`/`prune` берут в нём эксклюзивную блокировку, поэтому планы не должны стартовать в одну минуту. Наш план идёт после короткого плана another-project и до большого `vps`: от самого `vps` его отделяют десять минут, а он растёт вместе с сервером.

## Что делает каждый скрипт

- **`pigeondrop-db-dump.sh`** (по таймеру) выгружает базу в обычный SQL без сжатия: restic сам сжимает и дедуплицирует, а gzip менял бы каждый байт каждый день. Перед тем как заменить хороший дамп, он проверяет, что дамп дописан (строка `PostgreSQL database dump complete`, обрезанный дамп всё равно большой, поэтому размер ничего не говорит) и что в нём есть `CREATE TABLE`. Пишет во временный файл и переименовывает (операция атомарная: Backrest никогда не увидит половину файла). Рядом кладёт `BACKUP_INFO`: время дампа и число строк каждой таблицы *по самому дампу*, с чем потом сверяется восстановление. Пингует watchdog при успехе и `<url>/fail` при любой ошибке.
- **`pigeondrop-restore-check.sh`** (вручную, после восстановления) загружает дамп из снимка в *отдельную* базу `pigeondrop_restore_test` (никогда в рабочую), сверяет число строк с `BACKUP_INFO` и проверяет файл каждой записи: он есть, его размер равен `bytes_received` из строки, а файл формата Ogg начинается с `OggS`. Файлы без строки он только считает: сервер пишет файл раньше строки, поэтому загрузка в момент снимка оставляет такой файл, и это безвредно.
- **`pigeondrop-backup-common.sh`** общий код: поиск контейнера PostgreSQL по метке Coolify (не по имени: в нём UUID и метка времени деплоя; больше одного подходящего контейнера — ошибка, а не «возьму любой») и работа с ним через `docker exec` (пароль берётся из окружения самого контейнера и на хосте не появляется).

Порядок «сначала дамп, потом файлы» выбран не случайно. Сервер пишет файл записи раньше, чем строку в базу. Если дамп сделан раньше файлов, у каждой строки дампа есть файл, кроме записей, удалённых в промежутке; если наоборот, то строки без файла появятся при любой загрузке в промежутке. Загрузки случаются чаще удалений, поэтому дамп идёт первым и за пять минут до плана.

## Установка (один раз, на VPS)

Репозиторий — источник правды, но на VPS файлы сами не попадают: после любой правки скриптов копируйте их заново.

Команды ниже можно вставлять в терминал как есть, кроме двух мест, где стоят `<угловые скобки>` (адрес сервера в `scp` и значения в файле настроек): их надо заменить на своё *до* вставки. Оболочка принимает угловые скобки за перенаправление и отвечает `No such file or directory`.

### 1. Скрипты и юниты

С вашего Mac, из корня репозитория:

```bash
scp tools/backup/pigeondrop-backup-common.sh tools/backup/pigeondrop-db-dump.sh tools/backup/pigeondrop-restore-check.sh \
    tools/backup/pigeondrop-db-dump.service tools/backup/pigeondrop-db-dump.timer <пользователь>@<vps>:/tmp/
```

На VPS:

```bash
sudo install -m 755 /tmp/pigeondrop-backup-common.sh /tmp/pigeondrop-db-dump.sh /tmp/pigeondrop-restore-check.sh /usr/local/bin/
sudo install -m 644 /tmp/pigeondrop-db-dump.service /tmp/pigeondrop-db-dump.timer /etc/systemd/system/
sudo mkdir -p /var/backups/pigeondrop
```

### 2. Настройки: `/etc/pigeondrop-backup.env`

Нужна метка общего PostgreSQL. Это та же метка, что у дампа another-project; посмотрите её там:

```bash
grep -h DB_LABEL /usr/local/bin/another-project-db-dump.sh /etc/systemd/system/another-project-db-dump.service
docker ps --format '{{.Names}}\t{{.Image}}\t{{.Label "coolify.resourceName"}}' | grep postgres
```

Нужна строка вида `coolify.resourceName=postgresql-database-<uuid>`. Есть ли в этом PostgreSQL база `pigeondrop` (она создана по `backend/DEPLOY.md`, шаг 3), проверит первый запуск дампа в шаге 3: если базы нет, он остановится с сообщением `has no database named 'pigeondrop'`.

Создайте файл (права 600, адрес watchdog — это «ключ»: тот, у кого он есть, может прислать успешный пинг и заглушить тревогу, в чат его не присылайте):

```bash
sudo tee /etc/pigeondrop-backup.env > /dev/null <<'EOF'
PIGEONDROP_DB_LABEL=coolify.resourceName=postgresql-database-<uuid>
PIGEONDROP_HEALTHCHECK_URL=https://hc-ping.com/<uuid-проверки>
EOF
sudo chmod 600 /etc/pigeondrop-backup.env
```

Проверку в healthchecks.io заведите отдельную для дампа: период 1 день, запас (grace) пара часов. Адрес можно не задавать, тогда пинга просто не будет, но без него остановившийся таймер никто не заметит.

### 3. Запуск и первый дамп

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now pigeondrop-db-dump.timer
sudo systemctl start pigeondrop-db-dump.service && journalctl -u pigeondrop-db-dump -n 20 --no-pager
cat /var/backups/pigeondrop/BACKUP_INFO
```

В `BACKUP_INFO` должны быть `dumped_at` и строки `rows.users=…`, `rows.messages=…` и так далее. Если команда пишет `no running postgres container carries the label`, метка в `/etc/pigeondrop-backup.env` неверна.

### 4. Подключить каталоги к Backrest

Нужен путь тома с записями. Coolify добавляет к имени тома UUID приложения (получается что-то вроде `lysivnglgqwx3xbuhvccw2ny-pigeondrop-data`), поэтому путь ищется по имени, подставлять ничего не надо:

```bash
docker volume inspect "$(docker volume ls -q | grep 'pigeondrop-data$')" --format '{{.Name}}  {{.Mountpoint}}'
```

В ответе одна строка: имя тома и путь вида `/var/lib/docker/volumes/<имя-тома>/_data`. Если строк две или больше (старый том от прежней установки), `docker volume inspect` ответит ошибкой: тогда выберите тот, что подключён к работающему приложению (`docker inspect <контейнер приложения> --format '{{range .Mounts}}{{.Name}} {{end}}'`).

Монтирование добавляется через override-файл, чтобы не править основной `docker-compose.yml`. **Если `/opt/backrest/docker-compose.override.yml` уже есть** (в нём монтирование another-project), добавьте две строки в его список `volumes`, а второй файл не создавайте:

```yaml
services:
  backrest:
    volumes:
      - /var/backups/pigeondrop:/backup/pigeondrop-db:ro
      - /var/lib/docker/volumes/<имя-тома>/_data:/backup/pigeondrop-data:ro
```

(Это содержимое файла, а не команда: `<имя-тома>` замените на имя из ответа выше.)

Проверьте слияние (эта команда ничего не запускает), все старые монтирования должны остаться в списке, затем примените:

```bash
cd /opt/backrest && docker compose config
docker compose up -d
docker exec backrest ls /backup/pigeondrop-db /backup/pigeondrop-data/messages
```

Если `ls` отвечает `Permission denied` на томе, Backrest работает не от root: другой способ дать ему чтение выбирать надо по тому, как он у вас запущен, спросите меня.

### 5. План в Backrest

Репозиторий `b2` уже есть (его адрес обязан начинаться с `s3:`, иначе restic считает его локальным путём). Новый план:

| Поле | Значение |
|---|---|
| Plan ID | `b2-pigeondrop` |
| Repo | `b2` |
| Paths | `/backup/pigeondrop-db` и `/backup/pigeondrop-data` (два пути в одном плане: один снимок держит согласованную пару) |
| Excludes | `.tmp-*` (временные файлы, в которые сервер пишет запись, пока её принимает) |
| Schedule | cron `20 3 * * *` (UTC, как у остальных планов) |
| Retention | по времени: daily 7, weekly 4, monthly 12 |
| Hooks | Healthchecks для этого плана (отдельная проверка: период 1 день, запас пара часов). Telegram на репозитории `b2` уже покрывает ошибки всех планов |

Два пинга нужны оба и не заменяют друг друга: пинг плана молчит, когда снимок не дошёл до B2; пинг скрипта молчит, когда дамп устарел. Если таймер остановится, Backrest продолжит ночь за ночью снимать один и тот же старый файл и докладывать об успехе.

Запустите план вручную (**Backup now**). В **Snapshot Browser** должны быть `/backup/pigeondrop-db/pigeondrop.sql`, `BACKUP_INFO` и `/backup/pigeondrop-data/messages/…`.

## Проверка восстановления (обязательна)

Копия, которую ни разу не восстанавливали, копией не считается. Сделайте это один раз сейчас, и ещё раз после новой миграции, меняющей схему, и иногда просто так.

1. В Backrest: план → снимок → **Snapshot Browser** → корень снимка (оба пути) → значок восстановления → **Restore to path**: `/restore/pigeondrop-test-1`.
   - Каталог **не должен существовать**: restic создаёт его сам и иначе отказывает (`target directory already exists`). При повторе берите новое имя.
   - Путь должен лежать внутри `/restore`: он смонтирован с хоста (`/opt/backrest/restore`). Любой другой путь окажется внутри контейнера и пропадёт при его пересоздании.
2. На VPS:

   ```bash
   sudo pigeondrop-restore-check.sh /opt/backrest/restore/pigeondrop-test-1
   ```

   Скрипт сам находит восстановленные каталоги (`pigeondrop-db`, `pigeondrop-data`) и читает настройки из `/etc/pigeondrop-backup.env`. Он занимает секунды, а в конце печатает `RESTORE CHECK PASSED` или `FAILED` с причинами. Рабочую базу он не трогает: загрузка идёт в `pigeondrop_restore_test`, которая удаляется (`--keep` оставит её для просмотра, удалите вручную).
3. Что значат сообщения:

   | Сообщение | Что случилось |
   |---|---|
   | `the dump is older than 36 hours` | таймер дампа остановился, а restic снимал старый файл. Для сознательного восстановления старого снимка есть `--allow-stale` |
   | `the dump did not load` | дамп повреждён; `psql` остановился на первой ошибке |
   | `restored N rows, the dump held M` | при восстановлении потеряны строки |
   | `missing` / `wrong size` / `not an Ogg file` | том с записями не скопирован или скопирован не весь |
   | `N file(s) have no row` | предупреждение, не ошибка: загрузки около момента снимка |

4. Уберите восстановленное: `sudo rm -rf /opt/backrest/restore/pigeondrop-test-1`.

## Восстановление с нуля (после потери сервера)

Порядок и что нужно иметь под рукой:

1. **Пароль репозитория restic** и ключи B2. Пароль невосстановим: без него снимки нечитаемы. Он должен лежать в менеджере паролей вместе с `APP_KEY` Coolify (`/data/coolify/source/.env`).
2. Поднять Coolify и PostgreSQL (копия базы Coolify лежит в снимке плана `vps`, `/backup/coolify`), восстановить из неё приложение PigeonDrop или создать заново по `backend/DEPLOY.md`.
3. Создать роль и базу (`backend/DEPLOY.md`, шаг 3). Роли в дамп одной базы не входят.
4. Восстановить снимок плана `b2-pigeondrop` (как выше), загрузить дамп **от имени роли** `pigeondrop`, чтобы она владела таблицами (`SET ROLE`, потому что дамп сделан с `--no-owner`):

   ```bash
   ( echo 'SET ROLE pigeondrop;'; cat /opt/backrest/restore/<имя>/backup/pigeondrop-db/pigeondrop.sql ) \
     | docker exec -i <postgres> sh -c 'PGPASSWORD="$POSTGRES_PASSWORD" psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -h 127.0.0.1 -d pigeondrop'
   ```

   `psql` напечатает одну строку `set_config`: это нормально. `ON_ERROR_STOP=1` обязателен: иначе `psql` сообщает об успехе после пропуска всех упавших команд, и половинчатое восстановление выглядит как полное.
5. Положить файлы записей в том `pigeondrop-data` (каталог `messages/`) и владельцем сделать пользователя `65532:65532`, под которым работает контейнер (иначе он не сможет в них писать).
6. Запустить приложение. Миграции применятся сами (`MIGRATE_ON_START=true`), и версия схемы (`goose_db_version`) возьмётся из дампа.

## От чего это защищает

| Сбой | Как защищено |
|---|---|
| Дамп оборвался (диск, соединение) | проверяется завершающая строка и наличие таблиц; хороший файл не заменяется, watchdog получает `/fail` |
| `pg_dump` упал | то же; любой неудачный выход (в том числе тот, под который нет своего сообщения) пингует `/fail` |
| Backrest снимает недописанный дамп | дамп пишется во временный файл и переименовывается атомарно |
| Таймер остановился, и никто не заметил | пинг watchdog при успехе: тревога в его отсутствии; плюс `dumped_at` в `BACKUP_INFO` виден при любом восстановлении |
| Контейнер пересоздан или переименован | поиск по метке Coolify, а не по имени |
| Выгрузили не тот сервер (общий PostgreSQL) | подходящий контейнер должен быть ровно один, и база `pigeondrop` должна в нём быть, до `pg_dump` |
| Восстановление выглядит успешным, а данных нет | сверка числа строк с дампом и проверка файла каждой записи |
| Восстановление затёрло рабочую базу | оно идёт только в `pigeondrop_restore_test`; совпадение имени с рабочей базой запрещено, существующая база с таким именем не перезаписывается |

## О чём стоит знать до публикации сервиса

- **Записи голоса — персональные данные.** Bucket в `eu-central-003` (ЕС), restic шифрует на стороне клиента, это хороший вариант для европейской аудитории.
- **Удалённая запись остаётся в копиях** до 12 месяцев (`monthly 12`): человек нажал «удалить», а в старых снимках файл ещё есть. Это надо либо описать в политике конфиденциальности, либо сократить срок хранения для этого плана. Решение по сроку за вами.
- Пока записей мало, копия стоит копейки (restic хранит каждый файл один раз, а записи не меняются). Лимит сервера: 100 МиБ записей на аккаунт.

## Что проверено и что нет

Скрипты прогнаны тестом `tools/backup/test/test-backup.sh` на настоящем PostgreSQL 17 в Docker (настоящие миграции, `pg_dump`, `psql`, `docker exec`): дамп и его `BACKUP_INFO`, каждый вид сбоя дампа, выбор сервера, чтение настроек из файла, восстановление, каждая поломка восстановления (см. таблицу выше) и загрузка дампа на пустой сервер от имени роли приложения (шаг 4 раздела «с нуля»). Тест идёт в CI вместе с `shellcheck` (задача «Backup scripts»). Тест проверен поломками: я по одной ломал 21 защиту в скриптах (проверка завершения дампа, поиск контейнера, сверка строк и файлов, защита рабочей базы, чтение настроек и другие), и каждый раз тест падал.

Не проверено, потому что у меня нет доступа к вашему VPS и Backrest:
- установка на VPS, юниты systemd, настоящее имя тома и права Backrest на него;
- настоящее восстановление через интерфейс Backrest (раскладка каталогов в восстановленной папке; скрипт ищет каталоги по имени и не зависит от неё, но я этого не видел);

Сделайте проверку восстановления сами сразу после установки и, если что-то расходится, пришлите вывод.
