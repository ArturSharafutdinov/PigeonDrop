# Проверка распознавания речи на VPS

Разовая проверка образа `stt/` (Parakeet TDT v3) на той машине, где он будет работать. Она повторяет на VPS то, что `bench/stt` делал на Mac (раздел 7 в [`STT_COMPARISON.md`](../../STT_COMPARISON.md)): настоящий образ с боевыми лимитами, ваши записи через настоящий протокол, замер скорости и памяти. К сервису она не относится: ничего не развёртывается, в Coolify не добавляется, сервер её не видит (папка `tools/` лежит вне `backend/`, как и `tools/backup/`, поэтому правка здесь не запускает деплой).

**Решения, с которыми проверка сверяется** (владелец, 2026-10-10): одна запись за раз (один поток обработки, одна копия модели); контейнеру 3 ГБ памяти без подкачки. Сколько ядер давать, проверка и должна показать: она гоняет 1 и 2.

## Что проверяется

| Шаг | Что делает | Зачем |
|---|---|---|
| Лимиты | Контейнер запускается так, как его запустит Coolify (`--memory 3g --memory-swap 3g --cpus N`), и читает свои лимиты; отдельный контейнер на 256 МиБ пытается взять 700 МиБ | Лимиты действительно применяются, подкачки нет, при нехватке памяти контейнер убивается (код 137), а не уходит в swap |
| Скорость (`speed`) | Для 1 и 2 ядер новый контейнер: время загрузки модели, первый вызов, 2 круга по вашим 21 записи, 3 вызова с записью на 60 с | Укладывается ли минутная запись в таймаут 90 с; сколько секунд звука в секунду; сколько процессорного времени на минуту звука |
| Тексты | Сравнение каждого ответа с текстом, который на тех же записях дал Mac | x86 и arm могут считать чуть по-разному; нужно знать, меняются ли тексты |
| Память (`memory`) | Два вызова одновременно (один должен получить 429); затем проходы по 31 записи (21 ваша, 9 длин от 8 до 56 с, запись на 60 с) вперемешку, память контейнера после каждого вызова | Хватает ли 3 ГБ и перестаёт ли память расти (на Mac потолок 2232 МиБ, последний подъём на вызове 54) |
| Сторож | Следит за памятью самой машины и убивает контейнер, если у машины остаётся меньше 300 МиБ | Проверка не должна отнять память у остальных приложений на общем VPS |

Не проверяется (это этап 5 плана): связь контейнеров в Coolify по имени, поведение в окне бэкапа (03:15–03:30 UTC), образ, собранный в CI, неделя непрерывной работы, cgroup v1 (проверка его не поддерживает и скажет об этом сразу).

## Что проверка делает с машиной

- Запускает контейнеры с лимитом 3 ГБ памяти без подкачки и с квотой 1–2 ядра. Порт открыт только на `127.0.0.1`. Токен случайный на каждый запуск.
- Не начинает, если у машины доступно меньше 3,5 ГБ (3 ГБ лимит плюс 512 МиБ запаса); `--force` отключает эту защиту.
- Во время работы убивает контейнер, если доступной памяти машины стало меньше 300 МиБ, и пишет об этом в итоге.
- По окончании (и при Ctrl-C) удаляет свои контейнеры (`pigeondrop-stt-check`, `pigeondrop-stt-check-oom`). Остальные контейнеры не трогает.
- Скорость будет меньше обычной, если в это время что-то ещё грузит машину; в отчёт попадает нагрузка (load average) и steal (время, которое хозяин виртуальной машины отдал соседям). Лучше запускать в тихое время.
- В сеть ничего не отправляется. Выход в интернет нужен только для сборки образа (пакеты `pip` и модель с Hugging Face).

## Как запустить

**1. На Mac, в клоне репозитория** (там, где лежит `bench/stt/data` с вашими записями):

```bash
tools/stt-vps-check/pack.sh
scp bench/stt/data/stt-vps-check.tar.gz ПОЛЬЗОВАТЕЛЬ@VPS:~/
```

Архив около 5 МБ: скрипт, исходники образа (`stt/Dockerfile`, `stt/app`), 21 запись, запись на 60 с, тексты стенда. В нём ваш голос: он нужен только на вашем VPS.

**2. На VPS:**

```bash
tar xzf stt-vps-check.tar.gz && cd stt-vps-check
docker build -t pigeondrop-stt image     # 3–5 минут, образ 1,6 ГБ; нужен выход в интернет
python3 check.py --quick                 # первая проба, около 5 минут: лимиты и скорость
```

Если проба прошла, полная проверка (лучше в `tmux`/`screen` или через `nohup`, чтобы обрыв SSH её не прервал):

```bash
nohup python3 check.py > check.log 2>&1 &
tail -f check.log
```

Полная проверка занимает 20–30 минут (шаг памяти ограничен 30 минутами). Нужны Docker с cgroup v2 и Python 3.8 или новее; больше ничего. Сборка на VPS нагружает 1–2 ядра на несколько минут: если на общем VPS собирать не хочется, образ можно собрать на Mac под `linux/amd64` и передать через `docker save | ssh ... docker load` (этот путь не пробовался: под эмуляцией сборка медленная, а библиотеки модели там могут не запуститься).

**3. Что прислать.** Файл `out/<время>/report.md` целиком (он сложен так, чтобы его можно было вставить в чат; текстов записей в нём нет, кроме тех, что отличаются от Mac). Если в итоге есть «СБОЙ» или «ВНИМАНИЕ», пригодится ещё `check.log`.

**4. Убрать.** Записи на VPS нужны только на время проверки:

```bash
cd ~ && rm -rf stt-vps-check stt-vps-check.tar.gz
docker rmi pigeondrop-stt          # если образ больше не нужен
```

## Как читать результат

В отчёте таблица «Вердикт»: каждая проверка получает «ОК», «ВНИМАНИЕ», «СБОЙ» или «не проверялось». Скрипт завершается с кодом 1, если есть «СБОЙ», и с кодом 2, если проверку нельзя было продолжить (например, не хватило памяти у машины).

| Проверка | ОК | ВНИМАНИЕ | СБОЙ |
|---|---|---|---|
| Лимиты | `memory.max` равен 3 ГиБ, подкачки нет, квота процессора как задана, потоков модели столько же, сколько ядер | потоков не столько, сколько ядер | другой лимит памяти, подкачка включена, другая квота |
| Сверх лимита | контейнер убит (код 137) | | выжил или код другой |
| Ответы | каждый вызов ответил 200 | | любой другой ответ |
| Тексты | все совпали с Mac дословно | есть отличия (они в отдельной таблице) или ответ менялся между кругами | |
| Запись на 60 с | худший вызов не больше 30 с (тройной запас до таймаута 90 с) | до 60 с | больше 60 с |
| Память | запас до лимита 512 МиБ и больше, пик перестал расти | запас 128–512 МиБ; или пик рос во второй половине серии; или вызовов меньше 30 | запас меньше 128 МиБ; контейнер убит; ни одного вызова |
| Одна запись за раз | из двух одновременных одна принята, вторая получила 429 `busy`, потом сервис отвечает | | иначе |
| Свободная память машины | в худший момент доступно не меньше 1 ГиБ | 300 МиБ – 1 ГиБ | проверку пришлось остановить |

Что сравнивать с Mac (Apple M4 Pro): 20 с звука в секунду на 2 ядрах, 4,3 процессорной секунды на минуту звука на 1 ядре, 49,6-секундная запись за 4 с на 1 ядре, пик памяти 2232 МиБ из 3072. Ядро VPS обычно в 2–5 раз медленнее. Пороги выше выбраны так, чтобы при таком замедлении всё ещё получалось «ОК»; важнее всего строка «Запись на 60 с» (таймаут `STT_TIMEOUT` у сервера 90 с) и «Память».

«Пик» это `memory.peak` контейнера, то есть всё, что ему засчитывается, включая кэш файлов модели; «своя память (anon)» это то, что процесс держит сам и что нельзя сбросить при нехватке. Убивает по лимиту именно нехватка после сброса кэша, поэтому пик с кэшем это оценка с запасом.

## Параметры

| Параметр | Что делает |
|---|---|
| `--quick` | только лимиты и скорость, один круг |
| `--steps oom,speed,memory` | какие шаги запускать |
| `--cpus 1,2` | сколько ядер давать на шаге скорости; `--soak-cpus` задаёт число ядер на шаге памяти (по умолчанию наибольшее) |
| `--passes 6`, `--soak-minutes 30` | шаг памяти: сколько проходов и не дольше скольки минут |
| `--rounds 2`, `--long-repeats 3` | шаг скорости: кругов по записям и вызовов с записью на 60 с |
| `--memory 3` | лимит памяти в ГБ |
| `--image`, `--data`, `--reference`, `--out` | другой образ, каталог записей, тексты для сверки, куда писать результат |
| `--force` | не проверять, что у машины достаточно свободной памяти |

Сырые результаты рядом с отчётом: `requests.jsonl` (каждый вызов: время, процессорное время, память, **текст**), `samples.jsonl` (память раз в секунду на шаге памяти), `facts.json`.

## Тесты

```bash
python3 -m unittest discover -s tools/stt-vps-check
```

Тесты идут без Docker и модели: сервис заменён заглушкой, разбор файлов cgroup и `/proc` проверяется на образцах, граничные случаи вердикта перебираются. Они входят в CI (задача «Speech recognition service»). Весь путь (настоящий образ, лимиты, шаги) проверен на Mac с Docker Desktop; на Linux с процессором x86 это впервые случится на вашем VPS.
